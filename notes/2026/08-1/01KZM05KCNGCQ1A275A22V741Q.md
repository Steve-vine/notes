`astral-sh/setup-uv` failed **three times** during the Sprint 31 release with a bare `##[error]fetch failed`, each time while resolving the uv version:

```
Trying to find version for uv in: .../pyproject.toml
Could not find file: .../pyproject.toml          # it looks at the repo root; ours is app/backend/
Could not determine uv version from uv.toml or pyproject.toml. Falling back to latest.
Fetching manifest data from https://raw.githubusercontent.com/astral-sh/versions/main/v1/uv.ndjson ...
##[error]fetch failed
```

It took out `deps-scan` twice (blocking a PR merge and, because `build-images` has `needs: [… deps-scan …]`, the staging deploy) and `sast` once on the **push → main** pipeline, which per ADR 0036 "should never go red". Every occurrence was on the self-hosted `compass-runners` in g5, and the job's real work never ran — Semgrep and pip-audit were skipped, not failed.

**Two things to fix, and the first makes the second moot:**

1. **Pin the uv version in the workflow** (`with: version: "x.y.z"`, or point `pyproject-file: app/backend/pyproject.toml` at the real file). setup-uv only fetches the manifest because it cannot find a version — the repo root has no `pyproject.toml`, ours is under `app/backend/`. Pinning removes the outbound fetch entirely and makes the toolchain reproducible, which is the ADR 0008 immutability argument applied to CI.

2. **The underlying outbound-fetch flakiness.** `raw.githubusercontent.com` and npm's audit endpoint both failed intermittently from the runners in the same session (`npm error audit endpoint returned an error`). That smells like the MTU issue the g5 estate has had before. Worth checking the runner pod MTU against the CNI's, since it will keep biting anything that fetches at job start.

**Also worth considering**: `deps-scan` gating `build-images` means a transient scan failure blocks deploys. That is the right default for a *real* finding, but a network flake shouldn't stop a release — the retry ergonomics deserve a look once (1) is done.

Raised from the Sprint 31 release (COM-191…195), where working around this cost several re-runs.
