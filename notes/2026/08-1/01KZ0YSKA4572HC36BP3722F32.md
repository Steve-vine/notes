With environment values interchangeable in practice, this becomes **the load-bearing tagging rule in the estate** — every other derivation keys off it, and unlike env values it is unambiguous, checkable and fixable.

- **Missing both** → the Resource's environment dimension is unresolvable and it belongs to no Application or platform grouping.
- **Carrying both** → ambiguous, and a compliance error.
- Extend the existing coverage/compliance report rather than building a parallel one; measure over the entities an integration *knows*, not the ones it has *tagged* (the denominator lesson already recorded in the Tag Dictionary design).

Also surfaces the **untagged containment root** case from the environments task — a cluster with no `project`/`env` leaves everything beneath it without an infrastructure environment. Four untagged clusters is an actionable list; four thousand untagged resources is not, so report the root, not the leaves.

**UI**: on the existing Tag Cloud hygiene view — per integration, so "these 12 EC2 instances carry neither" is assignable work.

**Acceptance**: the report names every Resource failing the rule, grouped so the fix is proportionate to the cause; a resource carrying both keys is flagged distinctly from one carrying neither.
