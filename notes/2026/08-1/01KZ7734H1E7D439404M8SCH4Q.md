From functional testing 2026-08-04 (Steve): filter dropdowns across the app behave and look differently page by page. Standardise them — every filter dropdown should:

1. **Open downward** (the Incidents/Issues page one opens upward today)
2. **Support multi-select**
3. **Be clearable per-dropdown** (one control clears that filter's selections)
4. **List entries alphabetically**
5. **Look identical everywhere**

## The good news — the target component already exists

`CheckboxFilter` (`components/CheckboxFilter.tsx`, ISE-175/ISE-477-490 FilterPanel work) already does most of this: fixed-width one-line trigger that never grows with selections ("3 selected"), tick-list multi-select, and an `Input.ClearButton` per dropdown. The task is **adoption + two behaviour fixes**, not a new component.

Current adoption is split (grep survey 2026-08-04):

| Widget | Where |
|---|---|
| `CheckboxFilter` (multi, clearable) | IssuesPage (5×), SignalsPage |
| Plain single-`Select` | EstatePage (4×), EventsPage (3×), PlatformLogPage (3×), AuditPage (2×), AgentRunsPage, ApplicationsPage, DashboardsPage, TagCloudPage, SettingsPage, PlaybookDeskSection |

## Scope

**A. Fix the two behaviour gaps in `CheckboxFilter` itself** (everyone inherits):
- **Direction**: pin the dropdown downward — Issues (the "Incidents" screen) opens upward today. Mantine Combobox flips by available space; the panel sits near the top of the page, so upward means it was let float. Pin `position: 'bottom-start'` with `middlewares={{ flip: false }}` (or equivalent) so direction is constant everywhere. If pinning can clip on short viewports, prefer constant-downward + internal scroll — consistency was the ask.
- **Sort**: options render in caller order today. Sort by label (`localeCompare`) inside the component, so no caller can produce an unsorted filter. Exception to decide in plan mode: **severity** filters — critical>high>medium is arguably the right order for that one; if kept, make it an explicit opt-out prop (`order="ranked"`) rather than caller-side sorting, so the default stays alphabetical.

**B. Migrate every filter-section `Select` to `CheckboxFilter`** — the full list above. Notes:
- Each migration turns a single-value filter param into a list; most backend endpoints take one value, so either the UI ANDs are re-queried per value, the param becomes repeatable (`type=a&type=b`), or the endpoint grows list support — **check per page**; several (Estate `type`, Events `event_type`, Platform Log `level`) may be single-valued in the API today. Where the API is single-valued and extending is disproportionate, migrating to the same *visual* component in single-select mode is acceptable — look-alike was the ask; note it in the PR.
- **Sort/order controls are NOT filters** — a "Sort by" Select (Estate list, Tag cloud) keeps its ranked order and single-select; leave those out of scope, but restyle if trivially cheap.
- Settings-page form Selects (model pickers etc.) are forms, not filter sections — out of scope.

**C. Regression guards**: a shared test for CheckboxFilter asserting downward opening (jsdom can assert the position prop/data-attribute — the ISE-515 lesson: assert the property that carries the intent), alphabetical order, multi-select toggling and clear-per-dropdown. Per-page tests keep passing with the new widget (the `getByLabelText`-matches-column-headers gotcha from the ISE-477 batch applies).

## Definition of done

Every filter section in the app presents the same dropdown: opens downward, multi-select with count label, per-dropdown clear, alphabetical entries (severity optionally ranked by explicit prop). Verified by eye on: Issues, Signals, Estate, Events, Audit, Platform Log, Agent Runs, Applications, Dashboards, Tag Cloud.
