Live-found 2026-08-04 (spotted in the worker logs while checking the M365 enable — another case for ISE-531's Platform Log):

```
WARNING cloudflare pages discovery failed
HTTP 400: 8000024: Invalid list options provided. Review the `page` or `per_page` parameter.
```

Fires on every Cloudflare sync (~15 min). Consequence: **Cloudflare Pages projects are never discovered** — `_discover_pages` (`cloudflare.py:1206`) degrades to an empty list, so any Pages project is absent from the estate. Whether this account has any is currently unknowable from ISE precisely because the call fails; part of the fix is finding out.

## Root cause

`CloudflareClient.get_all` (`cloudflare.py:415`) unconditionally appends `page`/`per_page=50` (`_PER_PAGE`, line 79) to every collection call. `/accounts/{account}/pages/projects` rejects those params — the Pages endpoints don't follow the standard v4 `result_info` page-numbering contract the rest of the connector's collections use. Every other `get_all` caller works; Pages is the odd one out.

## Fix

Verify the endpoint's actual contract first with the stored token (probe-in-pod pattern), then either:

1. **Plain GET without pagination params** for this endpoint (Pages project counts are small; if the response indicates more results exist, log honestly rather than silently truncating — the no-silent-caps rule), or
2. Follow whatever cursor/other pagination the endpoint actually offers, kept **local to `_discover_pages`** — do not grow `get_all` a per-endpoint switch; the anomaly should live next to the anomalous endpoint.

Add the regression guard the other slices have: a test stubbing the seam that asserts pages discovery sends acceptable params (reintroduce the bug, watch it fail — the ISE-515 verification habit).

## Acceptance

A full Cloudflare sync with zero `pages discovery failed` warnings, and either Pages projects present in the estate as `workload` entities (`cloudflare_service: pages`) or a verified-true "this account has no Pages projects".
