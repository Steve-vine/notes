Decided by Steve 2026-08-09: **a manually-created incident should be able to match and execute a playbook.** Today it structurally cannot.

```python
def match_playbooks(db, issue):
    if issue.finding_id is None:
        return []          # a hand-raised incident stops here, always
    finding = db.get(Finding, issue.finding_id)
    ...
    Playbook.kind == finding.kind
```

Matching keys entirely off the **finding** behind an issue. A hand-raised incident has no finding, so the function returns empty before kind, entity or anything else is considered. No playbook can ever match one — the docstring says so ("Empty for a manual issue with no signal to key on") and treats it as a definition rather than a gap.

**Why that is the wrong default.** Hand-raising an incident is exactly what an operator does when ISE has *not* noticed something yet — a server somebody reports as dead over the phone. That is precisely the moment a playbook is most useful, and precisely the moment ISE currently offers none. It makes the manually-raised incident a second-class citizen in the one workflow it exists for.

**The design question to settle first** (this is a decision, not just code): if there is no finding, what does a playbook key on?

1. **The entity.** An incident about a known entity can match playbooks scoped to that entity, plus any unscoped ones. Cheap and safe, but says nothing about *what kind* of problem it is.
2. **An operator-chosen kind.** Let whoever raises the incident pick the kind — which makes `kind` a vocabulary an operator has to know, and today it is a free-text field they can and did fill with something no finding ever produces ("Not responding" vs `server_unreachable`). If we go this way, the field needs to offer the real kinds rather than accept prose.
3. **Both** — entity narrows, kind selects.

Option 3 is probably right, but the load-bearing part is (2): **`kind` is currently free text on the playbook and an exact-match join on the finding.** Whatever we choose, a human typing a kind that no detector emits must not silently produce "no playbooks" forever.

**Also in scope**: whether a manual incident can *execute* a desk-executable playbook, not merely see it. Steve's answer is yes. Check what `issues.py:1051` (`desk_state == "desk_executable"`) and `ai/playbook_runner.py:47` (`if playbook not in match_playbooks(...)`) do once matching can succeed without a finding — the runner's guard is written against the same function, so fixing matching may be most of the work.

**Acceptance**: an incident raised by hand against a known entity offers applicable playbooks; a desk-executable one can be run from it; and a playbook whose kind matches nothing real is visibly wrong at authoring time rather than silently inert.
