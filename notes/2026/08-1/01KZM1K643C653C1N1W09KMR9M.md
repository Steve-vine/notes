Decided by Steve 2026-08-09: **a manually-created incident should be able to match and execute a playbook.** Today it structurally cannot.

```python
def match_playbooks(db, issue):
    if issue.finding_id is None:
        return []          # a hand-raised incident stops here, always
    finding = db.get(Finding, issue.finding_id)
    ...
    Playbook.kind == finding.kind
```

Matching keys entirely off the **finding** behind an issue. A hand-raised incident has no finding, so the function returns empty before kind, entity or anything else is considered. No playbook can ever match one — the docstring says so ("Empty for a manual issue with no signal to key on") and treats it as a definition rather than a gap.

**Why that is the wrong default.** Hand-raising an incident is exactly what an operator does when ISE has *not* noticed something yet — a server somebody reports as dead over the phone. That is precisely the moment a playbook is most useful, and precisely the moment ISE currently offers none.

---

## DECIDED 2026-08-10

**Matching keys on entity AND kind** (option 3 of the three below), and **`kind` becomes a closed vocabulary declared by connectors**.

**`signal_kinds()` — a new connector-contract sibling** to `sweep_specs()` (ISE-498, ADR 0085) and `threshold_specs()` (ISE-578, ADR 0088). Each connector declares the kinds its detectors emit; the registry aggregates them; the playbook authoring form becomes a Select over that list and the API refuses a kind no connector declares.

Correcting a wrong assumption first: **`kind_dictionary.py` is NOT this.** It maps Kubernetes CRD kinds onto canonical *entity types* (ADR 0046) and has nothing to do with signal kinds. There is no vocabulary of signal kinds anywhere today — `PlaybooksPage.tsx:164` is a bare `TextInput` labelled "Signal kind" with examples in its description, which is how "Not responding" got in.

Declared beats `SELECT DISTINCT kind FROM finding` because a kind must be offerable *before it has ever fired* — otherwise a fresh install offers an empty list and the silent-mismatch trap returns.

**The kinds to declare, from the current code:**

| Connector | Kinds |
| --- | --- |
| datadog | `monitor_alert` |
| kubernetes | `pending_pod`, `crashloop`, `oom_kill`, `unhealthy_workload`, `node_not_ready`, `node_pressure`, `node_flapping` |
| entraid | `identity-protection`, `app-credential-expiry`, `app-registration-hygiene` |
| github | `workflow_failure`, `dependabot_alert`, `code_scanning_alert` |
| m365 | `service-health`, `license-pool`, `license-status` |
| servers, freshservice, cloudflare, azure, aws, statuspage, webhook | audit each while implementing — the Obs Loop kinds (`failing_probe`, `estate_drift`) need a home too, and packs (ADR 0094) declare their own |

**Open sub-question for implementation**: whether packs and webhook sources — whose kinds are data, not code — extend the vocabulary at runtime. They should; the aggregation just needs to read them alongside the connector declarations.

---

**Also in scope**: whether a manual incident can *execute* a desk-executable playbook, not merely see it. Steve's answer is yes. Check what `issues.py:1051` (`desk_state == "desk_executable"`) and `ai/playbook_runner.py:47` (`if playbook not in match_playbooks(...)`) do once matching can succeed without a finding — the runner's guard is written against the same function, so fixing matching may be most of the work.

**Acceptance**: an incident raised by hand against a known entity offers applicable playbooks; a desk-executable one can be run from it; and a playbook can no longer be authored against a kind nothing emits.
