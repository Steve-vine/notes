Found working DDQ-6 (Company Two, EMIS), 2026-10-25. Raised at Steve's request.

**Chain:** independent (no migration, no API shape change; naming only).

## What's wrong

Most questions are named by the client's reference ("8.2"). A question without one gets a name made from its position in the list, and that is worked out differently in a dozen places. So the same question has different names on different screens, in tools and in emails. On DDQ-6:

- **The opening Data Hosting question** ("Do you provide Hosting Services…?") has no reference. Set-up called it **"Question 71"**: it counted before the 4 cover fields were put in front. The DDQ page, the progress list and the assignment all call it **"Question 75"**.
- **The "Date Completed" cover field** came back from the assignment as **"Question 4"**. The Questions card and Review answers call it "Date Completed".
- **Mixed case:** some places say "question 12", others "Question 12".
- **Covers shift the numbers.** Every unreferenced question's number moves by however many cover fields the DDQ has.

## What people see after the fix

- **A cover field** is always named by its label ("Date Completed", "Supplier Name"): on screen, in Actions and emails, in Polaris's tools, in messages such as "Someone else decided … first", and in the completed file's notes.
- **Any other question without a reference** is "Question n". Here n is its place **among the questions only**, so cover fields don't push the numbers along. DDQ-6's hosting question becomes "Question 71" everywhere: on the DDQ page, on the Questions card, in its assignment, in Review answers and for Polaris.
- **A question with a reference** keeps it ("Question 8.2", or "8.2" where a list shows references).
- The same capitalisation everywhere: "Question n" at the start of a line and in names.
- Adding or removing a question renumbers the unreferenced ones the same way in every place, because each place works it out from the same rule.

## Notes (technical)

**Backend:** these places each build the name on their own:
- `core/ddq_assignments.py` ~93 and `api/v1/ddq_assignments.py` ~45;
- `api/v1/ddq_layout.py` ~276;
- `core/ddq_layout.py` ~348 and ~589 (the set-up warnings, before covers are placed: hence "Question 71");
- `core/ddq_library.py` ~62, `core/ddq_packs.py` ~83, `core/ddq_review.py` ~99 and `core/ddq_review_answers.py` ~63.

Replace them with one `question_name(question, number)` in a shared core module:
- a cover → its text;
- a reference → it;
- otherwise "Question {n}", where n is the 1-based index among `kind == question`, in position order.

It needs the DDQ's ordered questions. Compute the numbers once per request with a helper (`numbers_for(db, ddq) -> {question_id: n}`), not with a query per name. Set-up names questions only after the final positions, including covers, are known.

**Frontend:**
- `questions/labels.ts` `questionName` is the shared helper. Make it take the number among questions (from the list), or have the API return `name` on each question (preferred: one rule, server-side, and Polaris's tools get it too).
- Replace the local copies: `AssignmentPanel.tsx` ~44, `AnswerReview.tsx` ~36 and `QuestionsCard.tsx` ~100/~362 (the "Q{n}" column keeps its short form, but with the same n).

**Polaris tools:** `ddq.py`, `ddq_common.py` and `ddq_answering.py` use the shared name. A question asked for by its name ("Question 71") must find it, as must one asked for by its number in the list.

**Tests:**
- a unit test for the rule, with covers, referenced and unreferenced questions;
- an integration test that a set-up warning, an assignment and Review answers name the same unreferenced question identically on a DDQ with covers;
- vitest for `questionName`.
