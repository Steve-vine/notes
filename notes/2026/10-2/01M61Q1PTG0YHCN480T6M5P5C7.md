Sprint 93, Vulnerabilities - Cloud sources. Companion to the AWS read memory task. Found on staging, 2026-10-28, while Steve was testing sprints 90–93.

## What's wrong

Steve fixed the AWS policy at 13:08 and pressed Read now at 13:10. That read died partway through, most likely killed for running out of memory, and recorded nothing. For the next three hours the AWS Status still showed the 13:02 problems ("The user may not read Security Hub…"). Steve reasonably took that to mean the fix hadn't worked.

Nothing on screen said a newer read had started and never finished. The same happened again at 16:31.

When the worker is killed mid-read, nothing records a finish or an error: the read's start time is newer than its finish time, and that's all. After 45 minutes Compass quietly lets a new read start, but the screen never says the last one was lost.

## What people should see

- **While a read runs,** the account shows "Reading — started 16:26". Discovery reads partly do this already; the security read that follows doesn't.
- **When a read has been going far longer than it should** (past the in-flight window, 45 minutes today), the account and the tile say "The last read, started 13:10, didn't finish. Read now to try again." The tile turns Needs attention.
- **Older results stay, but are labelled with their time:** "From the read at 13:02". Problems from an older read then aren't taken as current.
- The same goes for every cloud and directory read that keeps a start and a finish time: AWS, Azure and Google Cloud discovery and security reads, Active Directory, and Entra ID.

## Notes

- The security reads (`read_<cloud>_vulnerabilities`) don't record a start time at all, only a result. Give them one, as discovery has.
- A sweep, every few minutes, can mark a read whose start is past the window and has no finish as not finished, so the state is stored rather than worked out on screen.
