ADR 0057.

Some framework requirements will never apply to a given company, and today they
read as permanent gaps that nobody can close. HIPAA's healthcare clearinghouse
isolation and group health plan documents apply to a fraction of covered
entities. PCI's payment-page script integrity means nothing to a company that
takes no cards. They will sit in the gap list forever, dragging the score down
and training people to ignore it.

ISO has the same hole from the other direction: a Statement of Applicability is
only an SoA if an excluded control carries a justification. ADR 0011 gave that to
Core controls per company. Framework requirements never got it.

## What changes for the reader

On a company's view of a framework, a requirement can be marked **not
applicable**, with a reason that is required, not optional. Out-of-scope
requirements leave the gap list and the coverage denominator, and appear in their
own section so the exclusion is visible rather than hidden.

The SoA export gains the exclusion column it has always needed.

## Implementation

- Applicability is **per company**, like the control assessment — a new
  `company_framework_requirement` row carrying `applicable`, `justification`,
  actor and date. Not a column on the shared requirement: scope is a company's
  decision, and the requirement library is shared reference data (ADR 0017).
- Default is applicable. Absence of a row means in scope — no backfill needed.
- Coverage percentages count applicable requirements only; show the excluded
  count alongside so the denominator is never silently smaller.
- Marking a requirement not applicable is an audit-trail event (ADR 0023).
  Un-marking it is too.
- The justification is free text but **not nullable when `applicable` is false** —
  enforce at the API, not just the UI.

Tests: excluding a requirement changes the denominator and the gap list; an
exclusion without a justification is rejected; two companies can disagree about
the same requirement; the SoA export renders the justification.
