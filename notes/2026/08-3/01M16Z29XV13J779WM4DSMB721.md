Revoking an API token currently stamps `revoked_at` and leaves the row in the list. A revoked token can never be used again and its plaintext was only ever shown once, so the row is pure clutter on a screen whose whole job is "which tokens of mine are live". **Decided: revoke deletes the token.**

## Change

- `POST /api/v1/tokens/{token_id}/revoke` (`api/v1/tokens.py:59-70`) deletes the row rather than setting `revoked_at`. Keep the path and the 204 — the caller's intent hasn't changed, and renaming it to a `DELETE` is a breaking change to `/api/v1` for no user-visible gain (ADR 0004).
- Keep it idempotent: revoking an already-gone token stays a 204, not a 404. The current code already guards with `if token.revoked_at is None`.
- Frontend `admin/TokensSection.tsx` — the row disappears on success; the existing `invalidateQueries(['tokens'])` already handles it.

## Two knock-ons

**The Status column becomes single-valued.** `TokensSection.tsx:50, 60-64` renders Active/Revoked badges. With revoked rows gone every row reads "Active", so the column carries no information and should go. That frees width for `Last used`, which is the column that actually tells you whether a token is still in use.

**`revoked_at` goes vestigial.** Every surviving row will have it `NULL`, so the `is_active` check in `models/api_token.py:31` becomes dead in practice. I'd **keep the column and the check** rather than migrate it away — it costs nothing and it means a row that somehow survives deletion still fails authentication. Worth a one-line comment saying that's deliberate, so the next reader doesn't "tidy" it.

## Flag before building — there is no other record

`api/v1/tokens.py` **does not write to the activity log.** Grep for `ActivityLog` writers: `vendor_requests`, `vendor_purge`, `role_resolution`, `vendor_assessment_start`, `auth_sso`, `data_types`, `users`, `approval_areas` — tokens is not among them. `ActivityPage.tsx:28` has an `api_tokens: 'API token'` label, but nothing ever writes those rows.

So today the token row is the *only* evidence a token ever existed. Delete it and there is no record that anyone ever held API credentials, when they got them, or when they gave them up — in the tool whose job is governing exactly that kind of access. Revocation is also the moment a security question gets asked ("was this key live in March?"), and it would become unanswerable.

**Recommended: log create and revoke to the activity log as part of this task.** The entity label already exists, so it's a small addition, and it makes the deletion lossless — the list stops being cluttered *and* the history gets better than it is now. If that's not wanted, the deletion should still go ahead as asked; this note is here so the trade-off is a choice rather than a surprise.

## Verify
Revoke a token: it vanishes from the list, a second revoke of the same id still returns 204, and a request carrying that token is rejected. Backend tests currently assert `revoked_at` is set — update them to assert the row is gone.
