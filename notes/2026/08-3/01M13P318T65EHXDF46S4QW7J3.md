Defect in COM-447, found testing sprint 45 on staging (`staging-20260828-0133`).

`governed_memberships` is **empty** on a healthy, fully populated mirror. Observed on staging: last sync 2026-08-28 08:45:10, 1,558 users / 3,340 groups / **70,844 memberships** / 2,040 devices — and the Coverage tab reads *0 explained, 0 nobody has explained yet*.

## Why

`_reconcile_provenance` is called two ways:

- `tasks/directory_sync.py:690` — full pass, whole world
- `tasks/directory_sync.py:821` — delta pass, `group_ids=scope` (only the groups that surfaced in the delta)

The mirror had valid deltaLinks and a `last_full_completed_at` from long before this sprint deployed, so **every pass since the deploy has taken the delta branch**. Pre-existing memberships never surface in a delta, so they are never reconciled. On a quiet tenant that is approximately none of them.

The proof needs nothing else: sync healthy + mirror populated + provenance empty can only mean no full pass has run since deploy.

Migration `0128`'s note says "the table lands empty and the first mirror sync after deploy fills it." That is only true when the first pass is a **full** one, and nothing makes it so. The note is wrong and should be corrected along with the code.

## Why it matters more than a wrong number

**The mover goes quiet.** With no records, `plan_mover` finds nothing for anybody: `remove`, `kept_exceptions` and `unattributed` all come back empty. So a mover removes nothing *and lists nothing* — the "this person has fourteen memberships Compass cannot explain, keep or drop?" listing that COM-448 calls the whole value of the mover on day one is silently absent. It looks like it worked.

Everything else provenance-backed reads empty too: the badges on every member list, the Coverage figure, and the cluster proposals (near-match and retirement still fire, which is what made the contradiction in COM-479 visible).

**It self-heals in up to 24 hours**, when `_FULL_RESYNC_INTERVAL` forces the nightly full pass — so this is not permanent breakage. But it is a day of confidently wrong screens on the sprint's keystone, **and it recurs on every fresh deployment of the feature**, which is what makes it a defect rather than a one-off.

## Scope

**Stop scoping the provenance reconcile.** Always reconcile the whole mirror, on full and delta passes alike.

Scoping borrowed the crawl's optimisation without needing it. Unlike the crawl this is a **pure local set difference over two indexed tables** — no Graph calls, no network — so the reason the mirror pass is scoped does not apply. Unscoped is also *more* correct: scoped, the reconcile can only delete stale rows that happen to fall inside the delta's group set.

Sanity-check the cost before committing to it: ~70k pairs into memory every 15 minutes should be sub-second and is dwarfed by the `$batch` edge crawl already in the same pass. If it does prove heavy, the fallback is a one-off unscoped sweep guarded on "has a full reconcile ever run", but prefer the simpler shape — extra state to remember whether a backfill happened is the kind of thing that goes stale.

Correct migration 0128's note in the same change, or leave a comment where it can be found: the next person reading it will otherwise believe the backfill is handled.

## Tests

- A delta pass over a mirror with **unreconciled pre-existing memberships** creates their provenance rows. This is the regression test, and it fails today.
- A delta pass still removes a provenance row whose membership has gone from a group the delta did **not** touch.
- The existing full-pass tests keep passing untouched.
- A mover against somebody with unexplained memberships lists them — the COM-448 behaviour that is silently absent right now.
