COM-330 built `auto-rerun.yml` so that a run which failed for infrastructure reasons is retried once, immediately, without a human noticing. On the evening of 2026-08-28 four runs failed on downloads and **not one of them was absorbed** — every one needed someone to read the log, decide it was infrastructure, and click rerun. That is the exact cost the job exists to remove.

## What got through

Two shapes, both plainly transport failures, neither matched by any signature in the list:

- **`npm error code ETIMEDOUT`** — `npx --yes openapi-typescript` inside the OpenAPI drift check. It failed the **backstop on `main` twice**, once on COM-486's merge and again on COM-477's. Both times the drift check never ran, so a red backstop meant nothing had been checked rather than something being wrong — the worst reading for a gate to have. Verified by hand both times that there was no drift.
- **`Failed to download Helm from location https://get.helm.sh/...`** and **`DownloadKubectlFailed`** — the staging deploy, twice, before COM-466's runner image was live.

COM-466 already added `Exit handler never called` after npm took out `deps-scan` mid-sprint. This is the same audit continued rather than a new idea: the list was written from the shapes seen in one evening in August, and the ones since have simply not been added.

## Why the list keeps missing these

The existing signatures are mostly DNS and HTTP status — `EAI_AGAIN`, `getaddrinfo`, `502`, `i/o timeout`. A download that connects and then stalls produces neither. `ETIMEDOUT` is the plain socket timeout and is arguably the single most common failure on this uplink; the memory note on CI flakes has listed it as a known shape for weeks.

## Scope

Add to `SIGNATURES` in `.github/workflows/auto-rerun.yml`:

- `/ETIMEDOUT/i` — socket timeout, npm and anything else using libcurl or Node
- `/ESOCKETTIMEDOUT/i` — its sibling
- `/ECONNRESET/i` — the existing `connection reset by peer` regex does not match Node's error-code form
- `/Failed to download (Helm|Kubectl)/i` and `/DownloadKubectlFailed/i` — the `azure/setup-*` actions' own wording
- `/network request to .* failed/i` — npm's generic transport line, which covers shapes not yet met

Every one is a transport failure that application logic cannot produce, which is the bar the header sets for adding to this list. The cost of a false positive is one wasted rerun; the cost of the false negatives tonight was four interruptions and a blocked release.

## Also worth deciding

**The drift check downloads a package on every main run.** `npx --yes openapi-typescript@7.13.0` is the same disease COM-466 cured for kubectl and helm — a fetch on the critical path over a marginal link. Now that the runner image is ours, the generator could be baked in beside uv and Node, pinned there the way `OPENAPI_TS_VERSION` pins it today. That removes the failure rather than retrying it, and it is the reason two of tonight's four failures happened. Do it as part of this task if it is small; split it out if the peer-dependency isolation (`openapi-typescript` wants TypeScript ^5, the project is on 6.x — the reason it goes through `npx` at all) makes it awkward.

## Done when

A main or PR run that dies on any of the shapes above is rerun automatically and nobody hears about it, and a run that fails a real check is still left alone. Note that `workflow_run` only fires for the copy on the default branch, so the change does nothing on its own PR — its first real exercise is the next flake after it lands.

Refs: COM-330 (the job), COM-466 (the last signature added, and the baked-tools precedent), ADR 0041.
