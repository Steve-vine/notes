The Controls list and the Assessments queue run ACC.1, ACC.10, ACC.11 … ACC.2, because the refs are sorted as text. Anyone scanning for a control by number has to hunt for it, and working down the assessment queue in order means jumping about the library.

**Expected** — controls read in number order inside each domain: ACC.1, ACC.2, ACC.3 … ACC.19. Domains come in their configured order — the same order as the Dashboard's domain rows — so the list is grouped by domain rather than by alphabetical domain code.

**Assumption, say if it's wrong** — this is an ordering fix, not a new grouped layout. Neither table shows a domain today, so the grouping is only visible through the ref prefix; I'd add the domain as a group heading row above each block on both tables so the grouping reads. If you'd rather keep flat tables with a Domain column, or leave them bare, say so.

**Implementation** (backend — one fix serves both screens; neither page re-sorts client-side)
- `api/v1/controls.py:199` orders by `CoreControl.ref`, a `String(20)`. Join `Domain` and order by `Domain.display_order`, then the ref's number as an integer: `split_part(ref, '.', 2)` cast to int, wrapped in `NULLIF(…, '')` so an unexpected ref shape sorts last instead of erroring. Keep the ref prefix as a tiebreak.
- All 383 refs in `data/controls.csv` are strictly `PREFIX.N` (24 prefixes, N up to 31), so there is no sub-numbering to handle — but don't assume it in the SQL, hence the NULLIF.
- Same ordering in `api/v1/risks.py:241` and `api/v1/mappings.py:259`, which sort controls the same way — pull the ORDER BY into one shared helper rather than writing the expression three times.
- Tests: a domain with more than nine controls must come back 1, 2, … 10, 11; a ref that doesn't parse must not blow up the query. Worth a fixture crossing two domains to pin the domain order too.
