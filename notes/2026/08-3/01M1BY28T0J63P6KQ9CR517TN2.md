Preparing for a CIS audit means working through the controls CIS actually asks about, not all 383. The Assessments queue filters by domain, status, maturity and ownership, but not by framework — so "show me what CIS covers" means holding the crosswalk in your head.

**Expected** — a framework picker beside the existing filters. Choose one and the queue holds only the controls with a mapping to that framework, with the count line reflecting it. It combines with the other filters as they already combine: CIS *and* not yet assessed *and* mine.

**A control counts as covered if it maps to the framework at all**, whatever the strength of the relationship. Filtering out the weaker mappings would quietly claim CIS asks less of us than it does, which is the wrong way for an audit-preparation tool to be wrong. If picking out the strong ones turns out to matter, that is a second filter later, not a hidden rule now.

**Frameworks are versioned** (ADR 0058) and mappings hang off a particular version's requirements, so the picker lists versions as they are named — "CIS Controls v8.1" — current versions first. Selecting one filters on that version's mappings; a control mapped only to v8 does not appear under v8.1, which is correct and is the sort of thing the crosswalk exists to show.

**Assumption, say if it's wrong** — the same picker goes on the Controls list too. Both screens read the same endpoint, so once the filter exists server-side it is one component on the other page, and "which controls does CIS ask about?" is as fair a question in the playbook as in the queue.

**Implementation**
- `api/v1/controls.py` `list_controls` takes a `framework` slug alongside `domain` and `q`: exists-subquery over `control_mappings` → `framework_requirements` → the framework, unknown slug 404s like the domain filter does. Keep it a filter on the existing endpoint rather than a new one — the ordering, visibility and search rules all apply unchanged.
- Frameworks for the picker come from the existing list endpoint; show name + version, current versions first, and exclude any with no mappings at all rather than offering a filter that can only return nothing.
- `pages/AssessmentsQueuePage.tsx`: the framework goes in the query key beside `domain` so the fetch re-runs; the remaining filters stay client-side as they are. `pages/ControlsPage.tsx` gets the same picker.
- Regenerate `schema.d.ts` for the new query parameter.
- Tests: a control mapped to the chosen framework is returned and one mapped only to another is not; a weak mapping still counts; framework and domain filters combine; an unknown slug 404s; a control mapped to two versions appears under each.

**Worth deciding when it's on screen** — with a framework selected, whether the queue should show which of its requirements each control answers. It is the natural next question for someone assessing against CIS, and it is also another column on a busy table. Left out here deliberately.
