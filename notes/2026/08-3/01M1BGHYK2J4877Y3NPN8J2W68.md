Coverage proposals cluster people on every mirrored membership, whatever kind of group it is. Dynamic-membership groups are in there, and so are Microsoft 365, distribution and role-assignable groups — none of which Compass is allowed to manage. Everywhere else this is refused with a sentence: the matrix won't map a dynamic group to a business role, and a joiner, mover or leaver won't write to one, because in Entra the rule decides who is in it. **Accepting a proposal skips that check entirely** and maps the groups straight onto the role.

Two things go wrong. A role gets created holding groups the rest of the app then refuses to touch. And the "missing" list that acceptance produces — the gaps meant to be filled through the ordinary request path — can name groups no request can ever fill; raise one and it is bounced at the gate.

**Approach — keep them in the analysis, refuse them at acceptance.** These proposals are the migration tool for a tenant nobody can explain, and a dynamic group that genuinely marks out a job is real signal about how the place works. Excluding them from the clustering would hide that. So the clusters stay as they are; what changes is that acceptance maps only the groups Compass can manage, and says plainly which ones it left behind and why.

**And make it obvious before anyone accepts.** A proposal offering a role for 20 people across 10 groups looks compelling right up to the moment you notice 9 of them are dynamic — at which point it is a role with one real group in it, and probably not worth writing. The screen must not let that discovery happen after the click.
- Each group in a proposal is labelled with its kind, using the wording the refusals already use: *dynamic-membership security*, *Microsoft 365*, *distribution*, *role-assignable*.
- The proposal leads with the count that matters — "10 groups, 1 manageable" — not a bare "10 groups". Whatever the headline number is, it should be the honest one.
- A proposal where nothing is manageable is still shown, because it still says something true about the tenant, but it cannot be accepted and says why. It can be dismissed like any other.
- Ordering and any "strength" signal should reflect the manageable groups, so the most appealing-looking proposals are not the ones with the least in them.

**Implementation**
- `core/coverage_proposals.py` `accept()` (~line 353) appends `BusinessRoleGroup` rows with no validation. The mapping endpoint `api/v1/business_roles.py` (~line 110) has the guard already — non-governable and role-assignable both refused, with the sentences to reuse. Pull that check into one helper and call it from both, rather than a second copy that can drift.
- Acceptance maps the manageable subset, records which groups were skipped and why, and returns that so the screen can show it. Skipped groups must not appear in the gap list — a gap nobody can fill is worse than no gap.
- `CoverageProposalOut` carries `group_ids`/`group_names` today; add the per-group kind and the manageable count so the UI doesn't have to re-derive it from a second call.
- `access/CoveragePage.tsx`: the labels, the honest headline count, and the disabled-accept case with its reason.
- Tests: a cluster containing a dynamic group still proposes; accepting maps only the governable groups; the skipped ones are reported and are absent from the gaps; an all-dynamic proposal cannot be accepted; a role-assignable group is refused the same way. Cover Microsoft 365 and distribution too — same hole, less obvious.
