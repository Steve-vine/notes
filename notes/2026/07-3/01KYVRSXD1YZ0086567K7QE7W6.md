Follow-up investigation, deferred at sprint planning (2026-07-30) and again at both releases: DNS records are evidence-only today (ADR 0062 §3) — nothing joins what a zone's records point at onto the estate. The mapping capability would harvest `routes-to` edges from CNAME/A record targets that match discovered entities (Cloudflare LBs, AWS ELBs, Azure App Gateways/App Services, hosts), giving the graph "which entity does this hostname front" — the missing piece between the estate's edge layer (Relationship Mapping, s5khymf) and the Cloudflare integration.

To work out (outcome = a proposal, not necessarily a build):
- **Matching without guessing** (ADR 0028): which target strings resolve honestly — CNAMEs onto `default_hostname`/LB DNS names are exact-string joins; bare A-record IPs onto hosts are weaker and may not clear the bar.
- **Where it runs**: inside the Cloudflare discovery sweep (DNS records are deliberately not fetched there today — this would reopen that decision with a bounded, targeted read) vs the slow Obs Loop vs an AI-proposed-edge pass (alias-proposal precedent, ADR 0028 §3).
- **Provenance and lifecycle**: harvested edges must retract when the record changes — set-replacement semantics like tag reconcile, not sticky assertions.
- **Volume bounds**: zones can carry thousands of records; only records whose targets match candidate entity attributes matter.

Related: ADR 0062 §3 (the deferral), Relationship Mapping sprint (the edge-authoring/harvest architecture this should align with).
