    Investigated — PR #468 (feature/ise-398-dns-routes-to-investigation). Outcome is a proposal, as asked: `docs/briefs/dns-routes-to-mapping.md`. No code, no schema, no API change.

    Two findings from the code move the question on from where ADR 0062 §3 left it:

    1. **The Cloudflare connector already reads DNS.** `_zone_routing_edges` lists each zone's CNAMEs during the discovery sweep and already emits `routes-to` edges from them — zone → tunnel via `*.cfargotunnel.com`, zone → Worker via routes and custom domains — reading records for the one id they carry and discarding them. So three of the four questions in the ticket are already answered by built precedent: **where it runs** (the Cloudflare sweep, not the Obs Loop, not an AI pass), **provenance/lifecycle** (harvested + `last_confirmed_at`, set-replacement comes free), and **volume bounds** (one paginated CNAME list per zone, already being made — extending the matching costs zero extra API calls).

    2. **The estate already resolves an edge target through the alias table**, not only within a batch. So the genuinely-unbuilt part — matching a CNAME onto an entity another integration owns — needs no new matcher: the owner publishes its provider-assigned hostname as a `dns:<hostname>` cross-key, and the zone points a `routes-to` edge at that key. Exact string equality between two values the providers stated, so tier 1 rather than a guess — ADR 0028 holds.

    **The matching cut** (your first question — which targets resolve honestly):
    - IN: Azure App Service/Functions `default_hostname`, AWS ELBv2 `dns_name`, AKS `fqdn`. All three are already stored as attributes; they only need emitting as cross-keys too.
    - OUT: A records onto host IPs. ISE stores only EC2 `private_ip`, which is not what a public A record points at, is reused across VPCs/accounts, and matching it is exactly the guess ADR 0028 forbids. This is most of the value anyway — the public estate is fronted by CNAMEs far more often than bare A records.
    - GAP: Azure Application Gateway stores no FQDN or public IP today. Small connector change, prerequisite not part of it, optional for a v1.

    **One decision left for you.** The `dns:` cross-key makes a public hostname part of an entity's IDENTITY rather than merely an attribute. That is what makes the join free. The safe failure mode is covered — ISE-510's ambiguity rule ignores a contested key rather than collapsing entities — but if that reads as stretching identity too far, the alternative is a Cloudflare-side lookup against `Entity.attributes`: more code, and a second way of doing what aliases already do.

    If the cross-key approach is accepted this is **one ticket, not a sprint** (graph surface is free — the canvas already draws `routes-to`). If rejected, it should be re-planned as materially larger.

Follow-up investigation, deferred at sprint planning (2026-07-30) and again at both releases: DNS records are evidence-only today (ADR 0062 §3) — nothing joins what a zone's records point at onto the estate. The mapping capability would harvest `routes-to` edges from CNAME/A record targets that match discovered entities (Cloudflare LBs, AWS ELBs, Azure App Gateways/App Services, hosts), giving the graph "which entity does this hostname front" — the missing piece between the estate's edge layer (Relationship Mapping, s5khymf) and the Cloudflare integration.

To work out (outcome = a proposal, not necessarily a build):
- **Matching without guessing** (ADR 0028): which target strings resolve honestly — CNAMEs onto `default_hostname`/LB DNS names are exact-string joins; bare A-record IPs onto hosts are weaker and may not clear the bar.
- **Where it runs**: inside the Cloudflare discovery sweep (DNS records are deliberately not fetched there today — this would reopen that decision with a bounded, targeted read) vs the slow Obs Loop vs an AI-proposed-edge pass (alias-proposal precedent, ADR 0028 §3).
- **Provenance and lifecycle**: harvested edges must retract when the record changes — set-replacement semantics like tag reconcile, not sticky assertions.
- **Volume bounds**: zones can carry thousands of records; only records whose targets match candidate entity attributes matter.

Related: ADR 0062 §3 (the deferral), Relationship Mapping sprint (the edge-authoring/harvest architecture this should align with).
