The tenant connection for the Access domain, as a **third, dedicated app registration** — not a widening of `m365_settings`. The COM-232 argument ("consent and revocation must be independent; the managed-content consent screen must never silently ask for the power to send mail") applies with more force to directory write: `User.ReadWrite.All` + `Group.ReadWrite.All` get their own consent, their own credential, their own revocation.

* **Settings**: singleton row (partial-unique-index idiom), `tenant_id` / `client_id` / `client_secret_encrypted` via `core/secretbox.py`; write-only secret through the API (read returns set/unset), fields named `*_secret` so `DEFAULT_REDACT_KEYS` redaction is automatic. Env fallback like `M365_*` in `core/config.py` for 12-factor deployments.
* **Graph client**: extend `core/graph.py` — no second Graph dialect (the `mail_transports/m365.py` precedent). It needs what the content flows never did: a **paged-GET helper** (`@odata.nextLink`, `$select`, `ConsistencyLevel: eventual`) — `/users` and group-member listing page at 100 by default. Token acquisition/caching, `GraphError` taxonomy and the `httpx.MockTransport` testing convention all reuse as-is.
* **Admin ▸ Integrations panel**: an "Entra ID access" card beside M365 and Email (`admin/IntegrationsSection.tsx` is the model): credentials form, **Test connection** reporting the Graph error inline.
* **Beat health check**: `tasks/` module (added to the Celery `include=` list) on the `mail_health.py` pattern — and per ADR 0044, verify the **grants**, not just the token: confirm the required permissions are actually consented.
* **Entra-side setup** documented as a script/README under `scripts/` (the `scripts/m365/` precedent): app registration, exact application permissions, admin consent.

Refs: ADR 0045, 0044 §1, 0034; `models/m365_settings.py`, `models/email_transport.py`, `core/secretbox.py`, `core/graph.py`, `tasks/mail_health.py`.
