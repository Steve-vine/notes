    **The two fields are not two spellings of one fact.** `resolved_at` is a SOURCE fact owned by ingest (`sync`, `webhook_signals`, `status_pages`, `servers` are the only writers). `status = "resolved"` is a HUMAN fact cascaded from the incident. The 45 `resolved` rows that DO carry a timestamp are simply the other order (went away first, resolved after), and `recovered` is 0-for-1913 because ingest owns both halves of that path. `resolve_incident_signals` (`promotion.py:670`) is the whole of it:

```python
finding.status = "resolved"     # and nothing sets finding.resolved_at
```

So a human resolving an incident leaves its signal in a contradictory state: terminal by `status`, unresolved by `resolved_at`. Every consumer that filters on the timestamp then treats it as live.

**Measured on staging 2026-08-15: 32 of 77 `resolved` findings have a NULL `resolved_at`, and all 32 pass the "present signal" filter.**

The split is diagnostic: `recovered` findings are **0 for 1913** — the source-driven recovery path sets both fields correctly. Only the human-resolution path is broken, which is why it went unnoticed. It bites hardest on ISE-derived observations, where a human resolving the incident is the only thing that ever touches the signal; a DataDog monitor gets its timestamp from the sync regardless.

**Two consumers, and the second is the serious one.**

- `signal_state_for_entities` (`entities.py:1568`) filters `Finding.resolved_at.is_(None)` — so the estate shows an active alert on an entity whose signal was resolved days ago. Reported on `mpwxdc01`.
- `present_signals_for_members` (`dashboards.py`) uses the **same** filter to decide what a tile evaluates. So a human-resolved signal can still hold a dashboard tile amber or red, and no amount of resolving incidents will clear it. That is the wallboard reporting a problem that no longer exists, which is precisely the failure the latch model and the webhook exclusion were designed to prevent.

**Scope**
- Set `resolved_at` alongside `status` in `resolve_incident_signals`, so the human path matches the recovery path.
- **Backfill the 32.** They will otherwise stay live for ever — nothing re-resolves an already-resolved signal, so the code fix alone does not repair existing rows. Use the resolving incident's `resolved_at` where one exists rather than `now()`, so the record stays honest about when it actually happened.
- Decide whether `status` or `resolved_at` is authoritative and make the consumers agree. Two fields encoding one fact will drift again; the cheapest durable fix may be for the filters to test both, or for a check constraint to make the contradictory state unrepresentable — `audit_event`'s append-only trigger is the precedent for enforcing an invariant in the database rather than trusting every writer.
- Check reactivation: `promotion.py:253` sets `target.resolved_at = None` on the incident when a signal recurs. Confirm the finding's own timestamp is cleared on that path too, or a reactivated incident inherits the opposite inconsistency.
