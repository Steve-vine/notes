The cloud renders at most `CLOUD_LIMIT = 200` tags. On staging the pool holds **2,279** — so 91% of it never reaches the browser, and the screen does not say so in any way an operator would notice.

What it says today (`app/frontend/src/pages/TagCloudPage.tsx:199-208`):

- `200 of 200 tags` — reads as "that's all of them"
- a small yellow badge: `Showing the 200 hottest tags`

The badge is honest about the cap but silent about the scale of what was dropped, and the count line beside it actively contradicts it. The existing code comment says "a silently truncated cloud reads as the whole estate when it is not" — the intent is right, the execution understates it by an order of magnitude.

Return the pool total from the cloud endpoint (count before `LIMIT`, under the same window/system/search filters) and say `200 of 2,279 tags`. The badge can then explain the *rule* rather than the number — that the cloud keeps the hottest, and the rest are reachable via search and sort.

This is the smallest of the four cloud fixes and the one that makes the other three legible: once an operator can see that most of the pool is hidden, "sort by entity count" and "search" read as the way to reach it rather than as decoration.

**Done when:** the footer states the true pool size, and the truncation notice explains how to reach what is not shown.
