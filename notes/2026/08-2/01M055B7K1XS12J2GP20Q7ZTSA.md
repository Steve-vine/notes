    Built and pushed as PR #693 — move to Review. (ISE-743 / #692 merged first, so this targets main directly.)

    The gotcha the task named is done properly, and it needed one more step than the task described:

    `smtplib` takes **one** `timeout` at construction covering the connect AND every command after it — two different questions collapsed into one number. So the socket deadline is re-set once connected: 5s connect, 60s command. **And again after STARTTLS** — the upgraded connection is a *new socket object* that does not inherit the first deadline, so missing that puts every post-handshake command back on the 5s connect bound, which is a slow relay reported as a broken one. That second one is not obvious from reading the stdlib docs and is the half a reviewer would most likely miss.

    Both halves are asserted directly, on both sockets, because the bound is invisible in behaviour until the day a relay stops answering. Verified by flipping each `settimeout` off in turn — deleting either fails two tests.

    Settings are `smtp_connect_timeout_seconds` / `smtp_command_timeout_seconds`, deliberately separate from the HTTP ones: a relay is not an API, and an operator with a slow smarthost should be able to tune it without touching every HTTP connector in the estate. The numbers mirror ADR 0092's reasoning, not its constants.

    Judgement calls:

    1. **`security=none` is `degraded`, not `error`.** Reachable and usable, and worth saying once that the login and every message cross the network in clear — but a private-network smarthost is a legitimate deployment, and refusing it would be ISE deciding an operator's network topology.
    2. **An unknown `security` value raises rather than normalising to `starttls`.** I wrote the silent fall-back first and then took it out: a silent normalisation is how a relay ends up negotiating something the operator did not choose while the screen still shows the word they typed.
    3. **Everything lives in the credential secret, not split with `System.config`.** Host/port/security are the shape of ONE connection; splitting the non-secret half would mean two forms for one relay, with the rotate flow able to move only half of it.

    **One real gap found and closed while here.** The Email tab was not naming `connector_type` on its credential writes, and `credentials_api` skips connector validation entirely without it (ISE-199). So a truncated SendGrid key or a mistyped SMTP security mode was being stored unchecked and discovered by the first message that failed to arrive — the exact failure class this sprint keeps closing. Now named on both the add and the rotate path, and the connector's verdict is surfaced verbatim rather than a generic "storing the key failed".

    The screen needed no new UI: the five-field form draws itself from `credential_spec`, which is asserted rather than assumed.

The second transport, and the one with the widest reach: a generic SMTP relay covers an on-prem Exchange, a smarthost, Mailgun, SES-over-SMTP — anything that speaks the protocol.

Stacks on [ISE-743].

## Scope

`connectors/smtp.py` over stdlib `smtplib`. Credential/config fields: host, port, security (`none` / STARTTLS / implicit TLS), username, password (secret). `health_check` connects, negotiates the chosen security, authenticates and quits — so a wrong port or a refused login is visible on the tile rather than at first send.

## The gotcha this task exists to get right

**ADR 0092 bounds outbound HTTP in one place. SMTP is not HTTP.** `smtplib` goes nowhere near `http_bounds`, and its default timeout is the global socket default — i.e. *wait forever*, which is precisely the behaviour that turned the 2026-08-06 DNS outage into a ~10,000-task broker backlog (ADR 0091/0092).

So this connector sets its **own connect and command deadlines explicitly, with a comment saying why** — an unbounded send from a worker is the same failure in a new place, and the next reader will otherwise assume the platform already covered it.

Mirror ADR 0092's reasoning for the numbers: short connect (a TCP connection not made in ~5s will not be), generous command deadline, no library-level retry (the delivery sweep is already the retry).
