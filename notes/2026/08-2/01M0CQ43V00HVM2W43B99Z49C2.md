The COM-239 lifecycle opens with `draft → pending_approval`, but draft earns nothing: the only actions on a draft are submit or cancel, so it's an extra click on every request. Remove the stop — **creating a standard request lands it in `pending_approval` directly**.

* **Backend**: collapse create-then-submit into one — the create endpoint validates fully (a draft could be half-formed; a pending-approval request can't, so creation now enforces the complete raise-form contract) and writes the request as `pending_approval`. The transitions map drops `draft` as an entry state for new requests; approval notifications fire on creation.
* **Existing drafts**: don't strand them — keep the enum value and the legacy `draft → pending_approval | cancelled` transitions so anything sitting in draft at deploy can still be submitted or cancelled; new requests simply never enter the state. (Enum stays, entry path goes — no data migration guessing intent.)
* **Expedited mode** is untouched — it already goes submitted → executing (COM-239); this brings the standard path to the same "the form is the request" shape.
* **Frontend**: raise forms get one primary action — **"Submit for approval"** — no save-as-draft affordance; cancel just closes the form. Request history/filters drop the draft status from pickers (kept only for any legacy rows that still carry it).
* If a genuine save-for-later need appears down the line (long batch entry interrupted), solve it as client-side form persistence, not by resurrecting a lifecycle state — note this in the PR so the reasoning survives.

Refs: COM-239 (lifecycle + transitions map), COM-240 (raise forms), ADR 0045 (request model).
