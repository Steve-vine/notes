    Done — PR #329, squash-merged to main 2026-08-21. The measurement answers the question in the negative, so the change is a record rather than a rewrite.

    The task asked to measure per-module durations first. Over all 609 integration tests with --durations=0:

      measured test-seconds        1115s
      / 6 workers = ideal wall      186s
      actual wall                   197s   -> 94% packing efficiency
      heaviest single module         60s   -> 32% of a worker's share

    test_directory_sync, the module the task named as a straggler, is 21s.

    For loadscope to strand a worker, one indivisible unit would have to approach a whole worker's share; the largest is under a third of it. Switching to xdist_group/loadgroup or splitting modules could win AT MOST ~11s of 197s, in exchange for markers on every heavy module and a scheduling mode that has to be kept in step with them. Not worth it.

    Where the time actually was, from the same profiling run: 58% of all test time is fixture setup, and 263s of that is rebuilding the FastAPI app once per test. That is COM-333, which took the suite from 197s to 90s — an order of magnitude more than rebalancing could have returned.

    Also corrects a stale rationale recorded next to the flag: loadscope was originally justified by module-scoped containers, and DEV-855 replaced those with session-scoped ones per worker, so nothing breaks if a module is split across workers. loadscope is now a BALANCE choice, not a correctness one — which is exactly what this task needed to know before proposing to change it.

`--dist loadscope` schedules whole modules per worker, and the modules are now lopsided (test_directory_sync has 27 tests; recert/access suites similar) — one worker straggles while the rest idle. Split the heaviest modules or mark logical groups with `xdist_group` and switch to `--dist loadgroup`, so the integration suite's tail shrinks without new hardware. Measure per-module durations first (`--durations`).
