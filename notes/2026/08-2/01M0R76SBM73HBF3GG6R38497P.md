All four reconcilers in `tasks/directory_sync.py` — `_reconcile_memberships`, `_reconcile_nested_members`, `_reconcile_owners`, `_reconcile_device_members` — build their `existing` set like this:

```python
existing = {(m.group_id, m.user_id)
            for m in db.scalars(select(DirectoryGroupMember))   # the WHOLE table
            if scope is None or m.group_id in scope}            # filtered in Python
```

The `scope` argument exists precisely so a **delta** pass only reconciles the groups that changed — but the filter is applied *after* the whole table is in memory. Every 15-minute pass, typically touching a handful of groups, loads all of it.

Measured on the tenant (2026-08-23): **74,669 rows** — 43,618 memberships, 27,296 device memberships, 1,806 nested, 1,949 owners. COM-386 grew that by 63% (memberships were 43,618 before devices) with nobody noticing, because nothing measures it.

- [ ] `.where(<col>.in_(scope))` in SQL when `scope` is not None, in all four. The full pass keeps `scope=None` and still reads everything — a scan-the-world crawl legitimately needs the whole set.
- [ ] Consider chunking the full pass's read too, or at least sizing it deliberately: 74k rows is fine today, and the growth curve is the concern rather than the current number.
- [ ] A test that a delta pass's reconciliation does not read rows outside its scope — otherwise the next person "simplifies" the `.where` away.

**Why this is worth doing now**: this is the third instance today of *accumulate everything, filter later*. The other two were the COM-395 audit sweep (OOM-killed the worker, 23k records) and the ad-hoc reconciliation script written to investigate it (OOM-killed itself, 70k rows). The worker runs at 287Mi against a 512Mi limit; headroom is the thing that failed twice. This is the last place the pattern lives, and removing it is a one-line change per function.

Refs: COM-395 (the same anti-pattern, in production), COM-386 (what grew the row count), COM-316 (why delta passes have a scope at all).
