    Done — PR #331, squash-merged to main 2026-08-21. Evaluated and DECLINED; recorded as an ADR 0041 amendment.

    Evaluated against a sprint that ran an eleven-task stack by hand, so the cost the task describes was paid rather than imagined. Three reasons, the first decisive.

    1. IT IS INCOMPATIBLE WITH STACKED PRs. A merge queue only accepts PRs targeting the protected branch. ADR 0041's stacking model has the child target its PARENT branch, precisely so the child's diff is its own work rather than its work plus the parent's. Those cannot both be true: to use the queue, every PR targets main, and a child opened before its parent merged shows the parent's commits as part of its own change. That is the state ADR 0036 was in and ADR 0041 deliberately reversed. The queue would automate the rebase mechanics at the price of the thing the mechanics exist to support.

    2. IT REINSTATES THE DUPLICATE FULL-SUITE RUN. The queue's value is testing the speculative merge of a batch, which needs the full suite on merge_group — a second full run per PR, the exact duplication ADR 0041 removed after measuring that two of three runs judged an identical tree. The arithmetic moved further against it this sprint: COM-326 and COM-327 took a PR run from ~22 minutes to ~7, so a queue would add about another 7 minutes per task to save a rebase command Claude Code issues without being asked.

    3. THE COLLISION IT PREVENTS IS RARE HERE and already has a cheaper control. It needs two sessions merging within the same few minutes; required_linear_history already makes a racing merge fail loudly rather than interleave silently, and the trunk backstop catches the two ways independently-green PRs actually break each other.

    What would change the answer, recorded in the ADR so it is not re-derived: more than one person merging routinely; a trunk that releases directly; or stacking becoming rare.

    Honest caveat on reason 3: this sprint DID hit a merge accident — #323 squash-merged with the wrong head and swallowed eight tasks. But the cause was `gh pr create` taking its head from the current checkout when run from the wrong branch, not two sessions racing. A merge queue would not have prevented it. The control that would is verifying the PR's head ref and SHA against the local branch before merging, which is now the practice.

Stacked trains are currently driven by hand: merge parent → rebase child onto main → retarget → wait for CI → repeat, and two sessions doing it concurrently collide on main. Evaluate GitHub's merge queue: PRs enter the queue when green, GitHub builds the speculative merge, and the train advances itself. Touches the ADR 0041 trigger model (merge_group event needs the full suite) and branch protection — write up as an ADR amendment if adopted.
