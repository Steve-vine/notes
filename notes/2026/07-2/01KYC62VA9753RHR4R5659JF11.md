Webhook events become a cheap detection path for systems with no supported integration: a sender that POSTs `level: alert` is a source with its own detection layer, so ISE forwards its verdict as an Alert signal — the Canon deferral principle, DataDog-monitor behaviour without DataDog.

- **Level → ladder mapping**: per-source mapping of webhook levels onto the canonical severity ladder (default e.g. `alert→high, warn→medium, info→info`), like any connector's alert mapping. The severity-override layer and global auto-incident threshold apply unchanged — no new promotion machinery.
- **Signal creation**: an alert-level event creates/updates a `Finding(signal_type=alert)`. Identity/dedup on `source + alert_key` (defaulting to event type) so a re-fire attaches (Recurring) instead of duplicating; incident correlation rides the existing open rule.
- **Entity resolution**: the event's `entity` hint resolves against estate names/aliases; matched → signal carries `entity_id` and joins the graph, unmatched → signal without entity (never invent entities).
- **Recovery** (the push-source problem — ISE cannot poll the sender): an event with `status: recovered` and the same `alert_key` marks the signal Recovered; additionally a per-source **TTL fallback** (nullable column from ISE-274, editable in the ISE-275 Settings UI) auto-recovers alerts not re-fired within the window, via a Beat sweep.
- **UI**: these signals surface on the existing Alerts screen and incident timeline like any other alert, with the webhook source named as origin; the event modal (ISE-276) links to the raised signal. No new screen.

Acceptance: POST an alert-level webhook → Alert signal appears on the Alerts screen and (above threshold) opens an Incident; re-fire attaches; a recovered-status webhook or TTL expiry moves it to Recovered.
