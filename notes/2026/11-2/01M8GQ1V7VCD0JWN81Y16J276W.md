**Brief** (an ADR amending ADR 0185, and ADR 0142/0154 for Collection). Raised by Steve on 28 Nov 2026 while testing the Scripting sprint. Write this first; the tasks of this stage build on it.

## Steve's direction
- Collection and Action integrations both get **two families**: **Web/API** and **Server**.
- Scripts support **SQL, PowerShell and Python**.
- A new workflow action, **Raise Alert**: it creates an Action, a notification and a log entry, from free text plus values picked from the workflow.

## What the ADR settles
1. **The two families, on both tabs.** "Add an integration" asks Web/API or Server first.
   - **Web/API** is what a Collection integration is today: an address, a sign-in, paging and a test read.
   - **Server** is anything Compass connects to that isn't a web service, defined by **how Compass reaches it, never by product** (the ADR 0147 §9 rule):
     - **SQL Server database** (today's action kind);
     - later **Windows server** (PowerShell remoting, e.g. managing IIS);
     - later **SSH** (Linux);
     - later other databases.
   - Proposed: a generic Server with these sub-kinds, not "Database" alone, so the Windows server case has a home. *Steve to confirm.*
2. **Read only and Can change things stay apart (ADR 0154).**
   - A Collection integration only ever reads. For a Server one, Test connection proves its login can't write; for a SQL Server database it asks the server what the login may do.
   - An Action integration is "Can change things".
   - Never one login for both; the two can point at the same server.
3. **Collection from a server.** A check on a SQL Server database is a SELECT: each row is a captured item, judged by workflows like any other. Feeds can read the same way.
4. **Where PowerShell and Python run.** In a separate, sealed-off container per run, holding only that run's inputs and its one integration's credential (ADR 0185 §9 makes this a condition). Two shapes to choose between, or both:
   - (a) the script runs in the container and calls a Web/API integration, or connects to a database, through the credential it's handed;
   - (b) the script runs **on** a Windows server through PowerShell remoting.

   *Steve to choose.*
5. **What a script can reach.** Only its integration. Never Compass's database or network (as the SQL runner today).
6. **Raise Alert.**
   - What it creates:
     - an Action (for whom: the workflow's owner, a named person, or a role?);
     - a notification;
     - a log entry.
   - Its text: free text with values from the trigger and earlier steps inserted.
   - Whether it has a severity.
   - **Open: where the log entry goes.** Compass has no event log today: the Activity log records changes people make to records, and each workflow and script keeps its own run history. Options:
     - (a) record alerts in the Activity log;
     - (b) add an **Event log** (Admin) for system events: alerts raised, scripts failed, integrations broken.

     *Steve to choose.*
7. **Languages and inputs.** Inputs arrive as variables, never pasted into the text, whatever the language. Outputs are read back by name (PowerShell: a returned object's properties; Python: a returned dict).

**Done when:** the ADR is accepted, with Steve's choices on 1, 4 and 6 recorded, and the tasks of this stage updated to match.
