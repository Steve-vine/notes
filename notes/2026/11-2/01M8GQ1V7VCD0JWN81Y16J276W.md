**Brief** (an ADR amending ADR 0185, and ADR 0142/0154 for Collection). Raised by Steve on 28 Nov 2026 while testing the Scripting sprint. Write this first; the tasks of Scripting - Phase 2 build on it.

## Steve's decisions (28 Nov 2026)
- **Integrations come in two families, for Collection and Action alike: Web/API and Server.**
  - **Server is generic**, its kinds defined by how Compass reaches the server, never by product (the ADR 0147 §9 rule):
    - **SQL Server database** (today's);
    - later **Windows server** (PowerShell remoting, e.g. managing IIS);
    - later **SSH**;
    - later other databases.
- **Scripts in SQL, PowerShell and Python.**
- **PowerShell and Python run in Compass, as generators.** They're for working out what to send, not for reaching other systems themselves.
  - Steve's scenario: a new starter "John Smith", login "john.smith". Another database lists a team's staff as "Smith, J. (john.smith)". A Python script builds that from the display name and login, then builds the SQL command that inserts it. The generated command is what's executed.
- **Generated SQL is held to one rule, in two halves, plus one allowance for published lists** (decided 28 Nov). See §3.
- **Scripts can read a document's named lists** (lookup tables in Content), COM-2236.
- **A new Event log**: date and time, event type (**Info, Warning, Alert**), entity, detail. Kept in a standard JSON format, so it can later be sent to a third-party service such as Datadog.
  - Events this stage: **scripts and workflows**, and the new action.
- **A Log Event workflow action** (in place of the "Raise Alert" first suggested): writes an event to the Event log, with **the person choosing its type** (Info, Warning or Alert).
  - **The type is a label only: an Alert doesn't automatically alert anyone.** It raises no Action and sends no notification.
- **Polaris helps with scripting: it reads, drafts and previews; it never publishes, runs or retries** (COM-2237, the decision ADR 0185 left for later). See §8.

## What the ADR sets out
1. **The two families** on both Add screens.
   - Web/API is today's Collection shape (address, sign-in, paging, test read).
   - Server asks how Compass reaches it.
   - Existing integrations become Web/API (Collection) and Server ▸ SQL Server database (Action).
2. **Read only and Can change things stay apart (ADR 0154).**
   - A Collection integration only reads; a Server one proves at Test connection that its login can't write.
   - An Action integration can change things.
   - Never one login for both.
3. **Generators** (PowerShell, Python):
   - **They run sealed off** in a container per run, with **no network and no credentials**: only that run's input values go in (including the rows of any List input, COM-2236).
   - **What comes out** is either:
     - (a) **values**, handed to later steps (e.g. a SQL script's inputs); or
     - (b) **a request for Compass to send**:
       - a SQL command with its parameters, to a Server integration; or
       - an API call (method, path, headers, body), to a Web/API integration.
   - **Compass sends a request (b)** with the integration's credential, which the script never sees. The answer is read back as outputs. The run records exactly what was sent (sensitive values hidden).
   - **Why:** this keeps credentials out of anything a person writes, and keeps every change Compass makes going through one place that records it.

   **The rule for a generated SQL command (Steve, 28 Nov 2026).** Anything typed into the published script, any number, or anything from a published list the script declared may appear in the command's text; anything else must arrive as a parameter. Compass checks before sending, and a command that breaks the rule is refused; nothing is sent, and the run fails saying why.
   - **Half 1, quoted values:** every quoted value in the command must appear word for word in the published script.
     - Passes: `INSERT INTO dbo.TeamStaff (Name, Team, Status) VALUES (@Name, 'Service Desk', 'Active')` with `@Name = 'Smith, J. (john.smith)'`. 'Service Desk' and 'Active' are written in the script; the name travels as a parameter.
     - Passes: one INSERT per team from a list written in the script (`teams = ["Service Desk", "Networks"]`). The command's shape varies, and every value is in the script.
     - Fails: `VALUES ('Smith, J. (john.smith)')`. The text was built at run time and isn't in the script. "The command has a value pasted into its text that isn't in the script; pass it as a parameter."
     - Fails (harmless-looking, on the safe side): `'Service Desk - Tier 1'` built by joining "Service Desk" and " - Tier 1". The joined text isn't in the script. Pass it as a parameter, or write the whole value in the script.
   - **Half 2, outside quotes:** every word in the command outside quotes (keywords, table and column names) must also appear in the script. Numbers are allowed anywhere: digits alone can't change what a command does.
     - Passes: `WHERE Id = 4512`, a number worked out at run time.
     - Fails: `DELETE FROM dbo.TeamStaff WHERE Id = {staff_id}` where staff_id came from an input typed as `7; DROP TABLE dbo.TeamStaff`. "DROP" and "TABLE" aren't in the script.
   - **The allowance for published lists** (Steve, 28 Nov 2026): a value from a **List input the script declared** (a named list in a published document, COM-2236) counts as the script's own text, under both halves. A document's list is published, versioned and reviewed like the script, so a looked-up table or column name can appear in the command (it can't be a parameter).
     - Passes: `INSERT INTO dbo.ServiceDeskStaff (Name) VALUES (@Name)`, where "dbo.ServiceDeskStaff" came from the Department mapping list's Team table column.
     - Values typed by people, or worked out at run time, still go as parameters, even when they were built from a list's values.
     - The run records the document, list and version the allowance came from.
   - The check reads SQL as SQL Server does: comments, bracketed names and N'…' text count as what they are. The ADR fixes the details (e.g. case-insensitive keywords).
   - The same idea applies to a generated API call: its path and body are checked the same way (values worked out at run time go in the body or query as values, never into the path's fixed parts). *Settle in the ADR.*
4. **SQL scripts** stay as they are: run on a Server ▸ SQL Server database. An input can also be filled by a lookup in a document's list (COM-2236).
5. **The Event log.**
   - **Each event has:**
     - a time;
     - a type (Info, Warning, Alert);
     - an entity (what it's about: a script, a script run, a workflow, a workflow run, a request, a person);
     - a detail (in words);
     - who or what caused it;
     - its company, where it has one.
   - **Format:** the OpenTelemetry log data model, rendered as JSON (timestamp, severity text and number, body, attributes such as entity type, id and name, and resource `service.name=compass`). Datadog, Splunk, Elastic and others take it as it is, so forwarding later is configuration, not a new format.
   - **Kept** append-only, like the Activity log.
   - **Read** under Admin ▸ Event log, filterable by type, entity and time, and exportable as JSON lines.
   - **The Activity log is unchanged:** it stays the record of changes people make. The Event log records what happens.
6. **Which events this stage:**
   - **scripts:** run succeeded (Info), failed or timed out (Alert), retried or dealt with (Info), published or retired (Info);
   - **workflows:** run met or not met (Info), failed (Alert), enabled or disabled (Info), a held person carried on without (Warning);
   - **Log Event's own events.**
7. **Log Event.**
   - Free text with values picked from the workflow inserted.
   - The person picks the type.
   - Writes one Event log entry per run.
   - Nothing else: no Action and no notification, whatever the type.
8. **Polaris and scripting** (COM-2237).
   - **Reads:** scripts, versions and runs (as today); action integrations (kind, what they connect to, owner, last test, scripts using them; never a password or key); the Event log.
   - **Drafts, for a person to save:** a script (SQL now; PowerShell and Python as they land), and a workflow that runs scripts, with its inputs mapped.
   - **Previews and tests** without sending anything: Preview, Try it for generators, and testing an access workflow against a past person.
   - **Never:** publishing, Run now, Retry, Mark as dealt with, Carry on without it, enabling a workflow, or touching an action integration's credentials. These change other systems, so they stay with a person on screen. Polaris says who can.
   - Its instructions explain all this, so it offers scripting where it helps.

**Done when:** the ADR is accepted with these decisions, and the tasks of the sprint match it.
