Found comparing Nessus as configuration (COM-1714) with the coded reader on staging, 2026-11-11. The configured Findings feed brings in 14,291 findings, but **without CVE numbers**: Nessus only gives a host's findings as plugin ID, name and severity. The CVEs, CVSS score, description and solution are in each plugin's details, one read further (`/plugins/plugin/{plugin_id}`). The coded reader gets them from the .nessus export.

Without CVEs, Nessus findings can't join the same vulnerability that another source (Aikido, a pen test) found by CVE, and the Security Feed can't match them. Retiring the coded Nessus reader (COM-1716) would lose all of that.

Two things are missing today:
1. **Looking something up for each item, without fanning out.** A follow-on read today turns each item into the items it returns. Here each finding should stay one finding, with the plugin's details attached to it. Feeds already read repeated addresses once a run, so a plugin found on 200 hosts is read once.
2. **Taking values from a list by a field beside them.** Nessus lists a plugin's attributes as name/value pairs (`attribute_name: cve`, `attribute_value: CVE-2024-…`). A mapping needs to say "the values whose name is cve".

Nessus is the first to need these; any service with a details endpoint or name/value lists benefits.

**Chain:** on the chain (a read definition's settings and the mapping language grow: API change)

## What the person sees
- **A read can "look up details"** for each item, at an address built from its fields (e.g. `/plugins/plugin/{plugin_id}`). The answer is attached to the item under a name (e.g. `plugin`), and the item stays one item. It's read once per distinct address a run, within the run's cap on follow-on reads. "No permission" can skip it, leaving the item without details.
- **A mapping can pick from a list by a neighbouring field**, e.g. a finding's CVEs = the values of `plugin.attributes` whose `attribute_name` is `cve`. It's declarative, like the rest of the language: no expressions, nothing that runs code.
- **Nessus's Findings feed on staging** is updated to look up each plugin. Its findings then carry CVEs, a CVSS score, a description and a solution, matching what the coded reader gave.
- Polaris, the assistants and the feed editor learn both, the way COM-1712 taught them the others. In the editor, a looked-up read shows as "Look up details at …".

## Done when
- Tested against a fake service: details attached once per distinct address, the item count unchanged, the cap counting look-ups, "no permission" skipping one, and a mapping picking CVEs out of a name/value list.
- On staging, Nessus findings have CVEs and join existing vulnerabilities by CVE. Their counts and severities are compared with a .nessus export of the same run.
- No service name in code (COM-1696).
