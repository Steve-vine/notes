The foundation of the sprint (ADR 0143). An assistant given only Compass's MCP address finds out for itself how to sign in, sends the person to Compass in their browser, and gets its own sign-in once they allow it.

**Wanted behaviour:**
- An assistant that reaches the MCP address without a sign-in is told where to sign in. It registers itself, with nothing for the person to copy.
- The person signs in to Compass as they normally do (password or Microsoft) and lands on the Allow screen (next task). Allowing it returns them to their assistant, now connected.
- The connection stays alive while it's used. After 30 days unused the assistant has to send the person through the browser again.
- A connection ends at once, on the assistant's next call, when the person disconnects it, an administrator disconnects it, the person is disabled, or their role stops including *Connect an AI assistant*.
- Each connection is one assistant for one person (name, connected on, last used). Connecting and disconnecting are recorded in Activity.
- The person's own list of connections, and disconnecting one, are available for the Connect page.
- While the switch-over is open, a personal token still opens the door as it does today.
- The Polaris window in Compass is unchanged.

**Done when:** against a local stack, an MCP client that knows only the address (Claude Code, `claude mcp add --transport http compass <url>` with no header) is sent to sign in, connects and lists tools. After a disconnect its next call is refused. Tests cover: an expired connection is refused; a disabled person and a lost grant are refused; a code can't be used twice or by another client; a sign-in without the proof the client started with (PKCE) is refused.

**Implementation:**
- MCP authorization spec: protected-resource metadata (RFC 9728) on the MCP address; a 401 carries `WWW-Authenticate` with `resource_metadata`. Authorization-server metadata (RFC 8414). Authorization code + PKCE (S256 only). Refresh tokens rotate on use, 30-day idle expiry. Short-lived access tokens (~1 h). Token revocation (RFC 7009). Audience-bound to the MCP resource (RFC 8707 `resource`).
- Client registration: dynamic registration (RFC 7591), plus client ID metadata documents if the ADR's findings say any target needs them. Registration is rate-limited and grants nothing on its own.
- mcp SDK 2.3 has `mcp/server/auth` (authorize, register, token, revoke, metadata handlers, `OAuthAuthorizationServerProvider`). Use it where it fits; read its source in the venv first.
- The authorize step hands off to the frontend: not signed in → the normal login, then back to the Allow screen with the request intact (local and Entra SSO both have to return there). The authorize endpoint lives on the internal address. Metadata, register, token and revoke live on the public address (internet-reach task). Check that clients accept an `authorization_endpoint` on a different host from the issuer; if any won't, raise it.
- `assistant/gate.py`: accept the new access token, or a personal token while the switch-over is open; then the same `assistant.connect` check and the same `Caller`. Update `NO_TOKEN`.
- New tables for clients, connections, codes and tokens, every secret stored hashed. Respect the log-redaction list. Add the API under `/api/v1` for "my connections" and disconnect.
- Rerun the portal-host boundary check: the vendor-portal and trust hosts must still refuse all of this.

**On the chain:** migration + API.
