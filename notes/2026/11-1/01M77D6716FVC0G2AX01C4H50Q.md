    Built: PR #1748 (auto-merge set; independent, no migration, no API change).

    What you'll see: when several people (or a person and the Browser smoke) move quickly through screens, the API no longer stops answering and isn't restarted. Requests beyond what it can serve wait their turn briefly, holding nothing, so a screen can be a little slower in a burst but doesn't error. The liveness check answers however busy the API is.

    Cause (found): a deadlock between two pools inside the API, not a slow page or a busy database. Each request runs its steps on one of 40 worker threads, but keeps its database connection (one of 15) from sign-in until its answer is sent, and between steps gives its thread back and asks for another. With more than ~40 requests in flight, every thread was held by a request waiting for a connection, while the 15 requests holding connections waited for a thread to finish. Nothing moved until the 30 s pool timeout; the liveness check also needed a thread, so it failed and Kubernetes restarted the API.
    Evidence: staging's log from the 08:01 restart shows 74 pool timeouts in two waves exactly 30 s apart, 64 of them at sign-in, then the kill. Locally, four control pages opened at once reproduced it: all 15 connections "idle in transaction" for 13 s+ with nothing running, 106 timeouts, 14 of 17 liveness checks failed.

    Fix:
    - The API now serves at most 15 requests at once per process; the rest wait without holding a thread or connection. The pool is 30 (two per request, since a few screens open a second one), so an admitted request never waits for a connection. Settings refuse a smaller pool.
    - Liveness touches nothing and needs no thread; readiness still checks the database, session store and broker.
    - Polaris's chat window gives its connection back while it waits for a reply.
    - Any request holding a connection for 5 s or more is now logged with its path, so next time we'd know who.
    - Liveness timeout default raised from 3 s to 10 s everywhere (staging already had 10).
    Local A/B, four pages at once: before 20 server errors, p95 31 s; after 0 errors, p95 9 s.

    Production: runs 2 API replicas with no pool or probe settings, so it has the same 15-connection pool and an even stricter 3 s liveness timeout: the same risk. Nothing to change in the production repo; the next release brings the fix and new defaults (30 connections per replica, 60 at most, well under the database's 100).

    Worth a follow-up (not logged yet): the control page's checks list is the slowest request (0.5 s alone, 5–12 s under load) and opens a second connection.

    Checks: lint, format, types; unit suite 2192 passed; 11 new admission tests (liveness test fails if it's made sync again); a new integration test recreates the deadlock in miniature on real Postgres (errors without the fix, all served with it); Polaris and DB integration tests pass; helm lint on all values files. After the staging deploy: Browser smoke plus a person walking control pages at the same time.

Found in the sprint 116 pre-UAT pass on staging (2026-11-12).

**What happens:** twice this morning the whole of staging stopped answering for about a minute and then came back. Every screen errored in the meantime, a save failed with a 502, and the Browser smoke failed six of its walks.
- **07:42 UTC:** someone was moving quickly through controls in the assessment queue (INS.1, INS.2…) while I was using E2E Test Company.
- **08:01 UTC:** the Browser smoke was walking every screen as each test account and reached control INS.1.

Both times, the API ran out of database connections. For 30 seconds every request waited for one, then failed. The health check timed out and Kubernetes restarted the API. A re-run of the smoke a few minutes later passed, and INS.1 opened quickly on its own. So it comes from load, not from one broken page.

**Why it matters:** production has more people on it than staging. A control page alone asks for about 20 things at once, and two people paging through controls quickly can be enough to fill the API's 15 database connections.

**Technical notes:**
- SQLAlchemy `QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00` on ~130 requests. Then liveness probe failed → exit 137.
- The API logs from before the restart had already rotated away, so which requests held connections for long isn't known yet. Sampling `pg_stat_activity` during a single INS.1 load showed nothing busy.
- Things to look at:
  - requests that hold a session while doing slow non-database work;
  - `idle in transaction` sessions (one was seen briefly on `directory_users`);
  - pool size versus uvicorn concurrency;
  - whether the health check shares the pool, and whether it should answer without a database connection;
  - production's settings.

**Done when:**
- The cause is found: which requests hold connections and for how long.
- Fixed so that two browsers walking every screen at the same time on staging don't exhaust the pool or restart the API.
- The health check doesn't fail just because the pool is busy.
- Production's settings are checked for the same risk.
