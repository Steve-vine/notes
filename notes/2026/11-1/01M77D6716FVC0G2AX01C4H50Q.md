Found in the sprint 116 pre-UAT pass on staging (2026-11-12).

**What happens:** twice this morning the whole of staging stopped answering for about a minute and then came back. Every screen errored in the meantime, a save failed with a 502, and the Browser smoke failed six of its walks.
- **07:42 UTC:** someone was moving quickly through controls in the assessment queue (INS.1, INS.2…) while I was using E2E Test Company.
- **08:01 UTC:** the Browser smoke was walking every screen as each test account and reached control INS.1.

Both times, the API ran out of database connections. For 30 seconds every request waited for one, then failed. The health check timed out and Kubernetes restarted the API. A re-run of the smoke a few minutes later passed, and INS.1 opened quickly on its own. So it comes from load, not from one broken page.

**Why it matters:** production has more people on it than staging. A control page alone asks for about 20 things at once, and two people paging through controls quickly can be enough to fill the API's 15 database connections.

**Technical notes:**
- SQLAlchemy `QueuePool limit of size 5 overflow 10 reached, connection timed out, timeout 30.00` on ~130 requests. Then liveness probe failed → exit 137.
- The API logs from before the restart had already rotated away, so which requests held connections for long isn't known yet. Sampling `pg_stat_activity` during a single INS.1 load showed nothing busy.
- Things to look at:
  - requests that hold a session while doing slow non-database work;
  - `idle in transaction` sessions (one was seen briefly on `directory_users`);
  - pool size versus uvicorn concurrency;
  - whether the health check shares the pool, and whether it should answer without a database connection;
  - production's settings.

**Done when:**
- The cause is found: which requests hold connections and for how long.
- Fixed so that two browsers walking every screen at the same time on staging don't exhaust the pool or restart the API.
- The health check doesn't fail just because the pool is busy.
- Production's settings are checked for the same risk.
