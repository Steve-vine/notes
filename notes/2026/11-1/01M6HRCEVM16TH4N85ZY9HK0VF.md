Sprint "Secrets - New Module" (ADR 0141, COM-1563). Builds on COM-1574. It follows the integrations tile pattern (ADR 0128).

## What people see

- **Admin ▸ Integrations ▸ GitHub.** A new tile. Connecting it walks through creating a GitHub App in the organisation:
  - The App's permissions are all read only. Compass shows the exact list, and why each is needed.
  - The App is installed on all repositories, or the ones chosen.
  - Then Compass is given the App ID, the organisation and the App's private key.
  - The tile has a health pill, like Azure's ("Connected · last read 10:42", "Can't sign in: the key was revoked").
  - A company can connect one or more organisations.
- **Compass's own key.** The App's private key is held like the Azure client secret: encrypted, write-only, replaceable, never shown again, redacted from logs (ADR 0103 §3). It never expires, so the tile suggests registering it in Secrets like any other key.
- **Deploy keys as sources.** Generated by ▸ GitHub deploy key: pick a repository, then a key. Each key shows:
  - its title and GitHub's key ID;
  - created, and **added by** (a GitHub login);
  - **last used**;
  - **Can write** or Read only;
  - always **Long-lived**, because deploy keys never expire.
- **Fine-grained personal access tokens as sources.** Generated by ▸ GitHub token. Each token shows:
  - its name, and the person it belongs to (a GitHub login);
  - the repositories and permissions it has;
  - **expires**, or "No expiration" (then Long-lived);
  - **last used**.

  Classic tokens can't be listed by GitHub's API, and the tile says so.
- **Not yet tracked.** Deploy keys and tokens that no secret uses join "Keys at a source, not yet tracked" (COM-1573), with Can write and Long-lived as information. They raise nothing.
- **Pairing.** `compass-source-key` = the deploy key's GitHub ID on the vault entry pairs it with the key.
- **Rotation proven** when:
  1. a new deploy key appears on the same repository;
  2. every stored copy is updated after it;
  3. the old key is removed;
  4. the old key wasn't used after the store change.

  Recorded as **Seen at source and store**. The sentences follow COM-1573 and COM-1574.

## Notes (technical)

- GitHub App permissions:
  - Repository **Metadata**: read (mandatory).
  - Repository **Administration**: read. Needed for `GET /repos/{o}/{r}/keys`, which includes `added_by` and `last_used`.
  - Organization **Personal access tokens**: read. Needed for `GET /orgs/{org}/personal-access-tokens`.
  - Secrets and Environments read are added by COM-1576. Ask for them here, so people install once.
- Authenticate with a JWT signed by the App key, then use installation tokens (short-lived). Cache them until shortly before expiry, keyed by the stored key, as Azure's are.
- Page through every repository, and respect rate limits (the installation's 5,000/hour). Read on the discovery schedule.
- A new tile in `core/integrations/tiles/github.py`, plus the connection model and encrypted key column (`core/secretbox`). Add the column name to the redaction list.
- Gitleaks: no realistic-looking private keys in fixtures (memory: gitleaks scans branch history). Generate test keys at test time.
- Real check: Steve creates the App on RootCause-IT. Read locally first.
