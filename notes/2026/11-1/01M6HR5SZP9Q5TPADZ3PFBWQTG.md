Sprint "Secrets - New Module". Write ADR 0141 recording the rules Steve agreed on 2026-11-03.

## Why

Most of our keys are generated by third-party services and kept in AWS Secrets Manager or Azure Key Vault. Nobody can say how old they are, who owns them, or whether a rotation actually happened. An expired key is an outage, an old key that nobody owns is how breaches start, and auditors ask for proof of key lifecycle management (ISO 27001 A.8.24, PCI DSS 3.7 and 8.6, SOC 2). Library controls this serves: **IDM.18** (machine and service identities inventoried, owned, rotated on a schedule — key `s42.IDM.3`), **IDM.19** (secrets held in a managed store — `s42.IDM.4`), **KMC.2** (key lifetime defined — `KMC.3`).

## The rules

- **The thing tracked is the secret, not the vault.** A vault only knows what someone put in it, and its date says when the copy changed, not when the key did. Each secret (SEC-N) has:
  - a **source**, where it was generated: a vendor from the Vendor register (Stripe, SendGrid…), a technology asset, or a source Compass reads (Entra app, AWS IAM user, GitHub);
  - the **systems that use it** (technology assets);
  - where it's **kept**: one or more store entries (AWS Secrets Manager, Azure Key Vault, GitHub Actions, Google Secret Manager) or a place typed in;
  - an **owner** (a person), and a **rotation rule**.
- **Compass never sees a value.** It reads names, dates, tags and settings only. The AWS policy, Azure role and GitHub App permissions Compass asks for cannot read a value: Compass must be *unable* to, not merely unwilling (ADR 0099 §7, ADR 0103 §5). The form for typing a secret in has no value field, and refuses to save anything that looks like a key.
- **Compass reminds and proves. It never rotates.** No writes to any vault, source or tag, and no "rotate now" button. Rotation is done by the owner or by the cloud's own rotation.
- **Nothing is due until a person registers it.** Store entries Compass finds wait on **Secrets ▸ Discovered** (ADR 0099: discovery finds, a person decides). Only registered secrets get due dates, reminders and checks, so switching the module on doesn't flood anyone's Actions.
- **Due date** = the earlier of the expiry at the source and the last rotation plus the rotation interval. Intervals come from a rubric by kind of secret, and can be changed per secret.
- **Long-lived** = no expiry at its source (most third-party API keys, AWS access keys, GitHub deploy keys). It's a pill and an age on the secret, and a filter. **It never raises an action, a gap or a check failure on its own** (Steve, 2026-11-03: the flag and the age are enough to change them out over time). A long-lived secret still gets the normal reminder when its rotation interval comes round.
- **Linking a stored copy to its secret.**
  - Tag the store entry `compass-secret` = `SEC-12`, and the next read attaches it.
  - Tag it `compass-source-key` = the source's own ID for the key (an Entra key ID, an AWS access key ID, a GitHub deploy key ID), and Compass pairs it with the key at the source.
  - Otherwise Compass suggests a pairing from names and timing, and a person confirms it.
  - Compass shows the exact tag to add. It never writes one.
- **A rotation is proven** when Compass sees both ends change: a new key at the source, a new version in every store, the old key gone at the source, and only the new one used since. Where the source can't be read (a third-party key), a store change plus the owner confirming that the old key no longer works is the proof. A rotation the owner records by hand is kept, marked as recorded rather than seen. The cloud's own rotation (AWS rotation on) is recorded as "Rotated by AWS".
- **A half-finished rotation says what's left:** "the new key isn't in the store yet", "the old key still works", or "something still uses the old key".
- **Actions** (ADR 0137: one action per thing). A secret has at most one open action for its owner: *Secret · Rotate* (from 30 days before it's due, the lead time a setting), *Secret · Confirm rotation*, or *Secret · Finish rotation*. An ownerless secret's action goes to the people who can manage secrets.
- **Check:** "Secrets are rotated on time" fails while any registered secret is past due, raising a gap on IDM.18. Long-lived alone never fails it.
- **Leavers and incidents.** A leaver's secrets lose their owner, are flagged "Owner left" and need a rotation. An incident lists the secrets its affected systems use, and can ask for them all to be rotated.
- **Where it sits.** Modules ▸ **Secrets**, after Inventory: who people are, what they reach, what systems hold, and the keys those systems use. Company-scoped.
- **Who can do what.** Two new permissions, *View secrets* and *Manage secrets*. The built-in Admin gets both; the starter roles stay frozen. A secret's owner can edit it and record or confirm its rotation.

## My assumptions (not discussed with Steve)

- Reference prefix **SEC-N**.
- Default rotation intervals: API key, deploy key, client secret, password and other: 365 days; access key and token: 90 days; certificate: no schedule (its expiry drives it).
- A leaver's secrets: the rotation is due in 14 days.
