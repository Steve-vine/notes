## Why

Moneypenny's SOC 2 review period runs 2027-01-18 to 2027-04-18. About seven of A-LIGN's requests come from logging and monitoring: audit-log settings with a recent extract for networks, servers, databases, applications and VPNs (R-1161, R-1166, R-1171, R-1177, R-1184), monitoring screens (R-1078) and capacity (R-1453). They touch EVM.2, EVM.6 and EVM.1. That evidence lives in Datadog (EU, `https://api.datadoghq.eu`).

Datadog's read API needs **two** keys on every request, each in its own header: `DD-API-KEY` and `DD-APPLICATION-KEY`. Today a Collection integration sends its key in one header. A key of several parts (COM-1722, `key_format`) can only be assembled into that one header's value, so Datadog can't be set up.

## What people see

- When setting up an integration that signs in with an API key in a header, the person (or Polaris) can say that the key has parts that each go in a header of their own, naming the header and the part. For Datadog: `DD-API-KEY` ← "API key", `DD-APPLICATION-KEY` ← "Application key".
- The account form asks for each part in its own box, as it does for a several-part key today. Each part is kept encrypted and write-only, and is never returned or shown. The account shows a hint of the last four characters of each part.
- The test read and every read send all the headers.
- Polaris's integration designer knows the option and proposes it when a service's docs ask for more than one key header.
- A one-header key, with or without `key_format`, works exactly as before.

## Rules

- Configuration only, never code that knows Datadog (ADR 0147 §9, COM-1696).
- None of the key headers may be a header Compass sets itself (Host, Authorization, Cookie and the others on the reserved list), nor one of the integration's fixed headers. At most five parts, as today.
- Changing which headers an integration's key goes in asks for every account's key again, just as changing the sign-in method does.

## Done when

- A Datadog Collection integration can be defined, an account added with an API key and an application key, and its test read passes against `/api/v1/validate` (or a cheap list such as `/api/v1/monitor?page_size=1`).
- Tests cover the two-header sign-in, the refusal of reserved or duplicate header names, and the fact that parts are never returned.

**Independent** (unless it needs a migration for the account's parts, in which case it joins the chain).
