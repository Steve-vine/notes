The core of ADR 0145 (COM-1695). The tasks for each area plug into this.

**Chain:** on the chain — migration + API

## What the person sees

- On a Collection integration's page, a **Feeds** section lists each feed: the area it feeds, a switch, its schedule, its last run (when, and what it did), and its state (*Running*, *Held for review*, *Broken*, *Off*, *Waiting for approval*).
- **Add a feed:**
  1. Choose the area.
  2. Choose the read or reads, which use the same read form as a check (path, query, where the items are).
  3. Map the area's slots, one row per slot: *take it from* a path in the item, a fixed value, or a value map (e.g. the service's `critical` → Critical, `fixed` → solved).
  4. Say what closes a record: *the source says so* (a slot and its values), or *missing from a complete read*.
  5. Choose a schedule: hourly, six-hourly, daily or weekly. Six-hourly is the default (my call).
- **Preview** runs the reads against one account now and shows the records the feed *would* create, update and close, without saving anything, with any slot it couldn't fill named.
- A feed starts **Waiting for approval**. Someone with the area's right approves it. The first run happens straight after.
- **Run now** is available to the area's managers.
- The switch is a feature switch (ADR 0128 §5). Off keeps the feed and everything it brought in.

## What a run does

- Reads every account the company has for the service, completely or not at all (ADR 0142 §4).
- Maps each item into the area's shape and hands the records to the area (the next three tasks), which applies its own rules.
- Keeps what was asked, when, through which account, and counts of new, updated, closed and unmapped records. A page of history per feed.
- Never stores a whole response. It keeps only the mapped slots, plus the service's text where the area keeps it.

## The configuration language

- Paths into the item (dotted, with `[]` for lists), fixed values, value maps with a default, date parsing (ISO, epoch seconds or milliseconds, or a stated format), joining two fields into one, taking the first non-empty of several, and lower/upper case.
- Nothing more for now. **No expressions that run code.** The language is data that Compass evaluates itself, like checks' rules (ADR 0142 amendment, COM-1606).
- Anything a service needs that this can't express is a capability for sprint sj4f1kj, never a special case (COM-1696).

## Done when

- A feed can be created, previewed, approved, run on its schedule and with Run now, switched off and on, and deleted (deleting keeps what it brought in).
- A feed whose service or account is removed shows *Broken*, with the reason.
- Activity records feed changes and approvals. A run isn't an activity entry; it's the feed's history.
- Tests:
  - the mapping language, case by case;
  - a preview saves nothing;
  - an unapproved feed never runs;
  - a switched-off feed never runs;
  - a read that fails part-way changes nothing;
  - approval needs the area's right;
  - COM-1696's test passes.
- Shown on screen to the same standard as the check forms (screen conventions).

## Notes

- New `collection_feeds` (integration, area, reads JSON, mapping JSON, closing rule, schedule, approved by and on, state) and `collection_feed_runs`.
- Reuse `core/collection/client.py` for every request, so the read-only, public-address and complete-or-nothing rules hold. Reuse `runner.py`'s account loop.
- One Beat entry that runs due feeds, not one per feed. Add a task label (`core/task_labels.py`).
- The area hand-off is one interface (`apply(company, feed, records, complete=True|False)`) that each area implements.
