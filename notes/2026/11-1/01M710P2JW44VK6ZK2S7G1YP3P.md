Raised by Steve while testing evidence collection on staging (2026-11-09). He defined a Cloudflare Collection integration with Polaris. Polaris's setup steps told him to make a **personal** API token, but Cloudflare recommends an **account** API token for a service connection. He made an account token with read-only rights. The test read refused it: "The service refused the sign-in (401). Check the key."

## The problem

- **The test read only works for personal tokens.** Polaris set the test read to `GET /user/tokens/verify`. Cloudflare only verifies personal tokens there. An account-owned token has its own verify address, `/accounts/{account_id}/tokens/verify`, and gets a 401 from the `/user/` one. The key was valid; the test read was wrong for it.
- **Compass sets one test read for the whole service, not one per account**, so it can't carry each account's Cloudflare account ID. The test read has to be an address that answers for every kind of key, such as `/zones` (a list any key that can read zones can see).
- **The setup steps steered towards a personal key.** Many services offer both a personal key and one owned by the account, organisation or a service user (Cloudflare account tokens, GitHub Apps and fine-grained tokens, Atlas organisation keys). The owned one is better for Compass: it doesn't stop working when the person leaves.
- The define prompt says "test_path is a cheap GET that works for any account". "Account" is ambiguous there, and nothing warns Polaris off "who am I" or "verify my token" addresses that belong to one kind of key.

Workaround on staging today: change the Cloudflare test read to `/zones` on screen.

## Done when

- **Polaris's define prompt** says the test read must answer for every kind of key the service issues, personal and account- or organisation-owned. It should avoid addresses about the current user or one kind of token (`/user`, `/me`, `/user/tokens/verify`) and prefer a cheap list the read-only key can see. It also says that Compass sets one test read for the whole service, so the address can't hold a per-account value such as an account ID.
- **Setup steps (key_steps)** prefer a key owned by the account, organisation or a service user where the service offers one. They name the read-only rights to tick, and mention the personal key only as the fallback.
- **"Why did the test fail"** (the explain step) knows this case. When a key is refused at a user-only address, it proposes a test read that works for any key, rather than telling the person to change their key.
- **Tests:** the define and explain prompts carry the new guidance. Use a unit test on the prompt text, the way COM-1640 checked the Accept guidance.
- **On staging:** defining Cloudflare with Polaris gives a test read that isn't under `/user/` and setup steps for an account API token. A real Cloudflare account token passing the test needs Steve's token, so that part is Steve's to check.
