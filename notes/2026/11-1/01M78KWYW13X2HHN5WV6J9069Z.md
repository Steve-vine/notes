## Why

Steve, testing on 2026-11-12: "At the moment IP addresses aren't a property of assets so the only way to add them is as an alias. As vulnerabilities tend to come in tied to IP addresses they need to match against them. This still seems to work but I wonder if IP addresses should be a separate property."

It does work: matching compares a target's address with an asset's aliases as plain text (`core/vulnerabilities/matching.py`, ADR 0129 §3b). As aliases, though, IPs:
1. **Aren't checked.** A typo, a stray space, or the same IPv6 address written differently silently fails to match.
2. **Go stale unseen.** Cloud and DHCP addresses change, and a stale one quietly sends new findings to the wrong asset. An alias has no source and no last-seen date.
3. **Clash unnoticed.** Two assets with the same IP make every finding on it "ambiguous" on Unmatched, and nobody learns that until it happens.
4. **Can't be ranges.** A cluster, load-balancer pool or small subnet can't belong to one asset; today that needs a company-wide IP-range rule.
5. **Don't say Public or Internal.** External pen tests report public addresses, often the firewall's or load balancer's, not the server's.

Steve agreed to a separate property (2026-11-12).

## What the person sees

**On the asset**
- The Technology asset form has an **IP addresses** list.
  - Each entry is a single address (IPv4 or IPv6) or a range (CIDR, e.g. 10.20.0.0/28).
  - Each entry has a **Public / Internal** label. When an entry is added, the label is guessed from the address (private, link-local and CGNAT ranges are Internal) and can be changed.
  - Entries are checked as they are typed ("That isn't an IP address or range"). They are stored in one standard form, so `2001:db8:0:0::1` and `2001:db8::1` are the same address, and a range is stored by its network.
  - A range is limited in size (no wider than /16 for IPv4 or /48 for IPv6), so one asset can't swallow a network. Wider ranges belong in a matching rule.
- The asset's page shows the addresses in their own row, with Public/Internal.
  - Where discovery supplied an address, it shows **where it came from and when it was last seen**.
  - An address the source hasn't reported for 30 days is shown faded, as "Not seen since <date>". It still matches until a person removes it.

**Duplicates are flagged, not refused** (as the serial number in COM-1757 is).
- Saving an address that another asset in the company already has, or that falls inside another asset's range, shows a warning naming that asset, with a link.
- An internal address can legitimately repeat, for example across two sites.
- The Technology tab gets a filter, **Shares an IP address**.

**Discovery fills them in**
- Where a discovery source or a Collection feed into Inventory gives an address (a cloud instance's private and public IPs, a directory server's address), it is added to the asset with its source and last-seen date, and refreshed on each read.
- **Discovery never overwrites or removes an address a person entered.** It also never removes one it added itself: when the source stops reporting an address, it only fades.
- This is configuration, never code that knows a service (ADR 0147 §9). A feed maps its address field like any other field.

**Matching**
- A vulnerability target's address matches an asset's single address exactly, or falls inside its range.
- An exact address beats a range. Two assets that are equally good matches stay ambiguous on Unmatched, as now, naming both.
- An asset's range sits **before** the company's IP-range matching rules: what Compass knows about an asset comes first (§3b, step 1).
- When it's added, Unmatched is re-tried, so findings already waiting are placed where they now match.

**Search**
- The Inventory search (COM-1756) finds an asset by an address or by an address inside its range.
- The top-bar search finds it too.

**Existing IP aliases move across**
- A one-off move, run with the migration, takes every alias on a technology asset that is an IP address or range and turns it into an IP address entry. It is labelled Public or Internal by the same guess, and recorded as entered by a person, since a person typed it.
- Aliases then hold names only. Typing an IP address as an alias afterwards says "Add it under IP addresses", with a button that moves it there.
- The activity log records the move once per asset, as made by Compass, listing what moved.

## Notes for the build

- **On the chain**: new data on a technology asset (address, prefix length, Public/Internal, source, last seen, entered by a person or by discovery), a data migration from aliases, and API schema and `schema.d.ts` changes. Postgres `inet`/`cidr` types and the containment operators make "inside a range" and duplicate checks cheap.
- Matching (`known()` in `core/vulnerabilities/matching.py`) reads addresses and ranges alongside aliases and attached resources' addresses. Keep the preview and the save on the same code (they share `place_unmatched`).
- Discovery sources already carry `address` facts (e.g. `core/discovery/review.py`). Fill the new field from them where a resource is attached to an asset.
- **Polaris**:
  - `inventory_get_technology_asset` and the list tool return the addresses;
  - `inventory_add/update_technology_asset` can add and remove addresses (with Public/Internal);
  - the list tool can filter by an address ("which asset is 10.20.0.5?");
  - `vulnerabilities_where_is_issue` names the address that placed a finding.
- Amend **ADR 0072** (an asset's IP addresses) and **ADR 0129 §3b** (matching on them, ranges before rules). Both are dated amendments.
- Coordinate with COM-1756 (search), COM-1757 (duplicate-flag pattern), COM-1775 (a new asset made from a finding should fill IP addresses, not aliases, from an IP host) and COM-1758 (the delete/duplicate flow moves addresses with the other links).

## Done when

On staging, in E2E Test Company:
- An asset takes `10.20.0.5` (Internal, guessed), `203.0.113.10` (Public, guessed) and `10.20.1.0/28`.
  - `10.20.0.300` is refused with the message.
  - A /8 is refused, pointing to matching rules.
  - Two ways of writing one IPv6 address are kept once.
- Adding `10.20.0.5` to a second asset warns, naming the first, and saves. Both show under **Shares an IP address**.
- A Nessus import with a finding on `10.20.1.7` places it on the asset by its range. One on `10.20.0.5` stays ambiguous, naming both assets.
- An asset that had `10.20.0.9` as an alias before the migration now has it under IP addresses, and not as an alias. A finding that matched it before still matches.
- An asset attached to a cloud resource shows that resource's IPs with their source and last-seen date. A person's own entry is untouched by the next read.
- Searching the Technology tab for `10.20.1.7` finds the asset with the range.
- Via Polaris: "which asset is 10.20.0.5?" answers. Adding and removing an address works and is in the activity log as via Polaris.
