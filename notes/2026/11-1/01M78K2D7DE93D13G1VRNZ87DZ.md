## Why

Steve, testing on 2026-11-12: "Importing a pen test requires every finding to be associated with an asset, this is OK most of the time but occasionally a finding comes up that can't be assigned to an existing asset, this ends up with either having to create a new asset as a placeholder or picking a related one."

There are two cases. This task covers the one where the thing **really exists but isn't in Inventory**: a forgotten web server, a test subdomain, a box the tester found. A new asset is the right answer here, because the pen test has found a gap in Inventory. What's wrong today is that adding one means leaving the import, filling in the full asset form, and coming back. Nothing marks the asset as half-done, so it stays a placeholder for good.

The other case, a finding that isn't about any one asset, is the companion task (Company-wide vulnerabilities). Steve chose both, and skipped "raise as a gap or risk instead" (2026-11-12).

## What the person sees

- In the **"Systems it affects"** picker on each finding of a pen-test import, and in **Record a vulnerability**, the last option is **New asset…**.
- It opens a short window:
  - **Name**: filled from the finding's first host or URL, which can be changed.
  - **Type**: system, application or datastore.
  - **Owner**: blank means the company's default vulnerability owner applies, as now.
  - **Aliases**: filled with the finding's hosts and URLs (each can be removed), so later scans and pen tests match it on their own.

  Nothing else is asked.
- On save, the asset is in Inventory and already chosen on the finding. A person can add several this way, one per finding, before confirming.
- The asset carries **"Added from a pen test, needs completing"**, with a link to the report (or "Added while recording a vulnerability"). It shows:
  - as a pill on the asset's page and in the Technology list;
  - in a filter, **Needs completing**, on the Technology tab;
  - in the asset owner's **Actions**, as "Complete <asset>".

  Saving the asset's full form clears the mark. So does **Mark as complete** on its page.
- **New asset…** is offered only to people who can add assets in Inventory. Someone who can work vulnerabilities but can't add assets sees, under the picker, "Not in Inventory? Ask someone who can add assets, or mark it Company-wide", with the second part once the companion task is in.
- The activity log records the asset as added from the pen-test import (or the Record window), by the person.

## Notes for the build

- **On the chain**: the mark is a new field on a technology asset (migration). The create and update schemas and `schema.d.ts` change.
- Reuse the asset create route. The window is a thin form, not a second asset form. Hosts become aliases using the same normalisation the alias field uses.
- The Actions item follows the ADR 0055 action-source pattern.
- **Polaris** parity: `inventory_add_technology_asset` gains the "needs completing" mark (set when added for a finding), and the Technology list tool can filter on it. COM-1772's `vulnerabilities_update_pentest_finding` can name a new asset by asking first, then adding it with the mark.
- Amend **ADR 0129 §7a** (dated) for the new route into Inventory, and note the mark in **ADR 0072**.

## Done when

On staging, in E2E Test Company:
- On a pen-test import, a finding whose host isn't in Inventory gets a **New asset…** with the name and aliases filled from its hosts. Confirming puts the vulnerability on it, with the default owner and a fix-by date from the report date.
- The asset shows "Added from a pen test, needs completing", linked to the report. It appears under **Needs completing** on the Technology tab and in its owner's Actions. Saving its full form clears all three.
- The same works from **Record a vulnerability**.
- A person who can work vulnerabilities but can't add assets doesn't see **New asset…**, and sees the hint instead.
- A later finding naming one of those hosts is suggested onto the new asset by itself.
