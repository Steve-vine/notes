Sprint "Secrets - New Module" (ADR 0141, COM-1563). Builds on COM-1571. This is the main path for Steve's estate: keys generated by a third party, kept in AWS or Azure.

## What people see

- **A stored copy changes.** When a read finds a newer version in an attached store entry, the secret's history records: **"New version in AWS Secrets Manager ▸ prod ▸ billing-api/stripe-live, 4 Nov"**.
- **The owner confirms.** That same secret's one action becomes **Secret · Confirm rotation**: "The copy in AWS Secrets Manager changed on 4 Nov. Does the old key no longer work at Stripe?"
  - **Yes, the old key is revoked.** A rotation is recorded, dated the store change, proven **Seen in the store, confirmed by owner**. Next due recalculates.
  - **Not a rotation** (a format change, a tag edit…). Dismissed, with an optional note in the history. Nothing else changes.
  - **Not yet, the old key still works.** The action becomes **Secret · Finish rotation**: "Revoke the old key at Stripe". It stays open until confirmed.
- **Several copies.** A rotation counts only when **every** attached copy has changed. Until then:
  - **"Half done: 1 of 2 copies updated."**
  - It names the one that hasn't changed: "Azure Key Vault ▸ kv-prod ▸ stripe-live hasn't changed since 3 Mar."
  - The action is *Finish rotation*.
- **Rotated by AWS** (COM-1569) needs no confirmation, because AWS changes both ends itself. If the same key also has a copy elsewhere, that copy must still change before the rotation counts.
- **Warnings model.** A half-finished rotation shows on the secret as a **Needs attention** pill, with a sentence saying what's left. The source tasks (COM-1573 onwards) add their own sentences: "the new key isn't in the store yet", "the old key still works", "something still uses the old key".
- **Still one action per secret** (ADR 0137): *Rotate*, *Confirm rotation* or *Finish rotation*, never two.

## Notes (technical)

- Compare each store entry's newest version CreatedDate (AWS) or `updated` (Key Vault) to what was last seen. Store `last_seen_version` per entry.
- A store change opens a `rotation_in_progress` on the secret: started_at, copies changed, copies outstanding. Confirming writes the `secret_rotation` row (proof `store_confirmed`) and clears it.
- Keep the warnings as a small list of typed reasons on the secret, so each source can add its own without new screens.
- The action source in `core/actions/secrets.py` picks *Rotate*, *Confirm*, or *Finish* from the secret's state.

**Chain:** on the chain (migration and API).

**Done when:** on staging, in E2E Test Company, with seeded store entries:
- bumping one copy's version puts *Confirm rotation* on the owner's Actions;
- "Yes" records a rotation proven *Seen in the store, confirmed by owner*;
- "Not a rotation" leaves Next due unchanged.
- **One key, kept in two clouds** (Steve, 2026-11-03): SEC-N, generated by a test vendor, has a copy in AWS Secrets Manager and a copy in Azure Key Vault, and is used by an AWS pipeline and an Azure pipeline.
  - Bumping only the AWS copy shows "Half done: 1 of 2", names the Azure copy, and gives the owner *Finish rotation*. It doesn't ask for confirmation yet.
  - Bumping the Azure copy turns the action into *Confirm rotation*. "Yes" records one rotation, dated the later change, and Next due moves on.
  - Both pipelines show the secret on their Secrets cards throughout.

The same case with a GitHub deploy key as the source is tested in COM-1581.
