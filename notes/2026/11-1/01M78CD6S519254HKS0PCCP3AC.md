## Why

Steve, testing on 2026-11-12: "There seems to be an MCP miss, currently it's not possible to set or edit the affected system on a finding." He asked for a check on whether the gap around findings is bigger. It is.

**Pen-test import page.** Polaris reads a report and proposes its findings (`vulnerabilities_propose_pentest_findings`), with systems as suggestions only. Once proposed, Polaris can't see a finding as it now stands or change it. Every change has to be made on screen, though the API has a route for each one:

| On screen (import page) | API | Polaris tool |
|---|---|---|
| See the proposed findings, each with its systems, hosts, confidence and Check this | `GET /pentest-imports/{id}` | none (the read tool returns only titles already proposed and, for a retest, the earlier findings) |
| **Change a finding: systems, title, severity, kind, CVSS, CVEs, hosts, description, recommendation** | `PUT /pentest-imports/{id}/findings/{fid}` | **none**. This is Steve's case |
| Add a finding by hand (e.g. a scanned report with no text) | `POST /pentest-imports/{id}/findings` | only as a "proposal" with page and confidence |
| Remove a proposed finding | `DELETE /pentest-imports/{id}/findings/{fid}` | none |
| Mark a Check this as looked at | `POST …/findings/{fid}/open` | none |
| Change one retest outcome | `PUT …/findings/{fid}/outcome` | only by proposing all outcomes again |
| Confirm into the register / Withdraw | `POST …/confirm`, `…/withdraw` | none, **deliberately** (ADR 0129 §7a: a person confirms). Keep it that way |

**A vulnerability in the register** (including a confirmed pen-test finding):

| On screen (vulnerability page) | API | Polaris tool |
|---|---|---|
| Edit details: title, kind, description, CVEs, CVSS, hosts/resources, recommendation | `PATCH /vulnerabilities/{id}` | **none** |
| Logged in error | `POST /vulnerabilities/{id}/state` (logged_in_error) | **none** (mark fixed, false positive, reopen and accept exist) |
| System | not changeable on screen either: a vulnerability is one per system, so a wrong system is logged in error and recorded again on the right one | none. With "logged in error" plus `vulnerabilities_record`, Polaris can do the same move |

## What to build

Tools in the Vulnerabilities area, acting as the person with exactly the permission the screen needs (*Work vulnerabilities*). Each tool names the finding as the page does (its title, or its position in the report) and returns the import page link.

1. **`vulnerabilities_get_pentest_import`**: the report's findings as they stand, each with title, severity, kind, page, confidence and check reason (and whether it has been looked at), hosts, **systems** (accepted, plus Compass's suggestions), CVEs, CVSS, and the retest outcome where there is one. Read-only.
2. **`vulnerabilities_update_pentest_finding`**: change a proposed finding before confirmation. Changes are partial, so naming systems doesn't wipe the rest. Systems are by name, resolved as `vulnerabilities_record` resolves them: set the list, or add/remove. Accepting Compass's suggested systems is one call.
3. **`vulnerabilities_add_pentest_finding`**: a finding the person dictates, without a page or confidence.
4. **`vulnerabilities_remove_pentest_finding`**: say first what will go.
5. **`vulnerabilities_mark_pentest_finding_checked`**: the person has looked at a Check this.
6. **`vulnerabilities_set_retest_outcome`**: one earlier finding's outcome.
7. **`vulnerabilities_edit`**: a register vulnerability's details, as the page's Edit, only while it's open. The tool description says the system can't be changed here, and says how to move it.
8. **`vulnerabilities_log_in_error`**: with a reason, as the screen asks.

Confirm, withdraw and upload stay on screen (ADR 0129 §7a; a file can't come through chat). Each tool's description says so where a person would expect it.

## Notes

- The routes are all there already. This is assistant tools only, so **independent** (no migration, no API change).
- Keep the Vulnerabilities area under Copilot's 128-tool limit (ADR 0144). Count the tools after adding.
- What a report says stays untrusted text (ADR 0129 §7a). Nothing here lets Polaris confirm.
- Audit findings have a similar but separate gap: Polaris can list them and draft a plan, but can't record, edit, link gaps or add closing evidence. Some of that is a deliberate sign-off (ADR 0133 §9: submitting to the auditor). It's not in this task.
