    The Kubernetes kind set is a per-integration dictionary, not a hard-coded trio (agreed 2026-07-24, Sprint 20: ISE-256..259). What a Kubernetes integration discovers as workloads was fixed at Deployment/StatefulSet/DaemonSet — the closed set of built-in controllers whose semantics (owner chain, replicas, restart, monitor tag) were all known a priori.     The generalisation keeps the original rule ("only kinds whose touchpoints we understand become workloads") but makes the set configurable per integration instance: a Kind Dictionary on the System, each entry mapping a GVK onto a CANONICAL ENTITY TYPE — `Rollout.argoproj.io/v1alpha1 is-a workload` — with optional overrides (replica JSONPaths, DataDog scope tag, owner-chain mode). Mapping to a canonical type inherits the whole semantics bundle. Config-authored cross-entity relationships (depends-on) remain the separate Relationship Mapping edge-authoring work.

    Built-ins become locked dictionary entries (same mechanism, not special cases). Write actions stay off for custom kinds — restart semantics are per-CRD (Rollout restarts via spec.restartAt, not the annotation) and belong to a later, explicitly-classified slice, per the "more governance, less generic" capability principle.     The operating model splits by persona, completing what ADR 0055 started: DevOps engineers investigate via Claude/MCP and author playbooks; Service Desk responders use a guided incident page that can ONLY execute published playbooks — with no per-execution approval (ITIL standard-change: the approval is spent once, at publish, by a second engineer who is not the sole author).

    A V2 playbook = a freeform natural-language body interpreted by AI, inside a structured envelope the server enforces: allowed catalogue operations (T1/T2 only, never T3), incident-derived target binding, run bounds (actions / wall-clock / tokens), deterministic validation predicates over evidence queries (the interpreter never self-certifies success), and an escalation path (halt + summarise; never roll back, never improvise).     CANON ADDITION (2026-08-04, from functional testing / ISE-539) — fold into the body on next edit:

    ## Webhooks are core application, not an integration

    An **integration** is ISE reaching into an external system of record — credentialed, synced, health-checked, with a connector contract. A **webhook source** is none of these: it is ISE's own front door, a token the operator mints so outside senders can push events in. It belongs to the core application, beside the event layer it feeds.

    The distinction had blurred in both directions: the synthetic System backing each source's alerts (ADR 0048 plumbing for severity overrides and dedup) leaked into Settings → Integrations and Overview as an apparent peer of Azure/EntraID — constant fake health, decoy State toggle, and orphaned forever if its source was deleted — while the managed event-display sources for polled integrations (ADR 0051 §4) leaked onto the core Webhooks page.

    Rule going forward: whatever plumbing webhook signals need may exist in the schema, but nothing webhook-shaped is ever presented as an integration, and nothing integration-owned is ever presented as an operator webhook. Settled now, deliberately ahead of Sprints 47–49 (Integration Decoupling / Packs), so the pack registry's definition of "integration" is built on the clean boundary.

    ## Voice escalation and on-call

    The attention ladder gains a rung above the Teams card. ADR 0069 §5 capped ISE's ability to demand attention (bots cannot send urgent/repeating Teams messages); the rung above a card is a phone that rings.

    Voice is PSTN via Azure Communication Services Call Automation — explicitly NOT Teams calling (ADR 0079). Both Teams-client routes (a Graph calling bot; ACS→Teams VoIP interop) can only ring a running Teams client and are unsupported/unreliable on Teams mobile — but the person a voice escalation exists for is precisely the one away from their desk. The bot stays notification-only; ACS arrives as its own integration (ADR 0071 shape) and `acs-voice` as a second channel kind, forcing the kind→poster registry ADR 0067 promised.

    On-call rotas are a first-class domain (ADR 0080): ordered members, contact number on the MEMBERSHIP (the person controls which device rings; EntraID mobilePhone is prefill only), simple rotation + override — deliberately not PagerDuty (no layered schedules/time zones/iCal). A rota is a DESTINATION resolved at delivery time, so it serves Teams cards before any calling exists.

    Acknowledgement amends 0067's fire-and-forget: escalation is a per-incident state machine (announce → wait → call → walk the chain, Beat-driven) halting on ack or resolve. On PSTN, ANSWERED IS NOT ACKNOWLEDGED — voicemail answers calls; the human signal is DTMF press-1, in v1 not deferred. Contact numbers are PII: redaction list, and logs name the person, never the number.

    **A public hostname may be part of an entity's identity** — ruled by Steve, 2026-08-05 (ISE-398 → ISE-556).

    The estate's identity model (ADR 0028) has so far treated a native key as an *integration's own name for a thing* — `k8s:shop/deployment/checkout`, `datadog:service:checkout`. This extends it: a **provider-assigned public hostname** is also an identity key, carried in a `dns:` namespace (`dns:myapp.azurewebsites.net`).

    **Why it is identity and not merely an attribute.** The hostname is issued by the provider, globally unique, and stated by the source of record — the same qualities that make a native key trustworthy. Treating it as identity means the existing alias machinery does the join: `reconcile_discovered`'s edge pass already resolves an edge's target through the alias table, so a Cloudflare zone can point a `routes-to` edge at `dns:<cname target>` and it lands on whatever entity claims that hostname. No new matcher, no second resolution mechanism alongside the one ADR 0028 deliberately has one of.

    **What it commits us to**, both accepted:
    - Two entities claiming one hostname would be a merge path, not just an edge path. Safe in practice — a provider does not issue one `default_hostname` twice — and ISE-510's ambiguity rule ignores a contested key rather than collapsing entities.
    - Signals resolve on hostnames too, since `link_findings_to_entities` also goes through aliases. A finding whose `entity_key` is a hostname will start landing on the entity.

    **The boundary.** Only provider-assigned, exact, stated strings qualify — App Service `default_hostname`, ELB `dns_name`, AKS `fqdn`. **Not** IP addresses (reused across VPCs and accounts; the estate stores private IPs, which is not what a public A record points at), and not name-similarity. A weaker matcher, if ever wanted, goes through the proposals queue as a tier-2 claim — it does not get to mint identity.

    This closes the ADR 0062 §3 deferral of DNS `routes-to` harvesting. Needs its own ADR when ISE-556 is built.

    Measured basis for the ruling: 33 zones, 698 CNAMEs, 465 distinct targets → **16 exact matches, all production Azure App Services** (`payments.moneypenny.com` → `app-mp-prd-uks-payments`, and fifteen more). Detail in `docs/briefs/dns-routes-to-mapping.md`.

    INTEGRATION DECOUPLING — Option A, the in-process squeeze (Sprint 47, ISE-495..499, 2026-08-05)

    The target: adding an integration should touch the registry line and nothing else. Four places still made that false, and each has the same shape — knowledge about a connector living in a module that has no other business knowing it. Four rulings, ADRs 0083-0086.

    1. A CONNECTOR DECLARES ITS OWN SUMMARY CARD (ADR 0083)
    The System detail page carried a bespoke "at a glance" card per integration — an endpoint plus a `_require_<type>` guard, a response schema, a React component, and a `connector_type === 'x'` line each. The screen whose whole purpose is to be generic over integrations had to be edited to learn about each one. `Connector.summary()` now returns labelled sections; one endpoint and one component render them. Three constraints make it safe:
      - it declares MEANING, not appearance (semantic tones, closed sets for style and icon), so the design system can restyle every card at once;
      - it takes NO ConnectorContext, so a summary structurally cannot cost a source round-trip on page view and renders for a system whose credential expired;
      - it never sees a Session — a narrow read-only reader answers a fixed set of questions in plain values, so the estate model stays free to move underneath every connector.
    Six endpoints, four guards, eight schemas and five components deleted; the OpenAPI surface SHRANK by ~1,100 lines.

    2. TAG WRITEBACK IS DECLARED, NOT MAPPED CENTRALLY (ADR 0084)
    `tag_remediation` held `{connector_type: operation}` plus a native-key-parsing branch per connector. Now an ActionSpec carries `tag_write` and the connector derives the target from its own key format. This caught a LIVE BUG: Kubernetes retags built `kind: "deployment"` while `set_label`'s schema only accepts `Deployment`, so every Kubernetes tag correction had ALWAYS been refused by its own action's validation. Green suite throughout, because the mapping and the schema lived in different files and nothing compared them. The new guard compares them, for every connector that declares a tag write.

    3. A CONNECTOR DECLARES ITS OWN SWEEP CADENCE (ADR 0085)
    The four polling sweeps each needed a Beat entry AND an `include` registration in `worker.py`. The two fail differently when forgotten — a missing entry means the sweep silently never runs; a missing include means Celery discards the task as unregistered, with no run and no error anyone sees. Both are now derived from one `SweepSpec`, so declaring the sweep IS registering it. The State toggle still gates the work (ADR 0072) and a test holds every declared sweep to it.

    4. A CANONICAL VOCABULARY IS SERVED, NEVER HAND-COPIED (ADR 0086)
    `ENTITY_TYPES` was mirrored into three React files, each with a comment claiming it mirrored the backend, and nothing checked. They had already drifted — the kind-dictionary editor was missing `secret`, so a Kubernetes Secret CRD could not be mapped to the type ISE-517 added for it. Served from `/api/v1/meta` as an ENUM, so it rides the OpenAPI snapshot: `generate:api` propagates it and CI's api-types check reddens on staleness. The distinction that matters for the next case: a LIST OF OPTIONS must be served (an unknown member is a filter that cannot find what it was added for); a MAP KEYED BY the vocabulary may be hand-written provided it degrades to a stated fallback (the graph's icon map keeps its unknown glyph).

    THE THROUGH-LINE
    Three of the four were found to have already drifted or already been broken, and in every case the suite was green through it — because the two halves that had to agree lived in different files and nothing compared them. The decoupling is not only about the cost of adding an integration; deriving both halves from one declaration is what turns that class of silent drift into a failing build.

    ## Declared thresholds — a connector's tunable trip points (2026-08-06, ADR 0088, ISE-578..583)

    Every detector has a number in it, and those numbers are what an operator learns after living with an estate for a month. They are now **declared by the connector**, as `sweep_specs()` declares cadences (ADR 0085): `threshold_specs()` returns specs with a label, unit, direction, bounds, the detector they feed, and one or more severity rungs. Core resolves, validates and renders them; one generic card on the System page serves every integration. Adding a threshold touches the connector's own module and nothing else.

    Four rulings worth keeping:

    **1. A threshold says what a signal is WORTH, never whether to act.** ADR 0026 stands untouched: the auto-incident threshold is global, so "high means we act" is true system-wide. A rung carries a severity on the canonical ladder and nothing else — it cannot suppress a signal or gate an incident. The severity-override layer remains the tool for "this matters less here", because it is auditable in a way a quietly-raised cutoff is not.

    **2. Ladders derive by default; declared bands are the exception.** The test is *"should moving one band move another?"* If yes it is one threshold with a derivation in the detector — Freshservice pages at twice its burst count, M365 escalates at a fully-consumed pool, and both declare ONE rung. If no it is a real ladder: EntraID credential expiry (90/60/30/expired) is four calendar lead times for a human to rotate a credential, and an estate with a quarterly change window wants the outer band moved without touching the inner ones. Declaring four knobs where the operator thinks in one is how a config surface becomes unusable.

    **3. A scoping parameter is not a trip point.** Some tunables shape what a detector *measures* rather than what a measurement is *worth* — the Kubernetes rate-guard window ("only churn seen in the last 30 minutes counts"). Those declare no severity. Giving one a rung on the canonical ladder would be a fiction dressed as a severity. A scoping parameter can never be a ladder, and asking one for a severity raises rather than returning nothing.

    **4. Declared must mean visible.** The ISE-537 lesson generalised: a setting that defaults invisibly is indistinguishable from one nobody implemented. So the card shows every effective value AND whether it is the connector's default or a choice somebody made, and the effective value (or whole ladder) is echoed into the observation's `details`, so a signal read months later carries the numbers that produced it.

    ### Where the boundary sits (settled 2026-08-06)

    **The threshold mechanism owns numeric trip points. Per-connector config owns everything else.** Freshservice keeps its own card and endpoints for ticket scope, the AI-adjudication switch and `requester_email` — lists, a boolean and an address. Widening ThresholdSpec to carry those would rebuild the per-connector config surface under a new name; the numbers are the part that generalises. **A connector may legitimately have both a generic thresholds card and its own config card** — that is the intended shape, not a leftover.

    Also new, and the first thing this made possible: **EntraID now warns before an app registration's secret or certificate expires** (one observation per registration at its worst rung). ADR 0030's Kubernetes rate guards, shipped as explicitly provisional with no way to refine them, are tunable per cluster for the first time.

    Canon addition pending — the interface capability matrix (2026-08-07, ISE-596).

    Recorded in full as ADR 0090 (`docs/decisions/0090-interface-capability-matrix.md`), formalising the "ISE Role Matrix" memo. The Canon concept to fold into the body:

    **The interface capability matrix.** ISE has three surfaces where a human meets its AI — Assist (read-only estate Q&A), the Incident Screen (in-app investigation and remediation), and Claude Code over MCP (deep investigation, ADR 0055). Capability is a property of the SURFACE; the role is a second, independent axis. Effective capability = interface ceiling ∩ role. Every role may use every interface — no surface is role-gated as a surface; the role decides what you can do there, not whether you may enter.

    - Assist: reads everything, writes NOTHING, executes read-only integration functions (the Evidence catalogue). It has no propose/approve/execute path of any tier — absent, not disabled.
    - Incident Screen and Claude Code: read everything, write the incident log only, execute Evidence, and propose through the governed tier gate (ADR 0017). Claude Code additionally carries BreakGlass for holders of the grant (ADR 0089).

    Three rulings that fix where the lines fall:
    1. Proposals sit under gated Execute, not Write — creating a ProposedChange is the front half of the execution gate, not a domain write. This is what keeps the Write column crisply "incident log only".
    2. Write means DOMAIN writes; ISE's own audit/telemetry exhaust is excluded (pulling Evidence writes a mandated credential_accessed row, ADR 0018, and that does not breach Assist's "Write: None"). Otherwise the column would be a lie about every surface.
    3. BreakGlass changes who approves, never what exists.

    And the principle that made it structural rather than documentary: **read parity is derived, not listed.** Tools carry a tier in one registry; each surface declares the tiers it gets.     ## Integration Packs (ADR 0094, Sprint 48 — released 2026-08-08)

    **A read-only integration can be a document rather than code.**

    The third rung of the integration ladder, after the bespoke connector (ADR 0014/0027) and the generic MCP Evidence Type (ADR 0031). A **pack** is a versioned YAML document an admin uploads in Settings; core interprets it, and the source becomes an Integration Type in the add-integration picker with no ISE release. Authoring reference: `docs/briefs/integration-packs.md`.

    **Why it is possible at all.** Look at what the eight REST connectors actually do on their read path: build a client with auth from a very short list, page a list endpoint by one of four idioms, honour a 429 once, and read a handful of fields out of each item. Only that last step is per-source — and it is *data*: "the id is at `$.id`, the severity comes from `$.priority` through this table". A thing that is data should be expressed as data. Everything above it was the same code eight times over.

    **The four rules that make it safe, and they are structural rather than reviewed:**

    1. **A pack contains no executable content.** No expressions, templates, scripts, author-supplied regexes or arithmetic. Every field is a literal, a choice from a menu core defines, or a path selector into a JSON document. This is why the auth and pagination menus are *closed*: an "auth: custom, here is how to sign it" escape hatch is a scripting language wearing a hat, and it would move the safety argument from structural to review-based overnight. A source that does not fit gets a menu entry added to core through CI, or gets a connector. That is a worse day for one integration and a much better decade for the platform.

    2. **A pack can never produce an action.** Not "does not yet" — cannot. There is no pack field that would populate a catalogue. An ActionSpec carries a risk tier and a reversibility claim, and both are human judgements about real blast radius that ADR 0017 guarantees were made by a person and reviewed at PR time. A tier written by whoever authored the YAML is not that judgement; accepting one would not weaken the tiered model, it would *end* it, because from that moment "T1" would mean "someone said T1".

    3. **Rung-1 vocabulary only.** Entity types, edge types and severities map onto the canonical lists; an unmappable value is an install-time error, not a sync-time surprise. A pack-minted type would render as a blank chip nothing could filter on and would fragment the estate along a boundary no screen expresses. `other` is the honest answer.

    4. **Observations are excluded too**, for a quieter reason worth keeping: an Observation carries ISE's own *confidence* about a source it is reasoning over. A pack defers entirely to what its source states — it has no judgement of its own to express, so it produces Alerts and only Alerts.

    **Everything downstream is unchanged.** A pack's entities go through `reconcile_discovered` and its alerts through `reconcile_findings` → promotion, exactly as a hand-written connector's do — identity harvest, tag pool, ignore rules, severity overrides, the auto-incident threshold. Nothing downstream knows a pack was involved, which is the whole reason packs map *onto* the existing contract rather than beside it.

    **Costs accepted, recorded rather than discovered later:**
    - Packs are runtime artefacts (DB rows, `connector_type` = `pack:<key>`, built-ins always resolve first so a pack can never shadow one). Installing one never runs a migration — a pack that could migrate could break an upgrade, which would put back the release cadence the whole thing exists to escape.
    - Resolution is a process-local cache with a ~30s TTL, so an installed pack goes live across API and workers within about half a minute rather than instantly.
    - **A wrong pack produces wrong entities rather than none**, and unlike a bad connector it was reviewed by nobody. Mitigated by install-time validation and the fail-closed `source_of_record` default, but it is real, and it is the price of the release cadence.

    **Packs and connectors coexist permanently.** A source with actions, a non-JSON transport, a register-shaped read path, or ISE-authored Observations still gets a connector. Packs take the long tail, which is where the volume is. Every source that does not fit is a signal about which menu entry to add next — the escape hatch would have hidden that signal and traded it for an unbounded review burden.

    ADR 0027 §6 (out-of-process integrations behind a versioned contract) remains open: packs are interpreted *in* core, deliberately buying most of the benefit without paying the contract-versioning tax.

    Evidence-from-a-pack, dry-run preview and the pack update/remove lifecycle are Integration Packs II (sprint `syte7bx`). The `evidence:` section is reserved and v1 rejects it with a pointer — a declared-but-unfetchable capability would put a broken promise on the System detail page, since ADR 0031 §2 made capability the thing the UI degrades by.

    ## Integration Packs II — evidence, the dry run, and the one State-toggle exemption (Sprint 49, released 2026-08-08)

    Completes the pack story begun in ADR 0094. Three additions to the Canon, and one of them changes a rule that had no exceptions.

    **Evidence from a pack, and who writes the schema.** A pack may declare on-demand read queries, which become the integration's evidence catalogue for incident investigation and MCP. The decision worth keeping is that **core generates the parameter JSON Schema** from a small closed declaration (name / description / `location: path|query` / `required` / `type`) rather than letting the author ship raw schema. ADR 0031 §3's self-describing catalogue only means anything if what the agent is *told* and what the server *enforces* are the same artefact; author-supplied schema would be a surface core never validated. Undeclared parameters are refused at fetch time, not merely discouraged in the schema.

    This also introduced **the only interpolation a pack has**: `{placeholder}` substitution in an endpoint path. It is substitution, not templating — every placeholder is enumerated at install time and must be backed by a declared path parameter (and the reverse, since an unslotted parameter would be silently dropped and fetch the wrong thing), and the value is percent-encoded with `safe=""` so it cannot add a path segment, climb out of one, or reach a different endpoint. A parameterised endpoint may not feed an `entities`/`alerts` mapping or the health probe, because sync has no argument to supply. §1's "no executable content" is intact: the substituted value comes from a schema-validated argument, never from the document.

    **THE DRY RUN, AND THE FIRST EXEMPTION ADR 0072 HAS EVER HAD.** A pack is unreviewed content — nobody signed off the mapping the way a reviewer signs off a connector — and a wrong pack produces *wrong* entities rather than none. The dry run is what pays that cost down: run the pack read-only against the live source, using the *same* mapping functions sync uses, and report what it would mint. Persist nothing.

    It runs on a **disabled** integration. ADR 0072 §1 says `enabled` gates every path "without exception" and that "it is only a read is not an argument". The exemption was taken deliberately and written into ADR 0072 rather than left as a quiet precedent, because requiring `enabled` defeats the feature outright: the operator would have to switch the integration on — and let it sync, writing entities — before they could see what it was about to write. A trust step that runs after the thing it gates is not a trust step.

    The distinction that resolves it, and the one to reach for if this ever comes up again: ADR 0072 was written against **ISE acting on a system's behalf on its own schedule** — its three worked examples are a sweep that kept sweeping, an owed notification, and an approved change firing later, all autonomous or deferred. The real line is not read-versus-write (§1 is right that the status-page bug settles that) but **autonomous background work versus a synchronous inspection that persists nothing**. The exemption holds only while the dry run persists nothing, is synchronous, is admin-only, is audited, and cannot be in flight when the toggle flips. A *scheduled* preview would not be covered and probably could not be justified.

    **Removal stands integrations down; it does not refuse.** Reversing the cautious first cut: a pack you cannot remove without first deleting its integrations is a pack whose removal costs you the estate history attached to them. Removing a pack (or switching its Type off) switches its Integrations off, leaves them in place saying why, and lets their entities **age out through the ordinary estate lifecycle** rather than tearing them down. Retirement is a judgement the lifecycle already makes well, and re-installing inside that window puts everything back. `Connector.provenance()` now carries the pack version into the sync audit, because a pack can be replaced between two syncs with no release — without it, "which mapping produced this entity?" has no answer once the document has moved on.

    **A gap the conformance check found, which was not about packs at all.** Verifying that pack sync/detection/evidence obey the State toggle exposed the same flaw in the *shared* evidence path: listing evidence sources filtered on `enabled`, but **fetching** loaded the system by id and never re-checked it. A switched-off integration stayed readable to any caller already holding its id — an earlier listing, an incident, or a model that guessed — on both the AI tool surface and MCP. That is exactly the shape §2 exists to prevent ("the dispatch query filters, the unit of work guards"), with only the first half present, and it affected every connector. The general lesson: **conformance-checking a new feature against an old rule is a good way to find where the old rule was never finished.**

    **Option B is proved.** ISE-508's acceptance test was written to be failable — author a real integration against a real product from the published spec, and if it cannot be done without touching core then Option B is not done. The GitLab reference pack (`docs/examples/gitlab-pack.yaml`) was authored with **zero changes under `app/`**, and proved against the live API: 200 real gitlab.com projects across two pages mapped with nothing skipped, and real issue payloads producing findings that join to the right project entity. That is the honest answer under ADR 0094 §3 — borrowing `application` or `service` would assert something about the estate GitLab never said — and it needed no code change, so it is recorded rather than fixed. Whether to add a `code-project` type is a question about the canonical vocabulary (ADR 0086) and the estate model, not about packs. Worth noting the pressure arrived exactly where ADR 0094 §1 predicted it would: on the menus, which is where that signal is supposed to show up.

    ## Reports — a frozen query, rendered to PDF on a calendar (ADR 0095, Sprint 58, released 2026-08-10)

    A **report** is a saved question about the estate that produces a document. Four rulings:

    **1. A saved report is a frozen deterministic spec; runs never touch AI.** `query_spec` is a `ReportQuerySpec` whose `where` clause is `attribute_filters.AttributeFilter` verbatim — the same predicate language the sweeps and Assist share, with the same two guards (a `->>` on a missing key is NULL not false; a cast of the wrong text aborts the query). AI may *author* a spec: describe the report in English, an agent drafts it, the operator reviews it in the builder and saves. But **the drafted object IS the saved object**, and once saved nothing about a run consults a model. A report landing in an inbox every Monday is a thing people stop reading carefully, and a number that came from one model on Monday and a different one in September is worse than no number.

    **2. Schedule is a calendar cadence, not an interval.** `{cadence: daily|weekly|monthly, time: "HH:MM", weekday?, day_of_month?}` in the report's own IANA zone. Every other periodic thing in ISE is seconds because those are machine rhythms; a report is a human one, and an interval expresses "07:00 every Monday" only until the clocks change. The arithmetic lives in one pure function: the spring gap fires an hour late rather than skipping the day, the autumn fold fires once on the first reading, and `day_of_month: 31` clamps to the end of a short month rather than skipping February.

    **3. Artifacts go to S3-compatible object storage, config-driven; the chart ships MinIO.** Not the database (an unbounded binary column every `pg_dump` then carries, for data whose whole lifecycle is "keep the last 20") and not a worker PVC (the pod that renders is not the pod that serves the download). Downloads go through an **authenticated proxy**, never a presigned URL — MinIO has no ingress, so a presigned URL names an address the browser cannot reach.

    **4. The run is snapshotted at dispatch.** `report_run.spec_snapshot` freezes `{template_key, field_values, query_spec, report_name}` when the run row is created, so a report edited on Tuesday cannot change what last Monday's PDF claims to be — and the worker's job is pure, never reading the mutable definition.

    Corollaries: PDF is rendered by WeasyPrint in the worker from a sandboxed Jinja2 template (no browser, no ~300MB Chromium fighting the dropped-capabilities securityContext); templates are code-declared behind a single `get_template(key)` seam so DB-stored custom templates extend one function; and **delivery (Teams/email) is deliberately not v1** — a report is a link in the app, and outbound delivery is a separate decision that composes onto a run already producing a durable artifact.

    Also settled here: `attribute_filters` gained a public `sort_expression(key, descending=)` — the same CASE-guarded casts used for ORDER BY, NULLS LAST in **both** directions, because Postgres's default would open a "soonest to expire" report with every entity that has no expiry at all.

*ISE Canon — the core concepts of ISE and how it works. A living reference; concepts are added as they are agreed.*

## The two layers: Signals and Incidents

Everything ISE reacts to falls into one of two layers, and keeping them separate is the central idea.

- **Signals** are *transient* and *machine-owned*. They reflect the current state of a system and come and go on their own as that state changes. There are two kinds — **Alerts** and **Observations**. Nobody has to "deal with" a signal; it is simply present or not.
- An **Incident** is *durable* and *human-owned*. It is the unit of work. Once opened it must be managed through to resolution by a person — it does not disappear just because the signals underneath it did.

The point of the Incident is to **disambiguate the transience of signals**. Alerts and Observations may flap; the Incident holds steady so a human has one stable thing to work, with a full history of what happened underneath it.

A guiding principle sits behind the two kinds of signal: **ISE defers detection to a source when that source has its own detection layer, and detects for itself only where the source does not.** DataDog has monitors, so ISE trusts them (Alerts). Kubernetes has no equivalent, so ISE forms its own judgement there (Observations).

## Record types

### Alert
A pre-defined failure state detected by an integration's *own* monitoring, which has decided a threshold or condition was breached. ISE forwards it rather than re-deriving it. Alerts are created in ISE with the details the integration provides.

- **Intake:** fast / event-driven — read from the integration as its state is polled, so an Alert surfaces as quickly as possible.
- **Identity & dedup:** keyed on the source's **stable identity plus trigger group** — for DataDog, `monitor/{id}/{group}`, never the display name (names collide and can be edited). A *multi-alert* monitor (one definition grouped e.g. `by host`) produces **one Alert per triggering group**: "Agent not responding on Server X" and "…on Server Y" are two distinct Alerts. The group key doubles as the affected-infrastructure entity for the estate knowledge base. A history of occurrences (last triggered, recurrences) is kept on the record.
- **Carries** the source's severity, mapped onto the canonical ladder (see *Severity, confidence & incident thresholds*).
- **Status:**
  - **Triggered** — currently firing.
  - **Recurring** — has triggered before within its lifetime window (lifetime configurable in settings).
  - **Recovered** — stopped firing on its own.
  - **Ignored** — a known false/unwanted alert; occurrences are still recorded but it stays suppressed and never opens or reactivates an Incident.
  - **Resolved** — *derived*, never set directly (see *Signal resolution & suppression*).

### Observation
An anomaly or issue ISE itself detects while checking an integration that has no detection layer of its own. This is ISE's *opinion*, so it is inherently lower-precision than an Alert and carries an ISE **confidence** ("how sure") alongside its severity ("how bad").

- **Intake:** the **Obs Loop** (below), on a slow schedule — and additionally gathered on demand while investigating an Incident.
- **Dedup:** by event *and* affected infrastructure (the estate entity); a record per observation keeps a history of when it was seen.
- **Carries** an ISE-assigned canonical severity and a confidence (see *Severity, confidence & incident thresholds*).
- **Status:**
  - **New** — detected for the first time.
  - **Recurring** — seen before within its lifetime window (configurable in settings).
  - **Recovered** — went away on its own / not seen again.
  - **Ignored** — known and unwanted in the queue; still recorded, never opens or reactivates an Incident.
  - **Resolved** — *derived*, never set directly (see below).

### Signal resolution & suppression
A signal's **Resolved is never set directly** — it is *derived* by cascade when its Incident is resolved, so "fixed" has a single source of truth.

- **Normal path:** signals go green (Recovered) → a human Resolves the Incident → the signals read Resolved.
- **Early-resolve path:** a human Resolves an Incident while its signals are *still firing* → those signals are forced to Resolved too.
- **Re-assertion:** if a Resolved signal is reported again, that is a fresh trigger → it **Reactivates** the Incident and the signal returns to Triggered/Recurring.
- **Escape hatch:** to stop a persistent/known signal from reopening, set the *signal* to **Ignored** — the durable suppression.

Consequence: a *continuously* firing signal will bounce straight back after an early-resolve (it re-asserts on the next poll), so early-resolve only "sticks" against a persistent signal if it is also Ignored. This is intended. The only two direct human actions on a signal are **Ignore** and adjusting its severity (see below); everything else about a signal is machine-driven.

### Incident
A unique, durable investigation of related Alerts and/or Observations. The Incident is the timeline of what happened, who did what, and when.

- **Opened by:** an Alert (automatically, above the threshold); a *severe, high-confidence* Observation (automatically, above the threshold); or a person, manually, from any signal.
- **Correlation (ingest):** one signal → at most one *open* Incident. A firing Alert either opens a new Incident or attaches to the existing open one for that signal; recovered-and-re-triggered signals re-attach rather than spawning duplicates.
- **Correlation (investigation):** related signals across the estate are added during the targeted investigation. Where several Incidents turn out to share a root cause, **ISE proposes a merge and a human accepts or rejects it** — merging is never automatic, because it is a judgement that needs the estate knowledge base.
- **Resolution is human-owned:** a signal clearing is a *hint* ("Recovered"), never an automatic close.
- **Severity escalates, but never de-escalates.** *Agreed 2026-07-22.* A live Incident follows its signal *upward*: when the signal's effective severity rises above the Incident's, the Incident is re-graded and the change is recorded on its timeline. It never follows the signal back down. The asymmetry is the whole design — escalation is *information* ("the estate is worse than this record says", and saying so late is worse than saying so loudly), whereas de-escalation would be a *judgement*, and judgement about how urgent something is belongs to the operator. A symmetric rule would also reintroduce flapping through the back door: a monitor oscillating Warn↔Alert would swing the Incident's severity, and its place in the queue, on every sync — precisely what the two-layer split exists to prevent. Consequence to read correctly: an Incident's severity records **the worst the estate got** during its life, not how bad things are right now. Only an Incident nobody has stood down escalates (New / Active / Reactivated); once a human has Resolved or dismissed it, escalation must not half-undo that decision.
- **Status:**
  - **New** — newly created.
  - **Active** — assigned to a person to deal with.
  - **Resolved** — believed fixed; may reactivate if it recurs.
  - **Reactivated** — was Resolved but detected again within the reactivation window.
  - **Closed** — Resolved for more than *x* days without recurring; moves here automatically (*x* configurable). A recurrence after Closed is a *new* Incident. (The correlation key must persist on a Resolved-but-not-Closed Incident so a recurrence can reattach.)

## Severity, confidence & incident thresholds

Every signal is placed on one **canonical severity ladder**, and the decision to auto-open an Incident is made once against it — so the rung means the same thing everywhere.

The ladder: **info < low < medium < high < critical**.

- **Alerts** get their severity from a per-connector mapping of the source's native levels (DataDog: `Alert→high, Warn→medium, No Data→low`). A source's scale is a subset of the ladder — DataDog cannot natively produce `critical`, so a critical Incident can only come from an Observation or another integration. That is the point of normalising: the ladder is a superset of any one source's scale.
- **Observations** are *born* with an ISE-assigned canonical severity ("how bad") plus a **confidence** ("how sure") — two distinct axes.

**Auto-incident policy is global, tuning is local.**
- A single **global auto-incident threshold** on the ladder (e.g. ≥ High) expresses policy: "we act on High and above," true everywhere.
- Sensitivity is tuned not by moving the threshold per integration, but by a **severity-override layer** over the connector defaults: `effective severity = override ?? connector default`. Overrides are **scoped** (per integration, down to signal-type or entity) and **auditable**, and never mutate the connector default (a connector upgrade must not wipe local tuning; history shows "downgraded high→medium by <person>"). *Example: pod restarts in the g5 cluster are semi-normal, so that observation type is overridden `high→medium`; with the threshold at ≥ High it no longer auto-opens Incidents, but is still recorded and available as evidence.* These overrides are the structured *tuning* register of the estate knowledge base (below).

**The open rule:**
- **Alerts** (high-confidence by construction): auto-open if effective severity ≥ threshold.
- **Observations**: auto-open if effective severity ≥ threshold **and** confidence ≥ a global confidence bar; otherwise they remain Observations for a human to promote.
- The threshold governs **automation only** — a human can always open an Incident manually from any signal below the bar.

**Two tools, one gradient:** *downgrade severity* = "keep showing me, keep it as evidence, just don't open an Incident for each one"; *Ignore* = "don't show me at all." Downgrade is the soft, common tuning; Ignore is the hard mute. For this to work in practice, downgrading must be a one-click action *from where the noise appears* (the Incident/Observation in the queue) — tuning as a byproduct of use, like maintaining the estate knowledge base.

**Detector trip points are connector-declared, not hard-coded.** *(Agreed 2026-08-06, Threshold Specs sprint, ISE-578..583.)* Where a deterministic detector compares a measured value against a numeric trip point (licence pool %, ticket-burst counts, k8s churn rates, days-to-expiry), the connector **declares** the threshold — key, default, bounds, unit — via `threshold_specs()`, the sibling of ADR 0085's `sweep_specs()`; core assembles the specs, validates per-System overrides against them, and renders them generically in the UI. Declaring never removes configurability (the spec carries the config key and bounds; the default is a default), and every declared value is **visible** in the app — the ISE-537 lesson that a defaulted-but-invisible setting is a setting nobody knows exists. Nothing here moves the auto-incident line: a declared threshold decides *what a signal is worth*, never *whether to act* — the global open rule and the severity-override layer above apply unchanged. Ladders are normally **derived** from one threshold (burst: medium at n, high at 2n) rather than being independent knobs; the agreed exception is **calendar-band ladders** where the bands are meaningful lead times for human action rather than multiples of a noise floor — the canonical case being app-registration credential expiry: ≤90 days low, ≤60 medium, ≤30 high, expired critical.

## The Obs Loop

The recurring Observation check. It runs on a regular, deliberately *slow* cadence — expensive detection work belongs on a loop measured in hours/daily, not minutes. Configurable in settings: each integration can be opted in or out, and its schedule set independently.

Each pass checks an integration for unusual or anomalous behaviour, records Observations, and captures what it sees as a **baseline of record** — the "normal" that later investigations compare against. It also validates the estate knowledge base against reality, surfacing drift as low-severity Observations. It is mostly *cheap deterministic detectors* (known failure modes) plus context-driven suppression, with AI reserved for genuine novelty — not an expensive model scanning everything, which is the pattern that drains budget.

**Drift watches durable knowledge; placement churn is counted, not reported.** *(Agreed 2026-07-26, ISE-301.)* The drift check raises Observations only for durable knowledge going stale — dependency edges (`depends-on` / `routes-to`) and anything a **human asserted or confirmed**, whose divergence from reality always surfaces. Volatile placement (`runs-on`, discovery-derived `part-of`) never raises drift: on an autoscaled estate nodes recycle constantly, and discovery's set-replacement plus entity retirement already reconcile placement silently — one Observation per vanished placement edge is noise by construction (it once produced 528 of 549 open findings). The churn is still **counted**, not ignored — read as a *rate* straight from Kubernetes' own event aggregation, so no churn store is needed (ISE-301 part 2): a **node-flap detector** raises one high Observation for a still-present node bouncing Ready↔NotReady past a threshold (a cleanly recycled node's object is gone from the cluster, so normal Karpenter churn can never read as a flap), and repeated `FailedScheduling`/`Unhealthy` events escalate from a records-only note to a page past a churn threshold. A generic pod-reschedule rate is deliberately **not** alerted on — consolidation reschedules pods as normal operation, so a raw rate cannot be non-noisy without baselines; faults are caught at their root instead (ADR 0030).

## The Incident Loop

Once an Incident is open, it is worked through a single loop that both *uses* what ISE has learned and *adds* to it. This closed feedback loop is what makes ISE cheaper and sharper with use; it extends the propose → approve → execute remediation loop with a learning bookend at each end.

1. **Raised** — from an Alert, a severe/high-confidence Observation, or a person.
2. **Recall** — cheap retrieval: match the Incident against **memory** (past incident instances with a similar signature/entity — "this looks like last month's connection-pool exhaustion on Kora") and **playbooks** (distilled procedures for this class of problem). Reframes the work from "solve from scratch" to "verify a prior."
3. **Investigate the real state** *(collaborative)* — gather current evidence, directed by knowledge-base traversal and any matched playbook, and test the recalled hypotheses against reality. A prior is a hypothesis to verify, never an answer to run.
4. **Propose resolution** *(collaborative)* — recommend a remediation via propose → approve → execute; default-deny, human-approved (ADR 0017/0021), refinable in conversation (ADR 0024).
5. **Validate resolution** *(collaborative)* — confirm the fix worked. This is the *same mechanism* as the Incident status model: validation confirms enough to **Resolve**; the reactivation window catches regressions; Closed-after-*x*-days-quiet is final validation.
6. **Update the knowledge base** — write back what was learned: the incident instance (automatic history, including *failed* attempts, which are as valuable as successes), any newly-discovered structure/context, and a **playbook** distillation (AI-proposed, human-confirmed — a bad playbook is confidently-wrong advice feeding remediation). Feeds the next Incident's Recall.

**Self-tiering.** Cost and human effort scale with novelty, automatically: a strong memory/playbook match short-circuits — quick confirm, high-confidence proposal, a rubber-stamp approval — while a novel Incident goes deep and heavily collaborative. Compute is spent in proportion to how new the problem is, and **cost per Incident falls as memory grows** — the inverse of a cold-start-every-time system.

**Two failure modes designed against:** *over-fitting to memory* (a new cause wearing a familiar signature) — priors must be rejectable by the investigation, which is explicitly prompted to consider "what if this isn't the usual cause?"; and *human fatigue* — mitigated by the self-tiering above, asking for proportionate involvement.

The three collaborative steps run over the existing chat surface (ADR 0022/0024). What is genuinely new versus today's diagnose → propose → execute → verify is the two bookends — **Recall** at the front and **Update** at the back — which wrap the existing remediation loop in a learning layer rather than replacing it.

### Incident signatures — how Recall matches
Recall turns on a signature, and there are *two*, computed at different moments for different jobs:

- **Trigger signature** — computed at Recall, cheaply, from the signal identity (`monitor/{id}/{group}`, or observation type) + the affected entity/entity-type. Coarse; its job is *retrieval*.
- **Diagnostic signature** — computed after Investigate, from the *cause found* (the failure mode). Precise; its job is *learning* — memory and playbooks are keyed on it.

The split is load-bearing because trigger↔cause is **many-to-many**: one trigger ("agent not responding") can have several causes; one cause (a DB outage) trips many triggers. So Recall matches on the trigger to get into the neighbourhood, and the diagnostic signatures of the priors it retrieves say which causes to check first.

- **Build signatures from stable attributes** (signal type, entity identity, failure mode), never volatile ones (event ids, timestamps, exact counts, time-varying title text). This is the `findings_fingerprint` lesson (ISE-44) — that fingerprint deliberately excludes `last_seen_at`; a volatile signature either never matches (no learning) or matches on noise (false learning).
- **Graded, structured-first matching.** Ranked similarity with a confidence, not an equality test: deterministic structured filters (same signal type + entity type + topology shape) narrow the set, semantic similarity ranks within it. Structured-first keeps Recall cheap and — because a human validates the recall — explainable.
- **Hung off the entity graph.** The backbone is `(signal-type, entity)`, so memory attaches to entities in the knowledge base (Kora carries its own incident history) and Recall pulls priors off the same graph it traverses for evidence — no separate index to keep in sync.
- **Layered by specificity and recency.** Match exact (this signal on this entity) → entity-general (this signal type on this entity type) → class (this failure mode anywhere), weighted by specificity and recency (the estate changes; an old match is a weak hint). Playbooks key on the coarse (class) level; memory on the fine (instance) level.
- **Loose but verified.** The dial runs from loose-match/false-recall to tight-match/no-learning; resolve it by biasing to *loose recall for consideration* and letting Investigate reject. Generous matching is safe because recall never acts — only the human-approved proposal does.

### Playbooks
A playbook is the distilled, reusable form of "how we handle this class of problem" — a *promoted, human-blessed generalisation* over incident memory (which is raw instances, captured automatically).

**Anatomy** (six parts):
1. **Applicability** — the class-level signature (+ optional context conditions) that decides when it fires; what Recall matches against.
2. **Ranked hypotheses** — likely causes and how to tell them apart; turns a coarse trigger match into a directed investigation.
3. **Investigation plan** — the ordered evidence to gather, as *intents* not literal calls. This field *is* the scoped evidence plan that replaces the blind tool loop.
4. **Remediation options** — candidate fixes, each tied to a cause and each a **reference to a governed action** from the connector's `action_catalogue()` (`ActionSpec`, with tier and parameters).
5. **Validation criteria** — how to confirm success; feeds the loop's Validate step.
6. **Efficacy & provenance** — authored-by / derived-from, a live success/failure record, last-used, confidence.

**Structured where it touches governance, narrative where it touches reasoning.** Structured: applicability, action references, validation (matching and governance must be machine-readable). Narrative: hypotheses and evidence intents (guidance the AI reasons with, not a rigid tree). A playbook is **loaded as context that shapes investigation and proposal — never a script the system runs**; "prior to verify" applies at the playbook level.

**Steps are stable intent, resolved at run time.** The investigation plan encodes stable intent ("check node memory pressure on the host running the agent") and lets the AI + estate graph + connector resolve the *how* now — the stable-vs-volatile lesson, so the playbook survives estate churn.

**Judgment, not privilege** *(the key safety property)*. A playbook's remediation options reference the *existing* action catalogue — it introduces no new execution capability and can never propose anything the catalogue + approval gate wouldn't already allow. Governance (default-deny, tiered approval — ADR 0017/0021) is unchanged. Playbooks make ISE smarter about *proposing*, never more powerful about *executing*.

**Advisory playbooks earn standing from feedback.** *(Agreed 2026-07-26, ISE-303.)* A playbook distilled from a diagnosis alone — hypotheses, no catalogue operation — is *advisory*: the executed-op efficacy rule can never score it. It earns standing through a separate feedback ledger (never conflated with proven-fix efficacy): an operator's one-click helped / didn't-apply verdict from Recall (always wins), plus a conservative, positive-only automatic credit when a resolved incident's recorded diagnosis bears its hypothesis out. Recall ranks a remediation playbook by executed efficacy and an advisory one by its feedback standing; helped-false is the advisory anti-rot signal.

**Authoring — crystallised incidents.** Three sources: distilled from a resolved incident (primary/organic — Update proposes, human confirms); authored directly (seed a known class); refined by repetition (each match adds causes, reorders by frequency, updates efficacy). Maturity grows with successful reuse: resolution → candidate → confirmed → matured.

**Efficacy is the anti-rot immune system.** Each application records its outcome (did the hypothesis hold? did remediation pass validation?). Ranking uses the live success rate; a falling rate flags the playbook for review and can surface like drift ("worked 8/10, last three failed since the DB moved to Aurora"). Failed applications are as valuable as successes. Stored in Postgres, versioned with provenance so a bad edit is auditable and reversible.

## Applying the model: DataDog (worked example)

DataDog already runs the "is something wrong?" evaluation continuously, over data ISE never ingests. So:

- **Monitors → Alerts.** Only monitor state produces Alerts, keyed by `monitor/{id}/{group}` so multi-alert monitors split correctly per scope.
- **Metrics, events, logs, dashboards, service map → not issue sources.** They are **evidence, gathered on demand** during an Incident investigation to explain *why* a monitor tripped.

This avoids duplicating detection DataDog has already done and avoids surfacing signals DataDog itself doesn't consider alert-worthy. Contrast Kubernetes: no monitor layer, so ISE detects there itself → Observations.

## Applying the model: AWS (v1 — read-only)

*Decided 2026-07-29 (sprint AWS Integration, ISE-358..363; ADR 0058 to be written with the foundation task).*

- **One Integration instance per AWS account**, authenticated with **static access keys** in the existing envelope-encrypted credential store (a keyless OIDC / Roles-Anywhere path was considered and rejected for now). The platform's read/write credential split maps onto two IAM identities; the write side is reserved for the follow-on actions sprint. v1 declares **Alerts + Entities + Evidence** — the action catalogue is empty.
- **Resources become estate entities:** EC2, RDS, EKS, ELB/ALB, S3, with **account-scoped native keys** (`aws:{account_id}:{arn}`, the ADR 0045 lesson). Two new entity types: `load-balancer` and `bucket`; EC2→host, RDS→database, EKS→cluster. AWS resource tags feed the unified tag pool.
- **Join, don't duplicate.** AWS discovery offers cross-keys onto the entities other integrations already know — EC2 instance → `datadog:host:{instance-id}` and `k8s:node:{node-name}`; EKS cluster → `k8s:cluster:{name}` — so the tier-1 alias harvest merges AWS resources into the existing estate rather than minting a shadow one (the ISE-205 precedent).
- **AWS alerting follows the deferral principle.** CloudWatch alarms and AWS Health events are the source's own detection layer, so ISE forwards them as **Alerts** (keyed on the alarm/event ARN) riding the standard signal lifecycle. Cross-source dedupe/reinforcement is deliberately the *existing* machinery — same-entity attribution plus human-gated "same affected entity" merge candidates — not a new correlation layer. The Health API needs a Business+ support plan, so that slice degrades gracefully where absent.
- **Evidence on demand:** describe-resource, list-resources, CloudWatch metrics/logs, CloudTrail lookup — through the standard Evidence contract, lighting up every investigation surface with no per-surface wiring.

## The Estate Knowledge Base

More than a topology map: the estate model is the shared knowledge base that makes the AI investigator competent in *this specific estate* rather than generically. It carries three registers of knowledge — all of them "what the humans and the environment know that a generic tool does not":

1. **Structural** — **entities** (services, clusters, databases, hosts, namespaces…) and typed, directed **relationships** (`runs-on`, `depends-on`, `hosted-on`, `routes-to`, `part-of`). Each entity has a canonical id, a type, and a set of integration **aliases** — how each connected system names it (`datadog:service:service-x`, `k8s:g5/team-a/deploy/service-x`). Edges carry provenance and a last-confirmed timestamp. Distinct from a `System` (a connected integration instance) — estate entities live *across and inside* Systems.
2. **Contextual** — free-form annotations that change how ISE *interprets* what it sees: behavioural caveats ("this cluster runs Karpenter, expect transient nodes on demand") and business meaning/criticality ("Kora is the company CRM, used across the business, composed of X/Y/Z"). Authored, sticky, loaded as context whenever the investigator reaches that entity.
3. **Tuning** — the severity overrides and Ignores (see *Severity…*), the structured face of the same knowledge.

All three are one idea: **capturing local human knowledge so ISE behaves correctly in this estate.** They act in two registers — *structured rules* (overrides, Ignore) applied deterministically at ingest, and *narrative context* fed into the AI's reasoning during investigation and observation. Both are wanted: structured for the known-and-repetitive, narrative for judgement.

Over time the knowledge base also accumulates **incident memory** and **playbooks** through the Incident Loop — the record of what has happened in this estate and the distilled procedures for handling it. Memory and playbooks are estate knowledge like any other; the Incident Loop is the knowledge base's read/write cycle, which is why the knowledge base is maintained by *working incidents*, not by a separate process.

**Stored in Postgres, not a graph DB.** At estate scale a few tables (entities, aliases, edges, annotations) with recursive queries suffice; a graph DB would be its own ADR and ops burden and cut against ADR 0002.

**Identity resolution** is the crux — deciding two integration names are the same entity — cheapest-first:
1. **Harvest shared keys / cross-tags automatically.** Integrations often already carry each other's coordinates (a DataDog agent in K8s tags metrics with `kube_namespace`/`kube_deployment`; K8s workloads carry `tags.datadoghq.com/service`). Where a shared key exists, resolution is free.
2. **Heuristic candidate-match** where no shared key exists — the AI proposes candidates, a human confirms; never auto-merge on a guess.
3. **Human-asserted aliases** are authoritative and sticky.

**Discovered vs authored.** Existence and placement (`runs-on`, `hosted-on`) are discovered from the integrations and refreshed on a cadence. Semantic `depends-on` edges no integration knows, criticality, context annotations, and corrections are authored and sticky. On conflict, **authored wins and the conflict is surfaced** (the "operator dismissal is sticky" pattern).

**The knowledge base is a cache, and the Obs Loop validates it.** Seeded by discovery, enriched as a byproduct of investigation (resolve-once, persist), and checked by the Obs Loop — divergence from reality ("graph says Service-X runs on g5, but it is no longer there") surfaces as a low-severity Observation. The thing that keeps a CMDB alive — noticing it has drifted — is automatic and rides the Observation machinery.

### Identity: a public hostname can be a native key

*Ruled 2026-08-05.* A native key has so far meant *an integration's own name for a thing* — `k8s:shop/deployment/checkout`, `datadog:service:checkout`. A **provider-assigned public hostname** is also an identity key, carried in a `dns:` namespace (`dns:myapp.azurewebsites.net`).

It is identity rather than an attribute because it has the qualities that make a native key trustworthy: **issued by the provider, globally unique, and stated by the source of record.** Treating it as identity means the existing alias machinery does the join — reconcile already resolves an edge's target through the alias table, so a Cloudflare zone can point a `routes-to` edge at `dns:<cname target>` and it lands on whatever entity claims that hostname. No new matcher, and no second resolution mechanism beside the one the estate deliberately has only one of.

Two consequences, both accepted: two entities claiming one hostname becomes a *merge* path rather than merely an edge path (safe in practice — a provider does not issue one default hostname twice — and a contested key is ignored rather than collapsing entities); and signals resolve on hostnames too, since finding-to-entity linking also goes through aliases.

**The boundary is exactness.** Only provider-assigned, exact, stated strings qualify — App Service `default_hostname`, ELB `dns_name`, AKS `fqdn`. **Not IP addresses** (reused across VPCs and accounts, and the estate stores private IPs, which is not what a public A record points at), and never name-similarity. A weaker matcher, if ever wanted, goes through the proposals queue as a low-authority claim — it does not get to mint identity.

The measured basis for the ruling: 33 zones and 698 CNAMEs over 465 distinct targets yielded **16 exact matches, every one a production App Service**. Sixteen real edges from an exact rule is the argument for exactness — a fuzzy rule would have produced more matches and no way to trust any of them.

### Entity lifecycle: live → retired → pruned

*Agreed 2026-07-22.* Discovery originally only ever created and refreshed entities, so the estate could not tell a live host from a dead one and grew forever on a churning fleet — the other half of the "does it still exist?" question the drift check above only asks about placement.

Every entity carries a **last-seen** stamp, refreshed each time discovery reports it — a distinct fact from "when did anything about it change", because a refresh that finds nothing new is still a sighting. An entity unseen past a window is **retired**: hidden from the estate by default but otherwise whole, its tags, edges, annotations and signal links all intact and still resolving. Discovery reporting it again **un-retires it in place**. That reversibility is what makes the judgement safe to get wrong — an integration having a bad day costs a temporarily-hidden row, not data, which is why retirement rather than deletion does the operator-facing work.

Only after a second, much longer window is a retired entity **pruned**, and pruning refuses anything still bound to an open Incident or carrying a human annotation — authored knowledge is not discovery's to throw away. Its *discovered* dependents go with it; its *history* does not. Signals and playbooks survive with their link nulled, because a record must outlive the thing it was about.

Windows are **per entity type**: transient kinds (hosts, workloads) churn on a timescale structural ones (clusters, namespaces) do not, and one clock for both would either thrash the fleet or never catch the ghosts. Retirement is decided by a slow sweep over last-seen, never inferred from a single sync being complete — one truncated page or degraded source must not retire a slice of the estate.

**Existence and classification read a source's silence differently**, and conflating them is a live bug class. *Any* source naming an entity proves it exists — a monitor scope that merely mentions a host is enough to keep it alive. But only a source that can actually *see* an entity's tags may assert them, so a tag-blind source reporting nothing withdraws nothing. Existence is a low bar that any sighting clears; classification is a claim only an observer may make.

**Maintained through conversation, not forms.** The AI is the interface, over the chat surface:
- **Query** — "what does Kora depend on?", "what runs on g5?" (read-only).
- **Validate** — "is it right that Service-X depends on Database-Z?" — the AI shows its assumption, the human confirms or corrects.
- **Enrich** — "Kora is the CRM, built from these services…" — the AI turns natural language into structured graph updates.

Enrichment is a **write**, but of ISE-internal metadata, not infrastructure — so it does *not* need the tiered-action governance (ADR 0017/0021). It is audited (provenance/authored-by) and confirmed ("I'll record that Kora is the CRM and depends on X/Y/Z — confirm?"): a distinct, lightweight write class kept separate from remediation. Keeping the graph accurate is therefore a conversation, not a chore — which is the real answer to CMDB rot.

**Why it earns its place.** The estate entity id is the **join key across everything** — an Alert's affected entity, an Observation's affected infrastructure (its dedup key), and the evidence gathered during investigation all resolve to the same entity. And during investigation the knowledge base turns blind exploration into **directed, bounded traversal**: resolve the affected entity, walk typed edges to what it runs on / depends on / is depended on by (blast radius), and hand the investigator a scoped evidence plan instead of many exploratory tool round-trips. That directedness is a core part of the cost story.

## The three layers of the estate: Resource, Application, Business Service

*Agreed 2026-08-02 (Sprint 45 design review).* The estate as built is a flat resource inventory — entities of many types, with no statement of what they add up to. Three layers name what an operator actually reasons about, and give an alert somewhere to land that is neither a host nor nothing.

**The layers, and the dependency direction.** Business Service → Application → Resource.

- **Resource** — infrastructure that exists. A server, an RDS instance, an EBS volume, a cluster, a Kubernetes Service, a DNS zone, an EntraID app registration. The physical or virtual compute, network and storage, plus the platform objects that configure them.
- **Application** — a deployed software capability that can be consumed, by a person *or by another application*. Chinwag, Kora, an API, a gateway, Twingate. Not touchable, and not the source code that builds it. Defining it by *consumption* rather than by "a thing a user interacts with" is deliberate: a VPN, a DNS service and an API gateway are Applications, and a definition resting on a user interface excludes them.
- **Business Service** — what a customer pays to consume: a telephone answering service, live chat. Notional rather than pointable-at, composed of one or more Applications. **An Application is never a Business Service**, even at one-to-one — collapsing them is what dissolves the model back into a flat list.

**Who owns the truth is what separates the layers.** Resources are **discovered** — an integration enumerates them, refreshes them, and can retire them. Applications and Business Services are **asserted** — no API owns their existence, so a human declares them. That single distinction decides how each layer is maintained and where rot can enter, and it is why the layers are a model rather than a display grouping.

**Naming discipline: "service" is always qualified.** The word arrives from every platform meaning something different, so it is never used bare. **Business Service** is the top layer; a **Kubernetes Service** is a Resource; a **DataDog APM Service** is DataDog's view of an Application. Vendor-qualified names need care wherever the vendor name can precede a generic noun — "DataDog Service" is ambiguous between the product and the APM concept, so the product is just **DataDog** (itself an Application ISE does not operate) and the concept is a **DataDog APM Service**.

Existing entity types carrying the collision, to be resolved:
- **`application`** currently holds EntraID **app registrations**, which are identity objects an integration owns — Resources. They become `app-registration`; *Application* is reserved for the middle layer.
- **`service`** holds both DataDog APM services and Kubernetes Services, which sit in different layers and must split.
- **`third-party`** is not a layer. Cloudflare, Twilio and Twingate are Applications; **external-ness is an attribute — who operates it — not a type.**
- **`workload`** is a Resource (below).

**Each integration declares what it is a source of record for.** AWS for AWS resources, Kubernetes for cluster objects, EntraID for identity objects, Status Pages for external Applications — because nothing else will ever tell ISE that Twilio exists. **DataDog is a source of record for nothing**, and neither is Freshservice: DataDog holds Monitors and Alerts, and neither is a thing in the estate. Its identifiers become **aliases on entities other sources own**, never entities in their own right. This is the observation-versus-record line — an observation source knows only what happens to be instrumented and reporting, which is a partial and fragmented view of the world, and promoting that to a statement about what *exists* is what fills an estate with opaquely-named half-entities (246 DataDog hosts, 73 of them named by raw instance id or UUID, at the time this was agreed).

**Unknown assets.** When an alert arrives against something no source of record claims, the alert and any Incident are still created and flagged as an **unknown asset** — but **no placeholder entity is minted**, which is the pollution this section exists to design out. The flag is a temporary state, not a label: when the account, cluster or server is finally integrated, the existing back-fill re-links the alert to the real Resource with its incident history intact. Gaps are deduplicated by the identifier the source used ("4 unknown hosts, 17 alerts", never 17 orphans), which turns the integration backlog into an evidence-backed list — and later becomes the detector for infrastructure appearing outside the accounts ISE knows about.

**Terminology.** *Entity* remains the technical umbrella in the model, the API and the code; user-facing surfaces use the layer names now that those are precise. A generic word is genuinely needed in exactly one place — an alert whose subject cannot be identified — and there "unknown asset" reads plainly.

**A Kubernetes workload is a Resource.** The case for promoting it to an Application instance rests on a one-to-one correspondence that does not exist: an Application is realistically several workloads — a web deployment, a worker, a scheduler, possibly the same set again in a second region — so workloads map **many-to-one** onto Applications, and promoting them would still require an Application concept above to group them. That builds the middle layer anyway *and* mislabels the Resource layer. Two supporting reasons: a cluster is full of workloads that are plainly not Applications (cert-manager, external-secrets, agents, operators), and deciding which of them count is itself a human assertion; and promoting them would make Applications discoverable on Kubernetes but asserted on VMs — one Application with two provenances, one of which the retirement sweep could quietly delete.

**The Application→Resource edge needs its own type.** It is *composition*, not placement. Reusing `runs-on` would inherit that type's exclusion from drift checks and from the impact walk, silently breaking the very rollup the layer exists to provide.

**Applications are the stable anchor, and they are seeded one proposal at a time.** A tag pattern proposes a whole Application at once — "workloads tagged `app:chinwag env:prod` suggest `Chinwag.Prod`, composed of these three" — so one confirmation covers many Resources rather than asking per workload. The payoff is stability: workloads recycle constantly and the Application does not, which makes it the right anchor for the things that must attach to the most stable subject available — incident memory, playbooks, annotations — and the layer a **DataDog APM Service** and a **synthetic monitor** both resolve onto. A synthetic is not an alert missing an entity: it observes an *outcome*, which is an Application-layer fact, and forcing it onto the load balancer or ingress it happens to traverse would blame one component for a fault that could be anywhere along the path. A synthetic red while every component is green is precisely what a resource inventory can never tell you.

**A Resource may serve several Applications, so Application→Resource is a relationship, not an attribute.** A tag can seed it; it cannot express many. This is the reason to build the layer at all: a shared database going red is three Business Services impacted, and severity becomes contextual rather than fixed.

**A monitor is a rule; an alert is an instance.** A fleet-wide monitor ("high CPU on any VM") has no subject *as a rule*, while every alert it fires does — it fired *about* a specific host. So resolution matches on what the alert fired **about**, never on what the monitor is scoped to. An alert that genuinely names no subject belongs to the integration or a group, and saying so is honest rather than a failure.

### Environments: two independent dimensions

There are two environments wearing one word, and the model only holds if nothing infers one from the other:

- **Infrastructure environment** — which platform tier the kit sits in, and by extension its change-control regime (`sandbox` / `staging` / `production`). A property of the Resource.
- **Application environment** — which stage of the software lifecycle an instance serves (`dev` / `test` / `demo` / `prod`). Part of the Application's identity.

A Demo instance on production-grade infrastructure is **correct**, not an anomaly — you want the customer-facing demo on reliable kit. Dev and Test co-tenanted on one staging cluster is equally normal. So a Production cluster legitimately hosts `Chinwag.Prod` and `Chinwag.Demo` while a Staging cluster hosts `Chinwag.Dev` and `Chinwag.Test`, and neither environment is derived from or validated against the other.

**Infrastructure environment is stated at the platform root and inherited downward by containment.** A cert tagged `app:chinwag env:test` does not state where it lives; it lives in a namespace, in a cluster, and the cluster carries the infrastructure environment. That containment chain is already in the graph, so the cert's infrastructure environment is *staging by location*. Things that **are** the platform — a cluster, an account, a standalone EC2 — state it themselves, because nothing above them can.

Two consequences: **the containment root must be tagged, and that is the single point to enforce** (four untagged clusters is an actionable list; four thousand untagged resources is not); and the inherited value is **derived on read, never stamped onto each Resource** — copying it down would just create another thing to go stale. Where no containment path reaches anything that states it, report it as unknown rather than guessing.

*Correction to an earlier formulation:* "a Resource shared across environments is a finding" is wrong as stated — a cluster serving both Prod and Demo is normal. The real detector is **customer-facing sharing with non-customer-facing** (a Prod Application and a Dev Application on one cluster).

Both of those detectors need one thing recorded: **whether an environment is customer-facing is a property of the environment vocabulary**, not a judgement re-made per Business Service. That is what turns "there are no test Business Services" and the sharing check from opinions into things ISE can verify.

### Naming

- **Application** — presented everywhere as `app.env` (`Chinwag.Prod`). The estate is always mixed, so an unqualified "Chinwag" is ambiguous exactly where it matters — incident titles, impact rollups, search. A name that *sometimes* carries the environment is worse than one that always does. Stored as **two fields with the dotted form derived**, never as a string: listing all Production Applications, listing all Chinwag instances, and validating the environment against the governed vocabulary all require it to be a field, not something parsed out of a name.
- **Business Service** — no environment, so just its name.
- **Resource** — named by its **source of record**. This is where the DataDog demotion pays off twice: a quarter of today's hosts are called `i-0abc…` or a raw UUID because DataDog is naming them and DataDog only ever had the instance id. Two supporting rules: **scope for display comes from the containment graph, not the string** (`checkout` in `shop` on `prod-uk` — names are not unique, and baking scope into the name repeats the native-key mistake); and **never invent a name, but always render type and scope**, so an untagged volume reads as "EBS volume vol-0abc… in Staging" rather than a bare identifier.

Source-of-record naming **retires the existing rule that only renames an entity while a single integration knows it**. That rule existed because ISE had no way to decide whose name should win; declaring sources of record settles it.

### Tagging: how the layers are derived

Everything above the Resource line is derived from tags resolving through the Tag Dictionary, which makes the mapping exercise and the tag-hygiene exercise the same work.

**Three roles, bound to dictionary keys by explicit selection.** The *roles* are structural — the model depends on there being a tag that names the Application, one that says platform-owned versus application-owned, and one that carries environment. *Which canonical key fills each role* is configuration, seeded as `app` / `project` / `env` but bound rather than baked. Aliasing is not sufficient: an estate that uses `platform` for the platform role **and** `project` for something else entirely cannot be served by aliasing `platform` → `project`, which would corrupt a real key. Exactly one key per role; a role may be unset, and ISE says so plainly rather than silently deriving nothing; the bindings are shown in a visible panel rather than discovered by accident while editing a key; and rebinding is audited and warned, because it re-derives Application membership across the estate.

**One `env` tag at source; its dimension is resolved by its sibling.** `app:` present → the environment is an *application* environment. `project:` present → an *infrastructure* environment. The discriminator already exists in the tag set, so nothing needs re-tagging and nothing is expressed twice to drift apart later.

**Canonical value lists are dimension-scoped.** `prod = production` stays aliased exactly as it is — people use them interchangeably and always will, and re-tagging every resource ever created to fix that is an endless project. The same raw `env:production` therefore canonicalises to application `prod` beside `app:`, and to infrastructure `production` beside `project:`. One alias set, two homes, and the whole problem stays inside ISE's resolution layer where it is one dictionary change.

**Compliance shifts accordingly.** The load-bearing rule is **"every Resource carries exactly one of `app` or `project`"** — unlike environment values, that is unambiguous, checkable and fixable, and every other derivation keys off it. A weak value cross-check survives for the values that genuinely do not cross over (`demo`/`dev` are not infrastructure environments, `sandbox` is not an application environment); it will never catch prod/production and should not try.

**An unknown tag key raises a proposal**, not just a coverage gap. Nothing unlisted maps silently, so an unrecognised key surfaces for confirmation and re-resolves deterministically once accepted.

**`impact` is an ordinary governed key**, not a role — an input to Business Service rules and otherwise shown on the entity alongside its other tags.

### Applications are entities: authored existence, derived membership

An Application has to be a real entity, not a derived view over a tag query. Annotations, incident memory, playbooks, severity overrides and the Business Service composition above all need a stable id to attach to, and a query result has no identity across time — correct the tag and the "Application" silently becomes a different thing with no history.

The lifecycle splits cleanly:

- **Existence is authored.** A tag pattern *proposes* an Application; a human confirms; the confirmation creates the entity. Asserted, but nobody types it from scratch.
- **Membership is derived.** Continuously computed from tags and maintained by machine, exactly as tag-rule groups work today, on `rule`-provenance composition edges.
- **Never retired by discovery** — the treatment `group` already has. If every Resource under an Application disappears that is an **Observation**, because only a human knows whether it is a broken sync, a deployment gap or a decommission. Removal is an explicit, audited human act, and the Application's history survives it.
- **A new `app:` value nothing claims raises a proposal**; rejection is remembered so it is not re-asked.

**The Application stores its own membership predicate.** Without that, renaming `app:chinwag` to `app:chinwag-web` silently forks it into a new Application and orphans the original's incident history. With a stored predicate, a tag rename is an *edit* to an existing Application.

Reuse the tag-rule machinery — predicate matching and membership-edge maintenance are identical and should not be rebuilt — but an Application is **not** a `group`. It is a typed layer with environment in its identity and Business Services above it: same mechanism underneath, distinct type and distinct screen.

### Sources that carry no tags of their own

Tags reach ISE three ways, and the third is missing:

1. **Harvested from the source** — AWS, Azure, Kubernetes resources carry their own tags.
2. **Asserted per entry at registration** — the registers, where a human adds the row and tags it.
3. **Integration-level defaults** — "everything this integration contributes carries these tags." **Does not exist for any integration**, and it is what a continuously-arriving source with no register needs.

Where the registers stand (verified 2026-08-02):

- **Status Pages** — the template, and the only one that carries tags all the way onto an entity: page tags are set at registration, editable afterwards, and pushed onto each tracked-service entity through the integration's own tag slice. Tagging the Cloudflare page `app:cloudflare` is what resolves its service entities to the Cloudflare Application.
- **Confluence documents** — register with tags, edit afterwards. Documents reach the estate by tag resolution rather than becoming entities, which is the intended design.
- **GitHub repos** — partial. Registration applies **one shared tag set to the whole ticked selection**, and there is no per-repo tag edit in the UI; the endpoint exists but nothing calls it, so giving one repo a different `app:` tag means re-registering the batch.
- **Freshservice tickets** — nothing. There is no register: tickets stream in and become signals, which inherit the ticket's own arbitrary Freshservice tags. This is the case that needs integration-level defaults.

## Collections: Groups, Business Applications, Business Services

*Agreed 2026-08-13 (Collections sprint, ISE-677..682).* Three things in ISE answer one question — *which parts of the estate do I want to reason about together?* — and they sat in three unrelated places: a Settings tab and two mid-list nav entries. **Collection** is the collective noun for a **Group**, a **Business Application** and a **Business Service**.

**It is an umbrella term, not a rename.** Each keeps its own name, its own URL and its own entity type; nothing is `/collections/*`, no table or API path changed, and the three are not interchangeable — they differ in exactly the way the layers section above describes. What the word buys is a place to put them (one nav section, between the operator's daily screens and the integrations that feed them) and a reason to draw them alike. Making it a real supertype in the model would be a different decision and would need its own ADR.

**A Group belongs with the other two, not with settings.** A group is *asserted operator knowledge about the estate* — the same kind of statement as a Business Application, one rung below it — not a configuration knob like a credential or an AI ceiling. Filing it under Settings said the opposite. It is the lowest rung because it collects Resources directly, where the two above collect what has already been collected.

**Collections are drawn as one kind of thing on the canvas.** A squarer box and a single shared colour for all three, against the pill-shaped blue every Resource wears. The rule underneath it: **on the graph, colour says WHAT a node is** — not where it sits, not what you clicked. That rule replaced a "root is gray" convention which had been harmless while colour meant nothing and became a lie the moment it did: the same Business Application appeared in two colours depending on which one the operator had rooted on. Focus is now said without a hue (a ring, a heavier border, a bolder label), which is the general form of the principle — *one visual channel, one meaning*.

Two consequences worth stating because both look like bugs and are not:

- **The root of a graph never folds.** Every node in a response hangs off the root, so collapsing it would fold the whole canvas into a single box. Collapse puts a *branch* away; the root is the thing being looked into.
- **An externally-operated `application` is not a Collection.** It is somebody else's Application — an asset ISE observes, not a way of gathering assets — so it stays a Resource-coloured pill. It had shared the Business Application glyph on the reasoning that they are the same shape of thing told apart by who operates them; once one became a Collection and the other did not, the shared glyph made the pair read as one type drawn two colours. **Two things must not share a glyph across a boundary that a colour now draws.**

## Integrations & Connectors

An **Integration Type** is a connector — the code that teaches ISE to work with a kind of system. A **developer** builds and tests it; it declares a set of capabilities and is released like any other code. An **Integration** is a configured instance of a Type: an **admin** supplies credentials and connects it to a specific target (this cluster, this DataDog account) and sets instance options (Obs Loop schedule, scoped severity overrides). **Users** then interact with what it surfaces. The bright line: **anything with a coding element is a developer's job; instantiating a tested Type is an admin's; everything else is a user's** — no muddy middle. In today's code these are `connector_type` (the registered class) and `System` (the configured instance).

**Capabilities (declared, optional).** A Type declares which it provides, and the platform degrades gracefully by capability:
- **Alerts** — poll the source's own detection layer → Alert signals (native levels mapped onto the canonical ladder).
- **Observations** — run ISE's detectors where the source has no detection layer → Observation signals (severity + confidence).
- **Entities** — enumerate entities, their native keys and observable edges → estate knowledge base.
- **Evidence** — on-demand read queries during investigation.
- **Actions** — the governed remediation catalogue (`ActionSpec`, with tier and reversibility).
- **Documents** — fetch registered narrative documents from their source of truth (see *The Document Register*).
- plus lifecycle: credential spec, health check.

DataDog declares Alerts + Entities + Evidence + Actions (it detects for itself); Kubernetes declares Observations + Entities + Evidence + Actions (no detection layer); Confluence declares Documents alone. A source may declare *both* Alerts and Observations (e.g. AWS: CloudWatch alarms + raw config).

**Two kinds of capability, two kinds of reuse.** *Semantic* capabilities (Alerts/Observations/Entities) map source concepts onto ISE's canonical model — reuse is a shared contract shape plus a small per-source mapping, not shared code. *Tool* capabilities (Evidence, Actions, Documents) are "give the AI access" and can be provided generically — e.g. a generic MCP-backed Type. Governing principle: **the more governance a capability needs, the less generic it can be** — read-only Evidence generalises cheapest (and fits the ADR 0023 read-only boundary); governed Actions carry irreducible per-source classification (the `ActionSpec` tier/reversibility). Reuse in practice: one Kubernetes Type serves any cluster (each cluster is an Integration); a monitoring Type shares a capability *shape* across vendors with thin per-vendor mapping; a generic MCP Type provides Evidence (and, with per-action classification, Actions) for many sources.

**End-state: integrations as independently-deployable modules.** The target is for an Integration Type to be an **out-of-process service behind a versioned contract**, deployed and removed on its own cadence (its own Helm chart / immutable image) without a core release — the registry becomes a runtime registry of *endpoints*, not import-time classes. MCP is the ready-made mechanism for the tool capabilities (Evidence/Actions), directly realising ADR 0014; the semantic capabilities need a richer versioned contract and are more work. Two non-negotiables keep this real, not illusory: integrations talk to core **only through the versioned contract, never the shared database** (or schema changes force plugin releases); and **authorization stays in core** — a plugin executes an already-approved action, it never self-authorises (preserving ADR 0017/0021). The permanent tax is **contract versioning** — "add without a core release" holds exactly as long as the contract is stable. This is a platform-extensibility goal, downstream of the cost-critical work, and staged: MCP tool-capabilities first, the semantic-capability contract later.

### A connector declares itself; core never learns about it

*Agreed 2026-08-05.* The target is that adding an integration touches the registry line and nothing else. Four places made that false, and each had the same shape — **knowledge about a connector living in a module with no other business knowing it**.

- **A connector declares its own summary card.** The System detail page carried a bespoke "at a glance" card per integration: an endpoint, a guard, a response schema and a React component each. The one screen whose entire purpose is to be generic over integrations had to be edited to learn about every one of them. A connector now returns *labelled sections* and one component renders them. Three constraints keep it safe: it declares **meaning, not appearance** (closed sets of semantic tones and icons), so the design system can restyle every card at once; it takes **no connector context**, so a summary structurally cannot cost a round-trip to the source on page view and still renders for a system whose credential has expired; and it **never sees a Session**, so the estate model stays free to move underneath every connector. Six endpoints, four guards, eight schemas and five components deleted — the API surface *shrank* by ~1,100 lines.
- **Tag writeback is declared, not mapped centrally.** A central map of `{connector_type: operation}` plus a native-key-parsing branch per connector became a declaration on the action itself. This caught a live bug: Kubernetes retags built `kind: "deployment"` while the action's own schema accepted only `Deployment`, so **every Kubernetes tag correction had always been refused by its own validation** — with a green suite throughout, because the mapping and the schema lived in different files and nothing compared them.
- **A connector declares its own sweep cadence.** Each polling sweep needed both a schedule entry and a worker registration, and the two fail *differently* when forgotten: a missing schedule means the sweep silently never runs; a missing registration means the task is discarded as unregistered, with no run and no error anyone sees. Both now derive from one declaration, so declaring a sweep **is** registering it.
- **A canonical vocabulary is served, never hand-copied.** The entity-type list was mirrored into three frontend files, each with a comment claiming it mirrored the backend, and nothing checked. They had already drifted — the kind-dictionary editor was missing a type, so a Kubernetes Secret CRD could not be mapped to the very type that had been added for it. It is now served as an enum that rides the API snapshot, so the types check reddens on staleness. The distinction to carry forward: **a list of options must be served** (an unknown member is a filter that cannot find the thing it was added for), while **a map keyed by the vocabulary may be hand-written** provided it degrades to a stated fallback.

**The through-line.** Three of the four were found to have *already* drifted or already been broken, and in every case the suite was green through it — because the two halves that had to agree lived in different files and nothing compared them. So the decoupling is not only about the cost of adding an integration: **deriving both halves from one declaration is what turns that class of silent drift into a failing build.**

### Servers: agentless, and ISE runs the automation itself

*Ruled 2026-08-05.* The server fleet joins the estate **agentless**, and **ISE runs Ansible itself** — never through an external execution layer. A task template in someone else's tool is a mutable black box, which would make ISE's tier declarations fiction: the tier says what an operation risks, and it cannot if the operation can be edited elsewhere. For the same reason there is **no run-command or run-playbook primitive, ever** — every operation is a pinned, ISE-authored playbook call.

Agentless inverts discovery: **inventory is an input, not an output.** The server register is the definitive fleet list, and a coverage reconciler audits it against every source that happens to know about machines (cloud VM inventories, directory device records, hypervisor guests), raising gaps through the proposals queue with dismissal and exclusion rules as the noise defence. Registration **binds to the existing entity, never mints a duplicate** — a cloud VM already in the estate stays one thing.

The capability split follows the standard connector shape: an identity-facts snapshot is the liveness sighting, everything else is on-demand Evidence; keys join on hostname; detection is Observations only, since there is no native detection layer to defer to. Every write operation is **T2** — deliberately not the cheaper tier a cloud instance action gets, because a server that does not come back is a site visit. Nothing is ever installed on a target.

## Knowledge sources & authority (Relationship Mapping)

*Added 2026-07-22 (Sprint 20 design). How the knowledge base's facts come to exist, how much each is trusted, and how conflict and decay are handled.*

**The four sources.** Everything ISE knows about the estate arrives through one of four sources, ordered by how rigid they are:

1. **Declared — tags.** Standardised key attributes stated at source (`env:prod`, `service:kora`, `role:database`) by whoever configured the thing. Authoritative in intent and self-maintaining (sync set-replacement withdraws what a source stops asserting), but only as consistent as the humans typing them — `env:prod` / `env:Prod` / `env:production` coexist today. The **Tag Dictionary** (below) is what makes them the fixed points of truth they should be.
2. **Deduced — integration structure.** What ISE works out from knowing how a platform actually works: pod-1 runs in namespace-a; a Service's selector routes to its workloads. Deterministic, refreshed by discovery, drift-checked. Depth honestly varies by integration: Kubernetes is rich; DataDog is a flat list whose structure must be recovered from its own tags (`kube_node:` → node cross-keys) and, where APM exists, the service-dependency map. Connectors declare what they can deduce (capability contract, ADR 0027).
3. **Learned — incident experience.** Causal knowledge found by working incidents ("this RDS instance broke, which took the Kora web UI down"). Captured at the Incident Loop's Update step as *proposed* structure (`depends-on`, resolution `ai_proposed`) that a human confirms — never auto-asserted; one incident is weak evidence, recurrence strengthens. Learned edges attach to the most stable subject available (the service, not the transient node it happened to be on).
4. **Authored — narrative context.** Human-provided documentation: annotations today, plus the **Document Register** (below) — live documents (runbooks, architecture notes) registered from their source of truth and scraped on a cadence. Consumed twice: as summarised AI investigation context, and mined into *proposed* structured claims that go through the confirm pipeline. A document is a source like any other — its extracted claims carry its provenance and are withdrawn or re-reviewed when it changes or disappears. Its *statements* are unverified narrative until confirmed, which is why documents sit lowest in authority even though the scrape keeps their freshness known.

**Everything is a claim with provenance.** Every fact — a tag on an entity, an edge, a group membership, an annotation, a statement extracted from a document — is a claim carrying *source* (which integration / document / incident / person), *method* (harvested / deduced / rule / ai_proposed / asserted) and *freshness* (first seen, last confirmed). This exists in fragments already (edge/alias `resolution`, `entity_tag.system_id`, `last_confirmed_at`, entity last-seen per ISE-206); Relationship Mapping generalises the model rather than inventing per-source machinery.

**Authority = method × freshness.** When claims conflict, ISE uses this order, freshness modulating within a tier:

1. **Human-asserted** — sticky; a fresh observed contradiction surfaces for re-confirmation, it never silently overrides a human.
2. **Currently-observed declared & deduced facts** (tags, discovery) — self-refreshing, so currency is knowable.
3. **Rule-derived** (groups) — deterministic consequences of tier 2.
4. **Incident-learned proposals** — until confirmed (confirmation promotes them to tier 1).
5. **Document-stated** — until confirmed.

So a current hard tag ("host xyz is the database") beats a stale document ("the app database is called abc") — by construction, not by special-casing.

**Conflicts are surfaced, never silently resolved.** Authority decides what ISE *uses*; the disagreement itself is kept and shown — a conflict flag on the entity, and for material drift an Observation (the existing drift machinery). Verifiability is provenance made visible: every fact rendered in the UI shows who says so, by what method, and when last confirmed — that is how a second person checks it is correct.

**Decay and pruning ride the source.** Each claim is withdrawn by the thing that made it: sync set-replacement for tags; discovery refresh plus the entity lifecycle (retire → prune, ISE-206) for deduced structure; document change/removal for extracted claims; recency-weighting for incident memory. Human assertions persist until a human retracts them (audited). Nothing lingers without a live source or a human signature behind it.

### The Tag Dictionary

*Agreed 2026-07-22.* The governance layer that turns raw tags into a standard vocabulary. It is to tags what aliases are to entities: many raw names, one canonical identity, explicit provenance on the link.

- **Standard keys.** A defined list of canonical keys (`env`, `service`, `cluster`, `role`, `team`, …), each with **aliases** (`env` ← `Env`, `environment`) and a **description** — the description exists for the AI as much as for people: it is how the investigator knows what `role:` means in this estate.
- **Values are `defined` or `open`.** A defined key carries a standard value list, each value with its own aliases (`prod` ← `Prod`, `production`) and description; an open key (`service:`) accepts any value, synonyms still mappable. Users can add to, edit, and delete from the standard lists — the dictionary is theirs, not shipped dogma.
- **Mapping, never rewriting.** Raw tags stay in the pool exactly as reported; a mapped tag points at its canonical (`canonical_id`, the entity-alias pattern). All matching — tag rules, groups, Tag Cloud heat, impact rollups — resolves through the canonical; all display shows the canonical with the original in the provenance tooltip ("`env:prod` — reported as `env:Prod` by DataDog"). Unmapping is a clean undo.
- **Dictionary aliases apply deterministically at ingest** — an alias listed in the dictionary *is* the confirmed mapping, so it resolves without ceremony. Only the truly weird (`pr0d`) escalates: a deterministic detector (case-fold, punctuation variants, seeded synonym table) plus AI for the long tail proposes candidates into the proposals queue. Nothing unlisted maps silently. A confirmed mapping is an audited human assertion about vocabulary; confirming one re-evaluates rules and groups deterministically.
- **Coverage expectations** per key declare which entity types should carry it ("hosts and workloads carry `env`"). The **compliance report** shows coverage %, values resolving only via alias, and values that exist in no dictionary — per integration, so "DataDog hosts are 40% missing `env`" is visible, assignable work. Coverage is measured over the entities an integration *knows* (its aliases), never the entities it has *tagged* — the latter drops the untagged host from its own denominator and reports 100% while half the fleet is unlabelled, which is the exact failure the report exists to catch. ISE never writes tags back to the source; fix-at-source proposals through the governed Actions layer are a recorded future model (ISE-210), not in scope.
- **Screens:** dictionary editor + review queue in Settings → Tags (admin); compliance/hygiene view on the Tag Cloud page (all users).
- **Seeded, then sanitised.** Ships seeded with the known keys and common synonym sets, and with value mappings proposed from the estate's actual pool; cleaned up in use.

### What the tag pool holds, and what the cloud says about it

*Agreed 2026-08-14; built as Sprint 65 (ISE-716..720).* The Tag Dictionary governs what a tag **means**; these are the rules for what gets into the pool at all, and for how the cloud reports it.

- **A tag earns its place if an operator could ever name its value.** That is the test, and it is deliberately *not* cardinality. Per-revision hashes and the `kubernetes.io` control-plane domains were the original exclusions; node-provisioner bookkeeping (`karpenter.*`, `eks.amazonaws.com`), injector state, package and chart metadata, and opaque machine-minted identifiers (`aws_ec2_fleet-id`, `kube_node`, backup timestamps) joined them. A one-value-per-entity key is **not** junk by that fact alone: `crossplane-name:kora-db` is precisely how a Business Application rule names a database. Ruling on cardinality would have thrown away a governed predicate — the first cut of ISE-719 did exactly that, and three tests caught it.
- **The rescue list is how a meaningful member survives a machinery family** — `app.kubernetes.io/name` and friends, and `karpenter.sh/nodepool` / `eks.amazonaws.com/nodegroup`, which are groupings a human defined and named rather than shapes a provisioner recorded. **A namespaced key is not machinery just because it looks like it**: `tags.datadoghq.com/service` is unified service tagging an operator sets deliberately, and a live group rule matches on it.
- **Before excluding a key, enumerate its consumers in code — reading the data is not enough.** `karpenter.sh/nodepool` is the precondition of the shipped node-recycling playbook, and no test would have caught its loss; the deny would have produced a green suite and a playbook that could never match. The live rule tables showed no conflict because the rules that happened to exist did not exercise what the code supports. **Data shows what is used today; the grep shows what is supported.**
- **The cost of a junk tag is not noise, it is a stolen slot.** Only ~5% of the estate's tags carry any alert in a week, so the cloud's ranking goes flat after its first level and most of its 200 slots are decided on entity count alone. Autogenerated machinery wins those every time — which is how `admission.datadoghq.com/enabled` outranked `mp-geo:uk`, a key the org deliberately applies. Deny-list changes need **no migration**: reconcile is set-replacement per (entity, system), so the links go on the next sync and the orphaned pool row is already excluded as dead.
- **The cloud encodes two variables on two channels.** **Size is `entity_count`** — how much of the estate wears the label, the structural, slow-moving fact, scaled so the word's *area* is proportional to the count. **Colour is `alert_count`** — how much it is hurting in the window, the volatile fact, log-normalised because alert counts are wildly skewed. One scalar on both channels left the variable that decides most of the ranking with no visual encoding at all. The heat ramp runs blue→red over five rungs, with monotone lightness across the whole ramp rather than a pale neutral midpoint — these marks are **text**, and a conventional diverging ramp would make mid-heat tags near-invisible.
- **Sort and search are server-side, because the cap is applied by the same `ORDER BY`.** The cloud returns at most 200 tags, so the ranking chooses *which* tags exist as far as the screen is concerned. A client-side reorder reshuffles the same 200; a client-side search narrows them. Both leave everything the ranking excluded exactly as invisible — which is how naming a real tag ranked 220th of 2,279 produced *"No tag matches that filter"*, a **wrong answer rather than a truncated one**. The general rule: **a filter applied downstream of a cap answers a different question from the one asked.**
- **The scales are computed before the search, not from its results.** Both denominators come from the top of the unfiltered ranking, so a tag keeps the colour and size it had in the cloud it was searched out of. Deriving them from the matches would make the first tag anyone searched for render as the hottest and widest thing in the estate.
- **A truncated view states the size of what it truncated.** "200 of 200 tags" was true of the response and a lie about the estate. The footer counts against the pool under the same filters; with the true total stated, the truncation notice explains the *rule* and names the controls that reach the rest. An operator who cannot see that most of the pool is hidden reads sort and search as decoration.

### The Document Register

*Agreed 2026-07-22; built ISE-219/220, ADR 0042.* Narrative documentation as a first-class, synced knowledge source — the fourth source made real.

- **The source of truth stays where it lives; ISE scrapes it.** Live documents are kept in Confluence. A document is registered in ISE by **URL + plain-text description + tag list**, and ISE fetches it on a regular cadence — nobody has to remember to copy documentation in after editing it. The scrape gives documents what tags and discovery already have: ISE knows when a document changed and when it disappeared. (Confluence is the first document source; the fetcher is a connector **Documents** capability, so other sources can follow.)
- **Tags link documents to the estate.** The document's tag list resolves through the Tag Dictionary to the entities and groups carrying those tags — tag a runbook `service:kora` and it rides along wherever Kora is investigated, with no manual entity links to rot. There is deliberately **no document→entity link at all**: a hand-made one is correct on the day it is made and rots silently after, where a tag-resolved one follows the estate as the estate changes. The description tells the AI (and people) what the document is for.
- **Consumed twice.** (a) *As context:* the AI maintains a short structured summary per document, refreshed when the scrape sees a change; summaries ride into investigations touching a linked entity by default, and a `read_document` tool pulls full text on demand — spend proportional to need, the evidence-on-demand philosophy. (b) *As claims:* on change, extraction proposes structured facts (edges, tags, aliases) into the proposals queue, each citing the passage it came from — confirming is reading a sentence, not a runbook.
- **Change is what costs, and change is defined narrowly.** The summary and the extraction both run *only* when a re-read finds the content actually different — never on a clock — so an estate that never edits its runbooks pays nothing after the first scrape. "Different" means the text, not the source's version token: a version bump with identical prose is a re-render, not an edit, and treating it as one would buy a paid re-summary on every no-op save.
- **Lifecycle rides the scrape.** Content change → summary and extraction re-run and *diff*: statements no longer made are withdrawn (unconfirmed) or flagged for re-review (confirmed — a human signature survives its source, never silently). Page gone → the same rule applied to the whole document at once. The source's own last-modified feeds freshness; a long-unchanged document is presented to the AI as aged, not as current truth.
- **Only a successful read may withdraw anything.** A failed fetch or a failed extraction diffs nothing at all. Treating "the source was unreachable" or "the model was unavailable" as "the document no longer says this" would quietly withdraw the estate's claims on an outage — the highest-consequence mistake available here, and the reason a deleted page (a fact about the source) and a timeout (a fact about the network) are distinguished rather than merged.
- **A document cannot invent infrastructure.** Extracted claims are resolved against entities the estate already knows; a claim naming something unknown, or a name two entities share, is dropped rather than guessed. The queue is only worth reading if everything in it is about something real.

### The proposals queue

*Agreed 2026-07-22.* One place where "ISE thinks it learned something — confirm?" lands, regardless of source: tag-mapping candidates (Dictionary), document-extracted claims, incident-learned edges, AI identity matches. Filterable by source; one-click confirm/reject with the citation or evidence alongside; **its own nav entry** — it is operator work, not admin configuration. Confirmation is the act that promotes a claim to a tier-1 human assertion; rejection is remembered so the same proposal does not return.

A claim is identified by **its own content, not by the row** — so the same claim raised twice strengthens one queue item instead of opening a second, and a claim already settled is never re-asked. That single choice is what buys detector idempotency and durable rejection together.

The queue answers a second question for document claims: not "is this true?" but **"is this still true?"** — a confirmed claim whose source stopped saying it is flagged for re-review rather than withdrawn. The only answer offered inline is *still true*; retracting means removing the edge or tag the confirmation created, and that belongs on the entity's own screen where the reviewer can see what else it touches.

### Impact & what-if

*Agreed 2026-07-22.* The rollup lands on the **incident "Affects" panel first** — the screen where "which Services does this hit? prod or test?" is actually asked — with the entity page as the second view of the same data. Both are views over one deterministic reverse traversal of the durable edge graph (walk incoming `depends-on` / `routes-to` from the affected entity), so the speculative form — **"what would happen if X failed?"** — comes almost free: the same query bound to any entity, as an impact preview on the entity page and as a chat question the AI narrates over. No AI is needed for the answer itself.

**Containment is not consequence**, and the walk must not conflate them: a node failing takes the workloads on it, but a workload failing does not take the node, so `runs-on` and `part-of` are excluded from the upward walk. Groups are read separately, as context rather than as blast radius.

Storage doctrine restated for this: every fact is a durable row — entities, edges, tags, documents, extracted claims. A confirmed document-derived edge is an ordinary `entity_edge` row distinguished only by provenance; unconfirmed proposals never join the graph. A what-if view may show unconfirmed proposals as visually-distinct hints ("a runbook claims billing-api also uses this — unconfirmed"), never mixed in as fact — the conflicts-surfaced principle applied to absence.

## Webhook Events (pushed context)

Every other integration is one ISE *pulls* from; Webhook Events are the reverse — an external system *pushes* a fact at ISE. A known event happens in the world (a release ships, a change is applied, a job runs) and the system that did it tells ISE, rather than ISE discovering it.

Decisions (Sprint 22 planning, 2026-07-25):

- **A fifth information source.** Webhook events sit alongside the four existing analysis sources — synced connector state, native signals, the estate knowledge base, and on-demand evidence — answering the question none of them can: *what did someone deliberately change, and when?* Motivating scenario: an alert fires for Chinwag crashing; analysis surfaces the Chinwag release event received an hour earlier.
- **Sources are pre-registered.** A webhook source is created in Settings and issued its own secret-token endpoint (Slack-style unique URL per source). Per-source identity, revocation and rotation; no open endpoint, no shared key.
- **ISE defines the schema.** Senders conform to a small ISE event schema (title, level, event type, outcome, status, alert key, entity hint, timestamp, detail) — predictable for the Events screen and for AI consumption — with the raw payload preserved verbatim. Adapters for vendor formats are a possible later addition, not the native model.
- **Both wirings into analysis.** A bounded recent-events summary is auto-included in incident analysis (events touching the affected entity's names/aliases first), and a read-only lookup tool lets investigation surfaces dig further on demand.
- **Events are data, never instructions.** The same untrusted-content posture as evidence and documents: event content informs, it cannot direct.
- **Visibility is first-class.** Events get their own top-level screen (nav entry, list + detail) — the pane-of-glass surface, not just an AI input.
- **Levelled events; alert-level events raise Signals.** *(Agreed 2026-07-25.)* Every event carries a `level` (info / warn / alert). Info and warn are pure events; an alert-level event *additionally* raises an ordinary Alert signal — the sender is a source with its own detection layer, so ISE forwards its verdict, per the deferral principle. This is the cheap path to DataDog-style alerting for systems with no supported integration. The per-source level→ladder mapping, the severity-override layer and the global auto-incident threshold apply unchanged — no new promotion machinery. Identity is `source + alert_key` (schema field, defaulting to event type) so a re-fire attaches rather than duplicates; an optional entity hint resolves against estate aliases (matched → the signal joins the graph; unmatched → a signal without an entity, never an invented one).
- **Recovery is told or timed, never observed.** The push-source problem: ISE cannot poll the sender to watch an alert go green. A `status: recovered` event with the same `alert_key` clears the alert, and a per-source TTL fallback auto-recovers alerts from fire-and-forget senders after a window of silence — both, because the sender population spans smart and simple.

### Webhooks are core application, not an integration

*Agreed 2026-08-04 (functional testing, ISE-539).* An **integration** is ISE reaching into an external system of record — credentialed, synced, health-checked, bound by a connector contract. A **webhook source** is none of those things: it is ISE's own front door, a token an operator mints so outside senders can push events in. It belongs to the core application, beside the event layer it feeds.

The boundary had blurred in both directions. The synthetic System backing each source's alerts (the plumbing that gives webhook signals severity overrides and dedup) leaked into Settings → Integrations and Overview as an apparent peer of Azure or EntraID — with constant fake health, a decoy State toggle, and orphaning if its source was deleted — while the managed event-display sources belonging to polled integrations leaked onto the core Webhooks page.

The rule: whatever plumbing webhook signals need may exist in the schema, but **nothing webhook-shaped is ever presented as an integration, and nothing integration-owned is ever presented as an operator webhook**. Settled deliberately ahead of the integration-decoupling work, so that the pack registry's definition of "integration" is built on the clean boundary rather than inheriting the smear.

## Dashboards

*Agreed 2026-07-25.* Wallboard dashboards are the estate seen from across the room: two levels — **Services**, then **Components** — coloured green, orange or red and readable at a distance.

A dashboard **Service** is one or more existing group entities (tag-rule-backed groups compose) plus a rule set, split into a Warn (orange) and an Alert (red) section. A rule is either *"N or more assets with `<severity>`-or-worse signals"* or *"`<signal title regex>` with `<severity>`"*, the regex validated at save time. Alert takes precedence over Warn.

Each section carries an **auto-clear** toggle, and switching it off is what makes service status *stateful*: the status **latches** when triggered and stays until an operator clears it by hand (audited, operator role). Status is therefore a persisted row per service — level, latched flags, triggered/cleared timestamps and who cleared it — written by a periodic evaluator, never computed inside a GET.

Two rules keep the colour honest:

- **Green is the absence of warn and alert, not a detected state.** A service whose groups resolve to zero entities shows grey/unknown — never green. A board that reports "fine" because it is looking at nothing is worse than a board that admits it cannot see.
- **Signal scope is Alerts and Observations joined to member entities**, with findings from the synthetic webhook System excluded outright: webhooks have no reliable all-clear, so a latching service fed by them would stay red for ever. "Present signal" is the standard definition — unresolved, not silenced, not ignored — so silencing a signal removes it from dashboard maths, while an **acknowledged incident keeps its colour** (acknowledgement means eyes-on, not less severe).

**Components** — the second-level board — are the union of the service's group members, each coloured by its own worst present signal. No per-component rules: the rules live at the Service level, and a component simply shows what it is carrying.

**Multiple boards** *(agreed 2026-08-07, Multiple Dashboards sprint, ISE-608..610 — amends ADR 0053's cardinality only)*: the single implicit wallboard generalises into **named boards**. A board is a named, ordered arrangement of existing services — board↔service is many-to-many, so a service (groups + rules + latched status) is defined once, evaluated once, and placed on any number of boards with a per-board order; the driver is one team wanting topical walls (Prod, Infra), not per-team isolation. Per-board curation is placement: removing a tile from one board touches no other, and a service on no board still evaluates and surfaces in the curation UI. A wallboard token is scoped to **one board** (the evolution the token model reserved); deleting a board revokes its tokens. Existing installs migrate everything onto a default board "Main" so live TV URLs keep showing the same tiles. One token may instead **rotate** through several boards at a chosen dwell time — the one-TV answer to topical boards. Not a widget system: the tile/rule/latch model is unchanged.

**Sources, and what a thing rests on** *(agreed 2026-08-12, ADR 0099, ISE-671..676 — amends ADR 0053 §§1-3)*: a tile no longer points only at groups. It points at **sources** — a group, a **Business Application** or a **Business Service** — which cost almost nothing to add because all three are estate entities and the join was always an FK to `entity.id` (no `source_type` column is stored: `entity.type` is the answer, and a copy would drift). The reason it had to happen: the alternative was authoring a tag-rule group that duplicates a Business Application's membership in a language that cannot express the same thing — a group ANDs predicates, a Business Application unions rules — so the two drift and the wall goes confidently wrong about something ISE models correctly one screen away.

The decision with teeth is that **a Business Application's derived dependencies colour the tile, exactly like its members**. Dependencies are computed on read (ADR 0096 §5) and are deliberately outside the membership *count* — but a wall does not ask "how many members are affected", it asks "is this OK", and a Business Application whose only database is dead is not OK. Members and dependencies are therefore one evaluated set under the unchanged rule language. Rejected: members-only (green through a dead database — the same failure as a green empty board, better disguised), an amber cap on dependencies (teaches the team that amber means outage), and a per-tile opt-out (two tiles for one Business Application disagreeing is worse than either answer). **Accepted consequence, stated rather than tuned away: one failing shared cluster reddens every tile above it** — the estate telling the truth about a shared dependency, the same fact the impact walk reports in the other direction.

A **Business Service evaluates entities, not its children's colours** — the union of its Business Applications' members and dependencies, re-evaluated by its own rules. Rolling up levels would let a Business Service and its Business Application disagree about one failure, and would leave the asset-count rule with no assets to count.

Two consequences carried into the build: **grey must say which emptiness it is** (no sources / an empty group / a Business Application whose rules match nothing / a Business Service composing nothing — a bare emptiness reads as a broken screen), and the components board splits into **Members** and **Depends on**, each inferred row saying how it was reached, in the same words the blast radius uses. Evaluation cost is the real constraint — the dependency walk is one traversal per member on a ~30s beat — so resolution is memoised per Business Application within a pass, **in-process only**: a persisted dependency cache would reintroduce exactly the staleness derivation exists to avoid.

**A dashboard tile is a Tile** *(agreed 2026-08-13, ISE-679 — naming only; the model is unchanged)*: ADR 0053 called the unit of a board a "service", and once a tile could point at a **Business Service** the composer read "New service" directly above a "Business Services" option group — one word for two different things, in adjacent controls, on a screen the naming discipline exists to protect. To a user the unit is now a **Tile**. The API, the table and the `service` identifiers deliberately did not follow: a contract rename costs a migration and a client regeneration to say something no user reads, and the mismatch is recorded in the code so it reads as a decision rather than a miss. **What a thing is called to a user and what it is called in a contract need not agree for the collision to be gone.**

## Voice escalation and on-call

*Agreed 2026-08-04.* The attention ladder gains a rung above the Teams card. A bot cannot send an urgent or repeating Teams message, which caps how hard ISE can pull at someone's attention; the rung above a card is **a phone that rings**.

Voice is **PSTN via Azure Communication Services**, explicitly *not* Teams calling. Both Teams-client routes — a Graph calling bot, and ACS→Teams VoIP interop — can only ring a running Teams client and are unreliable on Teams mobile. The person a voice escalation exists for is precisely the one away from their desk, so a channel that requires them to be at it answers the wrong question. The Teams bot stays notification-only; ACS arrives as its own integration, and `acs-voice` as a second channel kind — which finally forces the kind→poster registry the notification layer always implied.

**On-call rotas are a first-class domain**: ordered members, simple rotation, overrides. The contact number lives on the **membership**, not the person's directory record — the individual controls which device rings, and a directory `mobilePhone` is prefill only. Deliberately *not* a PagerDuty clone: no layered schedules, no time zones, no iCal. A rota is a **destination resolved at delivery time**, which is what lets it serve Teams cards before any calling exists at all.

Acknowledgement amends the notification layer's fire-and-forget stance: escalation is a per-incident **state machine** — announce → wait → call → walk the chain — driven by the scheduler and halting on acknowledgement or resolution. The rule that matters on PSTN: **answered is not acknowledged.** Voicemail answers calls. The human signal is an explicit keypress, and it is in v1 rather than deferred, because without it the system cannot tell a person from an answering machine.

Contact numbers are PII: on the redaction list, and logs name the person, never the number.

## The AI interaction model: three pillars

*Agreed 2026-07-25 (Sprint 24 — AI Interaction Review; ISE-263 map / ISE-264 audit / ISE-265 catalogue, plus the requirements discussion). The judging frame is the operator's: cost vs benefit per incident. The failures found: AI spend scaled with estate size rather than incident difficulty, and the surface with dialogue (chat) was denied reach while the surface with reach (diagnose) had no dialogue.*

1. **Conversation-first investigation.** Issue-chat is the primary investigation surface: it can look anywhere read-only (stored state, estate graph, on-demand Evidence), the operator steers it mid-stream, and it commits structured findings to the record. A diagnosis is what a good investigation session *produces* — the `commit_diagnosis` route — with the single-shot diagnose run retained as the one-click convenience, not the primary path.
2. **Cost proportional to difficulty.** Every question starts with the cheapest sufficient answer and escalates only when inconclusive. Self-resolution — the common case — is deterministic before it is agentic: "has the signal recovered?" is answered from the DB with zero model tokens (cheap-verdict-first). Context is **pulled, not pushed**: no force-fed estate block; the agent fetches the bounded, hub-summarised neighbourhood when the question needs it. Run token caps are runaway guards, not cost controls — the fix for a run hitting the cap is to shrink what it assembles and re-carries, never to raise the cap; per-task-type caps are set from measured numbers (per-stage token instrumentation), a recheck never sharing a full investigation's budget. The guard counts **fresh tokens** (`total − cache_read`): cached re-carry is the legitimate, cheap bulk of a tool loop, so only fresh assembly reads as runaway (ISE-294).
3. **Zero-cost retrieval.** The mechanical work of surfacing relevant information must not cost AI tokens. The retrieval contract — and the integration contract for every future source (webhooks, IAC repos): **comprehend once at write time** (cheap-to-read forms computed at ingest — the document-summary pattern generalised); **find in the database** (indexed, ranked search as deterministic tool calls); **read shortlists** (small, truncation-honest results the model drills into by choice). The model's budget is spent reasoning about evidence, never locating it.

Boundary decision recorded with the pillars: **the chat boundary is a WRITE boundary** (amends ADR 0023's framing). Chat may not mutate ISE or the estate — enforced by the read-only DB session — but read-only Evidence pulls are permitted (side-effect-free by contract, ADR 0031), and chat may write to ISE's own record in the governed loop-driver pattern (messages, enqueued runs, committed diagnoses). Nothing here weakens the hard line: no agent, on any surface, ever executes a mutation.

**The MCP surface advertises only what is registered.** *(Ruled 2026-08-06, from the ISE Test Plan review; implemented as ISE-584.)* `describe_resources` is a contract, not a roadmap: two design-brief capabilities — `propose_change` and desk-executable playbook runs at responder tier — were advertised in its role blurbs without existing in the tool registry. The ruling: `propose_change` is registered for real (opening the governed propose → tiered-approval path to Claude Code, with every app-side guard — catalogue validation, tier resolution, protected targets, connector guards — unchanged), and desk-executable playbook runs are **de-advertised** — playbook runs stay app-only. Nothing on the MCP surface may claim a capability the registry does not carry.

## The interface capability matrix

*Agreed 2026-08-07.* There are three places a human meets ISE's AI — **Assist** (quick read-only estate Q&A), the **Incident Screen** (in-app investigation and remediation), and **Claude Code over MCP** (deep investigation). Capability is a property of the **surface**; the user's role is a second, independent axis. Effective capability is **interface ceiling ∩ role**.

**Every role may use every interface.** No surface is role-gated as a surface — the role decides what you can *do* there, not whether you may enter. Any signed-in user may mint a personal MCP token, and that token's role **can never outrank its owner**, so a senior user may deliberately mint a down-scoped one.

| Interface | Read | Write | Execute (read-only integration functions) | Propose / approve / execute changes |
|---|---|---|---|---|
| **Assist** | Everything | **None** | All (Evidence catalogue) | — |
| **Incident Screen** | Everything | Incident log only | All (Evidence catalogue) | Through the tier gate |
| **Claude Code (MCP)** | Everything | Incident log only | All (Evidence catalogue) | Through the tier gate, plus BreakGlass for grant holders |

"—" means the capability **does not exist** on that surface. Assist has no propose, approve or execute path of any tier — absent, not disabled.

Three rulings fix where the lines fall:

1. **Proposals sit under gated Execute, not Write.** Creating a proposed change is the front half of the execution gate, not a domain write. This is what keeps the Write column crisply "incident log only" rather than smearing it.
2. **Write means *domain* writes.** ISE's own audit and telemetry exhaust is excluded — pulling Evidence writes a mandated credential-access record, and that does not breach Assist's "Write: None". Otherwise the column would be a lie about every surface, and a lie in a security document is worse than an omission.
3. **BreakGlass changes who approves, never what exists.** The action catalogue is still the wall.

**And the invariants are structural, not documentary.** A matrix that is merely *described* decays: read parity across the surfaces was once a hand-curated list per surface, and Assist silently fell four read tools behind with a green suite, because the test asserted what its list *was* rather than what it *ought to contain* — an allow-list can only ever do the former. Tools now carry a **tier** in one registry and each surface declares the tiers it gets, so a read tool added anywhere arrives everywhere that reads, and Assist's containment is the fact that **no acting tool is reachable from it**. Where a surface has its own registry with its own names (MCP), parity is kept by an explicit equivalence map that must have an entry per read tool — so adding one *forces* a decision about that surface instead of quietly leaving it behind.

## Breakglass

*Agreed 2026-08-06 (ADR 0089, Proposed; ISE-591/592).* During a major incident the tiered-approval wait (ADR 0017) competes with the engineer's **direct access** to the broken systems — if ISE is slower than ssh, the fix happens outside the pane of glass with zero audit trail. Breakglass keeps the emergency inside ISE: it **bypasses the waiting, never the machinery**.

- **Request in Claude Code, arm in the app.** A pinned, breakglass-granted user requests over MCP; nothing arms until they approve it on the incident screen in an SSO'd app session (reason + duration required, max 120 min). The interactive login is the step-up ceremony — self-approval is deliberate, and a stolen MCP token can request but never arm.
- **Armed:** the user's proposals auto-approve, stamped `approved_via: breakglass` — still full ProposedChange rows through the catalogue, tier resolution and governed executor. T3 restates its target for a confirm-back. The protected-target guard lifts (stamped); the EntraID self-escalation guard **never** lifts. No new capability: the catalogue is still the wall — breakglass changes *who approves*, never *what exists*.
- **Ends** on timer, manual disarm, incident resolve, or session supersede. Every transition writes the timeline, the Platform Log, and a Teams **System event** (the new platform-level notification type) — on arm *and* end. No mandatory post-hoc review: the trail is the record, and the trail is what going-direct can never provide.

## Reports

*Agreed 2026-08-07 (sprint sw5yz4n, ISE-615..619; ADR 0093 to be written with the build).* A report is a **frozen, deterministic query over the estate** that renders a PDF on a schedule or on demand. AI may help *author* the query — a one-shot agent drafts the structured spec, the human reviews, previews and saves it (the incident-learning pattern) — but **a run never touches AI**: it is the saved spec compiled to SQL, the same code path as the preview, byte-for-byte. The spec language is the existing `AttributeFilter` predicate vocabulary plus the entity-list filters and a group scope; the drafted object and the hand-built object are the same pydantic model, so there is no second dialect.

- **Schedules are calendar promises, not intervals.** "Daily at 07:00" in a per-report IANA timezone, dispatched by the house beat-tick + next_run_at gate. Still no cron anywhere.
- **Artifacts live in S3-compatible object storage, config-driven** — ISE's first blob store. Code targets the S3 API from settings; the chart ships MinIO by default, any endpoint can be pointed at. Runs keep a `spec_snapshot` so an artifact stays explainable after the report is edited; retention deletes the object before the row so nothing orphans.
- **Templates are sandboxed Jinja2 HTML** (autoescape, StrictUndefined), A4 portrait/landscape via `@page` CSS, rendered server-side by WeasyPrint in the worker only. v1 templates are code-declared; the format *is* the custom-template format for the later sprint — the registry lookup is the only seam.
- **Viewer reads, operator writes** — the dashboards mapping; the PDF only contains entity data viewers already see.

## Why it's shaped this way

Detection already exists inside the sources, so ISE forwards Alerts cheaply and deterministically. ISE spends real compute only where it must — on Observations, on a slow loop — and only on confirmed signal, inside an Incident investigation a human cares about. Competence comes overwhelmingly from what ISE builds — the knowledge base, methods (playbooks) and memory — not from the raw model or integrations; and that scaffolding is simultaneously the quality play and the cost fix, because good context and method let a cheaper model do less work for a better answer. The design keeps the expensive, AI-driven work off idle timers and pointed at things that are actually happening.

## Delivery philosophy

Design the whole target before building, so the data model and capabilities are right and **nothing has to be torn up and rebuilt**. Deliver it incrementally, but only in slices that are *permanent parts of the final thing* — never throwaway scaffolding a later phase supersedes. Where feedback matters (and for a product proving its own viability, it does), deliver the **load-bearing spine first** — for the knowledge base, that is entities + aliases + resolve-during-investigation — because the remaining registers (context, tuning), drift detection and conversational enrichment all hang off that spine additively.
