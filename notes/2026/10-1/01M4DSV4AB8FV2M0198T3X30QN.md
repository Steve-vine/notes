Found by Steve testing access control on staging, 2026-10-08 (`4131ac79`). Follow-up to COM-849 (a mover's account details).

## What happened

On a move request, after picking a new Primary role, the **Account details** section opens with:

> What the account says now couldn't be read — Active Directory could not be reached. Anything filled in here will be set; anything left blank is left alone.

It shows every time, for every AD account.

## Is it true?

**The first half is false. The second half is true.**

- Active Directory *was* reachable. The connection check passed at 12:53, 12:58 and 13:03 UTC ("Connected to moneypenny.local through mpwxdc01 … with Kerberos") and the AD sync ran clean at 12:52, 12:57 and 13:02 — the banner was on screen at 12:56–13:02.
- "Anything filled in will be set; anything left blank is left alone" is what happens: the request keeps everything sent, and the run reads the account again and writes only what differs.

## What people lose

- The form can't show what each field says today, so the role's defaults appear as "will be set to" with nothing beside them.
- The request records no "before" value, so the approver can't see what is being replaced.
- A field already as asked isn't dropped at submit (it is at run time, so nothing wrong is written).
- A field can't be cleared from the form — a blank is "left alone" when the account couldn't be read.

## Cause

`core/account_details.read_now` opens the AD connection **in the API pod** — it is called from `GET /access-requests/mover-details` (`api/v1/access_requests.py:1480`) and again when the request is raised (`:418`). It is the only place the API talks LDAP; everything else AD goes through the worker.

The chart gives the route to AD to the **worker only** — `networkAddon.targets: [worker]` is the default, staging's setting, and what `chart/values.yaml` and `chart/README.md` document ("worker — the only pod that talks LDAP", "worker is enough for AD"). On staging the API pod has no Twingate sidecar, so `connect()` raises and `read_now` reports "Active Directory could not be reached".

So this is not a staging quirk: any install that follows the documented setup gets the banner.

Two smaller faults in the same place:
- **Nothing is logged.** `mover_details` swallows `Unreadable`; the API log shows only a 200. Log a warning with the exception class (no values — they're personal data).
- **The wording guesses.** Every `ActiveDirectoryError`/`OSError` from `connect()` becomes "could not be reached" — a refused sign-in or a Kerberos failure would say the same.

## Fix

Do the live read where the route is: a small worker task (ids in, JSON out — account id + attribute names → readings or an unreadable reason), called from the API with a bounded wait, the way Test connection for Exchange already does (`check_exchange_connection_health.apply_async().get(...)`, `api/v1/integrations.py:597`). Use it for both callers (`:418` and `:1480`). On timeout the form carries on as it does today, saying Compass didn't get an answer in time — not that AD is down.

Not the fix: adding `api` to staging's `networkAddon.targets`. It would hide the fault on staging and leave it in every other install, and it contradicts the chart's own documentation.

Keep the Entra read as it is (the API pod can reach Graph) unless one path for both is simpler.
