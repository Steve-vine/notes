Found by Steve on staging, 2026-10-07: *"I just put in a leaver request, to be disabled at 15:45 today, but it disabled it immediately."*

Decided by Steve the same day: *"Expedited avoids the validation to allow a person to submit a change if nobody was available to approve it. It should still run on the schedule if one is set."*

## What happened

A leaver was raised at 15:36 with **Run at** set to 15:45 and sent with **Submit expedited**. The form threw the time away without saying so and the account (Arthur Pickle, staging) was disabled at once. The request holds no time at all.

That was built on purpose — "expedited means now, so it never carries a time" — and it is the wrong rule. Expedited exists for when nobody is available to approve; it is about **who has to say yes**, not about **when it runs**. A leaver whose last day is Friday, raised on a day the approver is away, should not have to be either left until someone is back or disabled days early.

## What people see

- **Submit expedited with a Run at time** raises the request without waiting for approval, and it **runs at that time** — within five minutes of it, like any scheduled request. Until then it reads **Scheduled**, and nothing has been changed in the directory.
- **Submit expedited with no time** runs now, as it does today.
- **Before it runs**, a scheduled expedited request can have its time changed or be cancelled, the same as an approved request waiting for its time.
- **After it runs**, it is validated by a second person, exactly as an expedited change is today. The time allowed for validation is counted **from when it runs**, not from when it was raised — there is nothing to check before then.
- **"Delete the account afterwards"** works as now: the days are counted from when the account is actually disabled.
- **The form says what it will do.** The small print "Not available on an expedited change — that runs now" goes. The note under the buttons becomes: *"Expedited skips approval: it runs now — or at the Run at time, if one is set — and must be validated by someone else afterwards."*
- **The timeline** reads Raised (expedited) → Scheduled to run → Executed, with the time it actually ran. It no longer says "Executed immediately" for one that waited for its time.

## What's permanent

The request records that it was expedited, who raised it, the time it was set to run, and the time it ran — so afterwards it is plain that nobody approved it and that it was not run early.

## Decisions taken (say if any is wrong)

- **Expedited still gets a second pair of eyes afterwards.** Read "avoids the validation" as "avoids the approval": the check after the fact stays. If you meant that to go as well, say so — that is a much bigger change.
- **A scheduled expedited request is not re-checked by anyone before it runs.** It is visible on the Requests list as Scheduled, expedited, and can be cancelled by anyone who could cancel it today — but nothing asks for a yes.
- **A leaver for an administrator's account** still needs an Access Admin's approval before it runs, expedited or not, scheduled or not. That rule is about the account, not the mode.
- **Only leavers have a Run at time today**, so only leavers change. If scheduling is later offered on joiners or movers, the same rule applies to them.
- **A time in the past** runs at the next sweep (within five minutes), as it does for a standard request — late is not skipped.

## Notes (technical)

- **ADR first.** This reverses a stated rule: ADR 0066 (scheduling) has expedited refuse a time, and ADR 0045 §6 describes expedited as execute-now-validate-later. Write `decisions/NNNN-*.md` superseding those sentences — expedited means *no prior approval*, not *now*. Don't edit the accepted ADRs.
- Form: `app/frontend/src/access/RaiseRequestModal.tsx` — `send()` builds `scheduled_for: mode === 'expedited' || !runAt ? null : …`; drop the `mode === 'expedited'` clause so the form sends what is on screen. `LeaverSchedule`'s description and the note under the buttons carry the old rule in words.
- Server, raise: `_validate_schedule(kind, mode, scheduled_for, delete_after_days)` in `api/v1/access_requests.py` refuses a time on an expedited request — allow it. `create_request` dispatches `execute_access_request.delay` at once for expedited (status `submitted`); with a future `scheduled_for` it must not.
- Server, run: `sweep_due_access_work` (`tasks/access_execute.py`) fires `status == approved AND scheduled_for <= now AND scheduled_fired_at IS NULL`, claimed by `_claim_scheduled_run`. A scheduled expedited request has no approval, so either the sweep and the claim take `submitted` too, or it gets a state of its own. Prefer the former — no new lifecycle value on a live enum (the reason ADR 0087 gives). `execute_access_request` already accepts `submitted`.
- Status: `display_status` reads *Scheduled* only for `approved` with a future time; extend to `submitted` with a future time. `_BEFORE_IT_RAN` maps `submitted` → "submitted" today.
- Validation clock: `validation_due_at` is set at creation (`add_business_days`); for a scheduled expedited request set it when it runs (`_finish`), and make the overdue-validation reminders/actions ignore one that has not run.
- Reschedule / cancel: `reschedule_request` and `cancel_request` check the status — allow `submitted` with `scheduled_fired_at IS NULL`. The privileged-account gate (`_require_privilege_gate`, `KINDS_GATED_ON_A_PRIVILEGED_ACCOUNT`) must still be met before a scheduled expedited leaver on an admin account runs — today that approval happens at the approve step, which an expedited request never passes through; check how an expedited leaver on a privileged account is handled now and keep it equivalent.
- Timeline: `RequestTimeline` in `RequestDetailPage.tsx` — "Executed immediately (requester = approver = executor)" for every expedited request; say "Executed" with the time when it was scheduled. COM-852's Completed entry is unaffected.
- Requests list: the Scheduled pill and the Mode pill (COM-853) already sit side by side — check an expedited scheduled request reads as both.
- API change → regenerate `schema.d.ts`, run the drift script. No migration expected.
- Tests: raise expedited with a future time → not executed, reads Scheduled, nothing written; the sweep runs it at its time → pending validation, validation due counted from then; expedited with no time still runs at once; reschedule and cancel before it runs; a past time runs at the next sweep; the privileged-account gate; the form sends the time with either button; the timeline wording.

## Done when

- An expedited leaver with a Run at time is disabled at that time, not before, with no approval step.
- An expedited leaver with no time runs at once, as today.
- It can be rescheduled or cancelled before it runs, and is validated after.
- The form, the list and the timeline all say what will happen and what did.
- The ADR is written.
- Smoke-tested on staging: raise an expedited leaver for ten minutes' time; check the account is still enabled; check it is disabled within five minutes of the time.
