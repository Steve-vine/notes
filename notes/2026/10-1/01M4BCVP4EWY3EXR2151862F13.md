Found by Steve on staging, 2026-10-07: *"I just put in a leaver request, to be disabled at 15:45 today, but it disabled it immediately."*

## What happened

The leaver was raised at 15:36 with **Run at** set to 15:45 and sent with **Submit expedited**. An expedited change runs the moment it is submitted — that is what expedited means — so the form **threw the time away without saying so** and the account (Arthur Pickle, staging) was disabled at once. Nothing was scheduled; the request holds no time at all.

The only warning is a line of small print under the field: "Not available on an expedited change — that runs now." Both buttons stay live with a time filled in, and the one that ignores it sits right beside the one that honours it. On a form whose whole job is to take someone's access away, that is a trap.

Scheduling itself is not broken: a leaver sent with **Submit for approval** keeps its time and runs then.

## What people see

- With a **Run at** time filled in, **Submit expedited** is **disabled**, and a line beside the buttons says why: *"Expedited runs now — clear 'Run at' to expedite, or use Submit for approval to run it at 15:45."*
- Clear the time and Submit expedited works as before.
- **Submit for approval** is unchanged.
- Through the API, an expedited request carrying a time is refused with the same message (it already is — keep it, and check the wording).

## Decisions taken (say if any is wrong)

- **Disabled, not a confirmation.** A prompt ("this will run now, not at 15:45 — continue?") is one more thing to click through in a hurry. If a time has been typed, the person meant it; make them take it out to expedite.
- **Not "an expedited request that runs later".** Expedited is break-glass: one person, no approver, runs now, validated afterwards. Letting one be scheduled would be a way to skip approval for an ordinary planned leaver.
- **The same rule for "Delete the account afterwards"** is *not* applied: an expedited leaver can still carry a deletion (it did here — one day), because the deletion is its own later step with its own cancel.

## Notes (technical)

- `app/frontend/src/access/RaiseRequestModal.tsx`: `send()` builds `scheduled_for: mode === 'expedited' || !runAt ? null : …` — that `mode === 'expedited'` is the silent drop. `LeaverSchedule` carries the small-print description; the buttons are at the foot of `RaiseForm`.
- Disable "Submit expedited" when `kind === 'leaver' && runAt`, and show the reason next to it (a disabled button can't carry a tooltip reliably — say it in text). Remove the silent drop from `send()` so the form can never again send something other than what is on screen; let the server's refusal be the backstop.
- Server: `_validate_schedule` in `api/v1/access_requests.py` already refuses a time on an expedited request — confirm the message reads in the same words.
- Check the same pattern anywhere else a form sends different values per button.
- Tests: `RequestsPage.test.tsx` / the raise-form tests — with a time set, Submit expedited is disabled and the reason is shown; clearing it re-enables; a standard submit still carries the time; nothing is ever sent with the time stripped.

## Done when

- A leaver with a Run at time cannot be sent expedited from the form, and the form says why.
- A leaver sent for approval with a time still runs at that time.
- No path sends a request that differs from what the form shows.
