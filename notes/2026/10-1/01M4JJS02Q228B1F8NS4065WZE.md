## What Steve asked (2026-10-10)

"On a request window (this is obvious on the mover window but may be on other windows), when displaying a popup such as clicking on a folder to see the details, the natural way to close the popup is to hit escape but this closes the whole mover requester, escape should just close the popup not the window."

## Behaviour wanted

- With a popup open inside a window, **Escape closes the popup only**. The window stays open and nothing typed or picked in it is lost.
- Focus goes back to the thing that opened the popup, so the keyboard carries on from where it was.
- With no popup open, Escape closes the window, as it does today.
- The same in every window, not only the move form — and for any popup added later without anyone having to remember.

## Where it happens today

Found by reading the code, not yet reproduced in a browser:

- **Move form** — every details box: Membership diff pills, Role groups, Manual groups, Dynamic groups (`MoverStayingGroups.tsx`, four `Popover`s) and the shared-mailbox pills (`MoverMailboxes.tsx`, `MailboxPill`).
- **Leaver form — "Run at"** (`RunAtInput.tsx`, `DateTimePicker`, which is a popover underneath). Likely the same; confirm first.
- Those are the only `Popover` / date-picker uses inside a `Modal` today (77 files use `Modal`; `ShellSearch` and `AccessGraphPage` use `Popover` on a page, not in a window).
- **Not affected:** `Select` / `MultiSelect` / `Menu` dropdowns already keep Escape to themselves.

## Why (Mantine 8.3.18)

`Modal` listens for Escape on `window` in the capture phase (`ModalBase/use-modal.mjs`) and closes unless `event.target` carries `data-mantine-stop-propagation="true"`. Combobox targets and Menu items set that attribute while open; `Popover` does not. So one Escape closes the popover (its dropdown's `onKeyDownCapture`) *and* the modal. The modal's listener is registered first and on `window`, so `stopPropagation` / `stopImmediatePropagation` from the popover cannot beat it.

## Approach (decide at build time)

One shared piece rather than five fixes:

- A shared popup component (or hook) for "a details box inside a window" that, while open, stops the enclosing window closing on Escape — e.g. a small context the window provides and the popup registers with, driving the `Modal`'s `closeOnEscape`; or setting the stop attribute on whatever holds focus inside the dropdown. Whichever is chosen must also cover the date picker in `RunAtInput`.
- `returnFocus` on the popovers so focus lands back on the pill.
- Add a line to `brief/information-architecture.md` → *Screen conventions*, and a check in the screen-conventions test that a bare `Popover` is not used inside a `Modal`, so the next popup gets it for free.

No backend change, no migration, no ADR (no architecture decision in it).

## Out of scope

- Asking "discard your changes?" when a window with something filled in is closed — that is **COM-897**, built after this one (it changes the same close path).
- Clicking outside a popup — already closes the popup only.

## Done when

- Move form: open a group / role group / dynamic group / mailbox box, press Escape → box closes, form still open with its roles, adds and removes intact; Escape again → form closes.
- Leaver form: open "Run at", press Escape → the calendar closes, the form stays.
- A `Select` dropdown inside a window still behaves as before.
- Tests: Escape with a popup open leaves the dialog in the document; a second Escape removes it. One test per shared piece, plus the move form and Run at.

## Smoke test (Steve — Safari)

1. Access → raise a move for someone. Click a manual group pill, press Escape: only the box closes.
2. Same for a role group, a dynamic group and a shared mailbox.
3. Pick a role and add a group first, then repeat step 1: what you picked is still there.
4. Raise a leaver, open "Run at", press Escape: the calendar closes, the form stays.
5. With nothing open, Escape closes the window.
