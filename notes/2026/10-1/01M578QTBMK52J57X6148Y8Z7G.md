Part of sprint 67, Inventory discovery - Software (ADR 0114). Fix-forward for COM-964. Found on staging, 2026-10-18.

## Why

COM-964 names each Azure VM's operating system from its image, which works: Windows Server 2012 R2, Windows Server 2022 and Ubuntu 22.04 on the PayAsGo2 subscription. What the VM's guest agent reports (its own name for the operating system and its version, e.g. "Windows Server 2022 Datacenter Azure Edition", 10.0.20348) is blank on all three VMs. All three are running on standard images, so their agents should be reporting. Opening one shows only "Operating system: Windows", with no version. AWS servers and domain-joined servers show both name and version.

## What people see

- **An Azure VM whose guest agent is running shows "Operating system, as its agent reports it" and "Operating system version, as its agent reports it"** on its details, as AWS servers do.
- **Discovered ▸ Software uses the agent's report where there is one,** as AWS does. It is more precise than the image name, and stays right after an in-place upgrade. The image name is still the fallback.
- **A VM that is stopped, or whose agent isn't running,** keeps the name from its image, and its version reads "not reported" rather than blank.
- **No permission changes:** the role already has what this needs.

## Notes (technical)

- `azure/compute.py` reads `osName`/`osVersion` from the subscription-wide `virtualMachines?statusOnly=true` listing. On staging, that listing returns the power state but not `osName`/`osVersion`. Check this against a real response first, as it's not yet proven.
- Likely fix: `GET {vm}/instanceView` per VM (same `Microsoft.Compute/virtualMachines/instanceView/read` action), which returns `osName`, `osVersion` and `vmAgent`. Ask only for running VMs, so a stopped VM costs nothing. This is one call per running VM; keep the statusOnly listing for power state.
- Feed the agent's name/version into the server-OS deriver (`core/discovery/os_names.py`) ahead of the image, matching the AWS order (agent → image), with `found_by` recording which one.
- Scale sets: check whether their instances' views carry the same, and do the same if so, or say they don't.
- Tests: a fake with the statusOnly listing lacking OS fields and per-VM instance views that have them; a stopped VM (no call, image name kept); a VM whose view has no `osName` (falls back to image, version "not reported").

**Done when:** on staging, the three PayAsGo2 VMs show the agent-reported operating system and version on their details, with no change to the role.
