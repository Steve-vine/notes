Raised by Steve, 2026-09-06, to bring risk statements into line with how the ISO standards ask them to be written.

A risk is currently a **title** and a free-text **description**, which lets somebody write "Ransomware" and stop. What a risk statement is supposed to say is: *because of this condition, this event might happen, and if it does these objectives suffer.* One box invites the first third of that.

## What changes

**`description` is replaced by three fields:**

- **Cause/condition**
- **Potential event**
- **Consequence/impact on objectives**

**The scores move next to the text they score** (Steve's call, 2026-09-06 — both pairs):

```
Cause/condition
[                                        ]

Potential event                 Likelihood
[                          ]   inherent [3] residual [2]

Consequence/impact              Impact
[                          ]   inherent [4] residual [4]
```

That layout is the argument for itself: **likelihood is the chance of the event, and impact is the severity of the consequence.** Putting each score beside the sentence it grades is what stops the numbers being chosen in the abstract — the same problem COM-579 addresses from the other side by naming the levels. The two together turn scoring from "pick a 3" into "how likely is *this event*, on this scale".

## Now is the cheapest possible moment

Staging holds **one risk, with no description at all**, and two revisions. So there is nothing to preserve and no transformation to get right. Do this before real risks are written and it is a schema change with no data problem attached.

**Before production, check that again.** If any risk has a description by then it has to be placed, not dropped — the honest destination is Cause/condition (it is where an unstructured statement usually starts) with the other two left empty, rather than a guess at splitting a sentence three ways.

## What else it touches

- **Risk revisions** snapshot the description. History is immutable, so old revisions keep the field they were written with; the new fields join the snapshot from here on. Do not rewrite history to make it look as though risks were always written this way.
- **Global search** indexes title and description today. It should index the three new fields — otherwise searching for a consequence you know you wrote finds nothing.
- **The API changes shape** (ADR 0004): schemas, the snapshot field list, regenerate `schema.d.ts`. Check the risk PDF and CSV reports render the three fields rather than silently dropping the removed one.
- **Required or optional?** Suggest all three optional at the API and none of them blocking a save — a risk half-written is still worth recording — but the form should make it obvious that a risk with only a cause is unfinished. Say if you would rather the event be mandatory.

## Related

- COM-579 — naming the levels on the likelihood and impact pickers. Same screens; land them together and scoring reads properly end to end.
