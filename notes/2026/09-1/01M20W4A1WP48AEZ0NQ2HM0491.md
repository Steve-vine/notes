    Done — merged as b19076a (squash, PR #416). CI green; branch deleted. Recorded as ADR 0059.

    Every checklist item landed, with one deliberate design change from what the task specified.

    **The change: an OS advisory lock, not a pid file.** The task called for "a lock file with the holder's pid" plus stale-lock takeover. Writing it that way, the takeover rule turns out to be the whole difficulty — the failure that matters is a syncer that died *without* tidying up (SIGKILL, OOM, a torn-down tmux session), and every liveness check is either non-portable (`/proc`, `kill(pid, 0)`) or a heartbeat with a staleness window to size and a clock to trust. An OS lock is released by the kernel when the fd closes however the process ended, so a stale lock isn't a state that can exist. That deletes the takeover item entirely rather than implementing it: no window, no clock, no takeover logic. The pid still goes in the file, but only to name the holder in a message.

    Costs one dependency, `fs4`, for the cross-platform primitive.

    What landed:

    - `GitSync::start` acquires `.notuvia/git-sync.lock` before spawning anything, and holds it for the worker's lifetime. Inside the gitignored index dir specifically, so one machine's pid can never be committed and pushed to another.
    - Losing is a normal outcome: `start` still returns a handle, `locked()` names the holder, no worker runs. Callers keep one code shape either way.
    - A locked-out `sync_now` names the owner instead of failing as "worker is stopped" — a manual Sync now that quietly does nothing is the invisible failure this exists to end.
    - `--sync-only` that loses logs it and exits non-zero, as specified. That interacts with the `Restart=always` I documented under NOT-418, so the unit gained `RestartSec=10` in the same PR — otherwise a genuinely double-configured daemon hot-loops.
    - Seven tests. Locks are per *open file description*, so a second acquire in the same process is refused exactly like one from another process — all of it testable without spawning children. The one worth naming is `a_locked_out_worker_never_commits`: a second worker that quietly worked would look fine, so that's the regression with teeth.

    **Known regression, deliberately shipped.** The rule is symmetric — the app takes the same lock — so the app can now lose sync to a sidecar that started first, where before both ran. `SyncStatus::locked_by` and its `vault.ts` mirror carry the fact, but nothing surfaces it, so on a laptop it would look like sync had simply stopped.

    Symmetry was the call: an app exemption is a second rule to remember, and app-plus-sidecar is the hazard ADR 0036 already named. The UI gap is recorded as follow-up in ADR 0059 rather than guessed at — `SyncAlert.svelte` is the right home, but it needs a new banner variant with its own copy and dismissal key, and someone should look at it.

    Verified locally against every CI gate before pushing: `cargo test --workspace` (398 + 40 + 27 + 2), `cargo fmt --check`, `cargo clippy --all-targets -D warnings`, `npm run check` (369 files, 0 errors), `npm test` (323), `npm run build`.

    Shipping in 0.24.0 alongside NOT-416 and NOT-418.

Follow-up from NOT-416, where this was the amplifier held out of scope.

Nothing stops N processes running the sync worker against one vault. On the
headless Linux box ten `notuvia-mcp --git-sync` instances were alive — one per
long-lived tmux Claude session — with seven fetching concurrently. Each was
independently paying NOT-416's inflated fetch cost, and together they were most
of a load average of 4.6.

ADR 0036 waved this through in its last consequence: "Two committers can now
target one clone... Each worker's cycles are internally serialised and git
itself arbitrates the rest, but the mode is documented as being for app-less
machines." True for two, and the mode being *documented* as single-owner is
exactly the weakness — the MCP server is spawned per client session, so the
count tracks how many agent sessions are open, which is not a number anyone
manages.

## Agreed work

- [ ] `GitSync::start` takes an advisory lock on the vault (a lock file under
      `.notuvia/`, held for the process lifetime, with the holder's pid).
- [ ] A process that can't take it starts **without** a sync worker rather than
      failing: it still serves MCP normally, and logs to stderr that another
      syncer owns the vault, naming the pid.
- [ ] A stale lock (holder gone) is taken over, so a killed process doesn't
      leave the vault permanently unsyncable.
- [ ] `--sync-only` is unaffected when it wins the lock; if it loses, it should
      say so loudly and exit non-zero — a daemon with nothing to do is a
      misconfiguration, not a degraded mode.
- [ ] Tests: two runtimes on one vault yield exactly one worker; the second
      still serves; killing the first lets the second take over.
- [ ] ADR amending 0036's single-owner consequence from convention to mechanism.

## Why this and not just operator discipline

The operational fix (one `--sync-only` daemon, per-session MCP registered
without `--git-sync` — see NOT-418) is correct and should land first, but it
leaves correctness resting on nobody ever passing the flag again. Eight-day-old
tmux sessions are precisely what discipline doesn't catch.

## Note for whoever picks this up

The watcher has no path to the sync worker — `watcher.rs` doesn't reference
gitsync at all, and every `git_touch()` call sits in `runtime.rs`'s write ops.
So a worker only auto-commits writes made by its **own** process; other
processes' writes are picked up by its interval tick, where `commit_local`
commits whatever is pending regardless of author. That is what makes a single
shared worker correct, and it's worth an explicit test.
