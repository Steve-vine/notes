ADR 0073 §5. Today the database is a hard external prerequisite that also demands the CNPG operator, so trying Compass on minikube means installing an operator and authoring a `Cluster` CR first. That is the largest single barrier to "anyone with a Kubernetes cluster can install this".

**A plain StatefulSet, on the pattern Valkey already uses** — no operator, no CRD, off by default. Turn it on and `helm install` on a bare minikube produces a running Compass with nothing else present.

**It is for evaluation and the values file says so in those words**: no backups, no failover, no high availability. Every real deployment supplies a `DATABASE_URL`, and that one path serves CNPG, RDS, Cloud SQL, Azure Flexible Server and a hand-rolled Postgres identically.

**Notes**

- Postgres 16 or later, and `pg_trgm` must be creatable — a migration runs `CREATE EXTENSION IF NOT EXISTS pg_trgm`. The bundled image satisfies this; document that **Azure Flexible Server does not** until `pg_trgm` is added to the `azure.extensions` server parameter, and the migration fails with a permissions error if it is not.
- The bundled database's password is generated by the chart (see the secrets task) and the `DATABASE_URL` derived from it, so enabling it needs no values beyond the toggle.
- The CNPG `Cluster` CR stays out of the chart — ADR 0005, reaffirmed by ADR 0073, and rejected explicitly in that ADR's Alternatives. `scripts/infra/` keeps the example manifests, and what they produce is just another connection string.
- Pin the image by digest rather than a moving tag, for the same reason the Valkey image should be (ADR 0008).

**Acceptance**: `minikube start` then `helm install compass oci://… --set postgres.enabled=true --set ingress.enabled=false` gives a working Compass reachable by port-forward, with no operator, no CRD and no other values supplied.
